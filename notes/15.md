## 一、概述

### 1.1 背景

当前Agent已具备Agent工作目录、Session工作目录、用户工作目录下的文件读写能力。需要在此基础上设计计划文件的落地方案，使Agent能够“先规划、后执行”，并在执行过程中严格遵循已确认的计划。

### 1.2 设计目标

- Agent接到任务后，先生成计划供用户审阅，经确认后方可执行
- 执行过程严格按照计划步骤顺序进行，不允许自行偏离
- 支持会话中断后的断点恢复
- 计划严格绑定会话生命周期，会话结束即清理

---

## 二、核心决策

| 决策项 | 选择 | 说明 |
|--------|------|------|
| 计划文件格式 | Markdown + JSON | Markdown用于人可读的计划主文件，JSON用于Agent自动维护的执行状态 |
| 审批机制 | 确认后执行 | 计划生成后状态为draft，需用户确认变更为confirmed后方可执行 |
| 并行支持 | 不支持 | 同一会话内同时只允许一个活跃计划 |
| 变更策略 | 严格模式 | 执行中任一步骤失败，计划立即暂停，等待用户介入 |
| 存储位置 | 会话工作目录 | 计划跟随会话生命周期，避免跨会话残留 |

---

## 三、目录结构

```
{session_work_dir}/
├── plan.md              # 计划主文件（人可读、Agent可解析）
├── progress.json        # 执行状态文件（Agent自动维护，用于断点恢复）
└── outputs/             # 会话执行产出文件目录
```

**设计考量：**
- 计划文件与会话工作目录共存，会话结束时整体归档或清理，无跨会话残留
- 单会话仅维持单计划，无需计划ID标识，扁平化结构即可满足需求
- outputs目录用于存放计划执行过程中产出的中间文件或最终交付物

## 四、文件格式规范

### 4.1 计划主文件（plan.md）

以Markdown格式承载，兼顾人类可读性与Agent解析需求。

**字段说明：**

| 字段 | 说明 | 可选值 |
|------|------|--------|
| 标题 | 计划名称 | 自由文本 |
| status | 计划生命周期状态 | draft / confirmed / executing / blocked / done |
| created | 创建时间戳 | ISO 8601格式 |
| 任务列表 | 编号的有序任务清单，使用Markdown checkbox标记完成状态 | - [ ] 未完成 / - [x] 已完成 |

**模板示例：**

```markdown
# 计划: {任务名称}
status: draft
created: {创建时间}

## 任务列表
- [ ] 1. {步骤描述}
- [ ] 2. {步骤描述}
- [ ] 3. {步骤描述}
```

### 4.2 执行状态文件（progress.json）

由Agent自动维护，用于追踪执行进度和支撑断点恢复。

**字段说明：**

| 字段 | 类型 | 说明 |
|------|------|------|
| plan_file | string | 关联的计划文件名，固定为"plan.md" |
| status | string | 当前执行状态，与plan.md中的status同步 |
| current_step | number | 当前正在执行的步骤编号 |
| steps | array | 步骤详情列表 |
| steps[].id | number | 步骤编号，对应plan.md中的序号 |
| steps[].desc | string | 步骤描述摘要 |
| steps[].status | string | 步骤状态：pending / doing / done / failed |
| steps[].result | string/null | 步骤执行结果摘要或错误信息 |

**模板示例：**

```json
{
  "plan_file": "plan.md",
  "status": "executing",
  "current_step": 3,
  "steps": [
    {"id": 1, "desc": "扫描下载文件夹", "status": "done", "result": "找到23个文件"},
    {"id": 2, "desc": "按扩展名分类", "status": "done", "result": "4类别"},
    {"id": 3, "desc": "创建子文件夹", "status": "doing", "result": null},
    {"id": 4, "desc": "移动文件", "status": "pending", "result": null},
    {"id": 5, "desc": "生成报告", "status": "pending", "result": null}
  ]
}
```

## 五、状态流转

### 5.1 计划生命周期

```
                    ┌──────────────┐
                    │    draft     │  ← Agent初始生成
                    └──────┬───────┘
                           │ 用户确认
                           ▼
                    ┌──────────────┐
                    │  confirmed   │  ← 等待执行指令
                    └──────┬───────┘
                           │ 开始执行
                           ▼
                    ┌──────────────┐
              ┌─────│  executing   │
              │     └──────┬───────┘
              │            │ 全部步骤完成
              │            ▼
              │     ┌──────────────┐
              │     │     done     │  ← 终态
              │     └──────────────┘
              │
              │     步骤执行失败（严格模式）
              │            │
              │            ▼
              │     ┌──────────────┐
              └────►│   blocked    │  ← 暂停，等待用户介入
                    └──────┬───────┘
                           │ 用户修改计划后重新确认
                           ▼
                    ┌──────────────┐
                    │  confirmed   │  ← 回到确认态，可重新执行
                    └──────────────┘
```

### 5.2 步骤状态

| 状态 | 说明 | 触发条件 |
|------|------|----------|
| pending | 等待执行 | 初始状态或前置步骤未完成 |
| doing | 执行中 | Agent开始处理该步骤 |
| done | 已完成 | 步骤成功执行完毕 |
| failed | 执行失败 | 步骤执行异常，严格模式下触发计划blocked |

## 六、核心工作流

### 6.1 计划生成与确认流程

```
1. 用户提出任务需求
2. Agent分析需求，生成plan.md（status: draft），呈现给用户
3. 用户审阅计划
   ├─ 同意 → 用户将status改为confirmed（或发送确认指令）
   ├─ 修改 → 用户直接编辑plan.md，再改为confirmed
   └─ 否决 → 废弃计划，Agent重新规划
4. plan.md进入confirmed态，等待执行指令
```

### 6.2 计划执行流程

```
1. Agent读取confirmed状态的plan.md
2. 将plan.md状态更新为executing
3. 创建/重置progress.json，所有步骤置为pending
4. 按步骤编号顺序逐个执行：
   a. 将当前步骤status置为doing，更新current_step
   b. 执行该步骤的实际操作
   c. 成功 → 步骤status置为done，result记录结果摘要
   d. 失败 → 步骤status置为failed，result记录失败原因
       → 计划status置为blocked
       → 通知用户，等待介入
   e. 同步更新plan.md中对应checkbox状态（- [x]）
5. 全部步骤完成 → 计划status置为done
```

### 6.3 阻塞恢复流程

```
1. 计划处于blocked状态
2. 用户介入处理（修改plan.md调整步骤）
3. 用户将status重新设为confirmed
4. Agent读取更新后的plan.md
5. 识别上次失败步骤，从该步骤恢复执行
6. 后续步骤继续按顺序进行
```

## 七、断点恢复机制

### 7.1 触发时机

- Agent每次启动或收到执行指令时
- 执行步骤发生异常后重新调度时

### 7.2 恢复逻辑

```
1. 检查{session_work_dir}/progress.json是否存在
   ├─ 不存在 → 无历史计划，进入正常新建/读取流程
   └─ 存在 → 进入步骤2

2. 检查progress.json中的status字段
   ├─ executing → 存在未完成计划，进入步骤3
   ├─ blocked → 存在暂停计划，提示用户有阻塞计划待处理
   ├─ done → 计划已完成，提示用户是否创建新计划
   └─ confirmed → 异常状态，按executing处理

3. 读取current_step，定位到对应步骤
   ├─ 该步骤status为doing → 说明上次执行中断，重新执行（步骤需保证幂等）
   ├─ 该步骤status为pending → 说明上次未开始，正常执行
   └─ 该步骤status为done → 异常状态，从下一pending步骤开始

4. 从定位步骤开始，继续顺序执行
```

### 7.3 幂等性要求

由于断点恢复可能重复执行status为doing的步骤，每个步骤的实现需保证幂等性，即重复执行不会产生副作用或错误。

## 八、严格模式故障处理

### 8.1 故障分类

| 故障类型 | 示例 | 处理方式 |
|----------|------|----------|
| 可预见的业务失败 | 文件不存在、权限不足 | 步骤标记failed，计划blocked，告知用户原因 |
| 意外异常 | 程序崩溃、网络超时 | 步骤保留doing状态，下次启动触发断点恢复 |

### 8.2 blocked态处理细则

1. Agent停止所有后续步骤的执行
2. 在当前步骤result中记录明确的失败原因
3. plan.md和progress.json双双更新为blocked状态
4. 向用户输出：“步骤{N}执行失败：{原因}。计划已暂停，请修改后确认继续。”
5. 等待用户操作，期间不接受其他任务指令

## 九、文件同步策略

plan.md与progress.json存在状态冗余，需保证二者一致：

| 事件 | plan.md更新 | progress.json更新 |
|------|-------------|-------------------|
| 计划生成 | 创建文件，status: draft | 不创建 |
| 用户确认 | status改为confirmed | 不创建 |
| 开始执行 | status改为executing | 创建，status: executing |
| 步骤开始 | 对应checkbox标注进行中（可选） | 该步骤status: doing，更新current_step |
| 步骤完成 | 对应checkbox改为- [x] | 该步骤status: done，填充result |
| 步骤失败 | 无需额外更新 | 该步骤status: failed，填充result，全局status: blocked |
| 计划完成 | status改为done | status: done |

**同步原则：** progress.json是执行状态的主数据源，plan.md的更新为辅助性、人类可读性服务。恢复时以progress.json为准。

## 十、目录与文件操作权限

| 操作 | 目标位置 | 说明 |
|------|----------|------|
| 创建计划文件 | {session_work_dir}/plan.md | 会话工作目录，Agent完全可写 |
| 维护执行状态 | {session_work_dir}/progress.json | 会话工作目录，Agent完全可写 |
| 产出中间文件 | {session_work_dir}/outputs/ | 会话工作目录，按需创建 |
| 交付最终产物 | {user_work_dir}/ | 用户工作目录，由计划步骤中明确指定路径 |
| 读取外部文件 | {user_work_dir}/ | 用户工作目录，计划步骤中指定读取路径 |

Agent工作目录不作为计划文件的存储位置，仅用于跨会话共享的Agent配置或持久化数据。

## 十一、边界情况处理

| 场景 | 处理方式 |
|------|----------|
| 用户试图开始新计划但当前有计划未完成 | 提示存在进行中的计划，需先完成或放弃 |
| 用户直接删除plan.md | progress.json检测关联文件不存在，视为计划废弃，清理progress.json |
| 用户直接删除progress.json | 视为重置执行进度，Agent重新从plan.md步骤1开始执行 |
| plan.md与progress.json状态不一致 | 以progress.json为准，plan.md视为可能被手动编辑过 |
| 用户修改confirmed计划未重新确认 | Agent检测plan.md修改时间戳变化，提示用户需重新确认 |
| 会话工作目录被清理 | 计划彻底丢失，无恢复手段，符合会话生命周期设计预期 |

---

## 十二、与现有能力的关系

| 现有能力 | 在方案中的角色 |
|----------|---------------|
| Agent工作目录读写 | 不参与计划存储，仅供跨会话持久化配置使用 |
| Session工作目录读写 | 计划文件主存储区，plan.md + progress.json + outputs |
| 用户工作目录读写 | 计划的输入来源和最终产出交付位置 |

三者职责清晰，无耦合。
