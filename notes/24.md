## 1. 背景：HTTP 的「单向请求」局限

### 1.1 HTTP 的天然短板

HTTP 协议本质上是一个**请求-响应模型**——客户端发起请求，服务端返回响应，然后连接结束。服务端无法主动向客户端推送数据。

```
    标准 HTTP：
    Client ──── Request ────► Server
    Client ◄── Response ──── Server
    [连接关闭]

    服务端想主动推送 → 做不到
```

这对实时场景（股票行情、消息通知、AI 流式输出）是致命限制。

### 1.2 传统解决方案的不足

在 SSE 出现之前，几种方案的局限：

| 方案 | 原理 | 缺点 |
|------|------|------|
| **短轮询** | 客户端定时发 HTTP 请求查询 | 大量无效请求，延迟高，浪费带宽 |
| **长轮询** | 客户端请求后服务端挂起，有数据再返回 | 每次都要重建连接，连接管理复杂 |
| **WebSocket** | 升级 HTTP 为全双工 TCP 连接 | 协议复杂，不兼容 HTTP/2 多路复用，需要特殊代理支持 |
| **隐藏 iframe** | 服务端向 iframe 写入 script 标签 | hack 方案，不优雅 |

### 1.3 SSE 的解决方案

SSE 在**标准 HTTP 之上**实现服务端推送，无需升级协议、无需特殊基础设施：

```
    SSE：
    Client ──── GET /events (Accept: text/event-stream) ──► Server
    Client ◄── data: {...}\n\n ───────────────────────────── Server
    Client ◄── data: {...}\n\n ───────────────────────────── Server
    Client ◄── data: {...}\n\n ───────────────────────────── Server
    [连接保持打开，服务端随时推送]
```

> SSE 的本质：**一个永不结束的 HTTP 响应**。

## 2. 核心概念

### 2.1 什么是 SSE

**Server-Sent Events (SSE)** 是 HTML5 规范中的一部分，定义了一种服务端通过 HTTP 连接向客户端**单向**推送事件的标准方式。

| 特性 | 说明 |
|------|------|
| **通信方向** | 单向：服务端 → 客户端（客户端通过普通 HTTP 请求发送数据） |
| **传输协议** | HTTP/1.1 或 HTTP/2 |
| **数据格式** | 纯文本（`text/event-stream` MIME 类型） |
| **自动重连** | 浏览器内置 `EventSource` API 自动处理断线重连 |
| **连接开销** | 极低，就是一个长连接的 HTTP 响应流 |

### 2.2 与 WebSocket 的本质区别

| 维度 | SSE | WebSocket |
|------|-----|-----------|
| **协议层** | 标准 HTTP | 独立协议（`ws://` / `wss://`） |
| **通信方向** | 单向（服务端 → 客户端） | 全双工（双向） |
| **数据格式** | 纯文本（`text/event-stream`） | 文本或二进制 |
| **自动重连** | ✅ 浏览器内置 | ❌ 需手动实现 |
| **断线检测** | ✅ 内置心跳机制 | ❌ 需自行实现 ping/pong |
| **HTTP/2 兼容** | ✅ 天然兼容多路复用 | ❌ 与 HTTP/2 多路复用冲突 |
| **代理/防火墙** | ✅ 完全兼容 | ⚠️ 部分代理不支持升级请求 |
| **实现复杂度** | 极低 | 中等 |
| **适用场景** | 订阅推送、日志流、AI 流式输出 | 聊天、游戏、协同编辑 |

> **口诀**：需要服务端推数据选 SSE，需要双向高频通信选 WebSocket。大部分 AI Agent 场景（流式输出、状态推送）SSE 完全够用。

## 3. 协议细节

### 3.1 HTTP 请求头

客户端发起 SSE 连接时，发送标准 HTTP GET 请求，带特定请求头：

```http
GET /events HTTP/1.1
Host: example.com
Accept: text/event-stream
Cache-Control: no-cache
```

| 请求头 | 必须 | 说明 |
|--------|------|------|
| `Accept: text/event-stream` | ✅ | 告诉服务端客户端需要 SSE 流 |
| `Cache-Control: no-cache` | 建议 | 禁用缓存代理 |

### 3.2 HTTP 响应头

服务端返回：

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
Transfer-Encoding: chunked    (HTTP/1.1)

data: {"message": "hello"}

```

| 响应头 | 必须 | 说明 |
|--------|------|------|
| `Content-Type: text/event-stream` | ✅ | 标识 SSE 流 |
| `Cache-Control: no-cache` | ✅ | 防止代理缓存事件流 |
| `Connection: keep-alive` | 建议 | 保持连接不关闭 |
| `Transfer-Encoding: chunked` | HTTP/1.1 默认 | 分块传输编码 |

### 3.3 事件流格式

SSE 的响应体是一种简单的文本格式，由多个**字段**组成，每条消息以两个换行符 `\n\n` 分隔：

```
field:value\n
field:value\n
\n
```

**完整字段定义**：

```
id: 42\n                        ← 事件 ID（用于断线重连的 Last-Event-ID）
event: customEventName\n        ← 事件类型（默认是 "message"）
data: {"key": "value"}\n        ← 数据内容（可多行）
retry: 3000\n                   ← 重连间隔（毫秒）
\n                              ← 消息结束标记
```

> ⚠️ **注意**：
> - `data:` 字段可以出现多次，实际值是多行拼接的结果
> - 每行结尾必须是 `\n`（LF），不能是 `\r\n`（CRLF）
> - 注释行以 `:` 开头，客户端忽略

### 3.4 五种字段详解

| 字段 | 出现次数 | 说明 | 示例 |
|------|---------|------|------|
| `data:` | 必须（否则消息为空） | 消息数据。可多行，多行时自动拼接 | `data: hello\n` |
| `event:` | 可选 | 自定义事件类型名 | `event: update\n` |
| `id:` | 可选 | 事件 ID。重连时通过 `Last-Event-ID` 头发送 | `id: 42\n` |
| `retry:` | 可选 | 重连等待时间（毫秒） | `retry: 3000\n` |
| `:` | 可选 | 注释行，客户端忽略 | `: heartbeat\n` |

### 3.5 实际示例

```
: 这是一个注释，客户端会忽略\n
\n
event: user_joined\n
data: {"username": "alice", "time": "2026-06-16T08:00:00Z"}\n
\n
event: message\n
id: 1001\n
data: {"from": "alice", "text": "Hello!"}\n
\n
id: 1002\n
data: {"from": "bob", "text": "Hi Alice!"}\n
\n
data: 没有 event 字段，默认触发 "message" 事件\n
\n
```

对应的客户端 JavaScript：

```javascript
const source = new EventSource('/events');

// 默认 "message" 事件
source.onmessage = (event) => {
  console.log('收到消息:', event.data);
  // event.lastEventId → "1002"
  // event.type → "message"
};

// "user_joined" 自定义事件
source.addEventListener('user_joined', (event) => {
  const data = JSON.parse(event.data);
  console.log(`${data.username} 加入了房间`);
});
```

## 4. 浏览器 API：EventSource

### 4.1 基本用法

```javascript
// 建立连接
const source = new EventSource('/events');

// 连接成功
source.onopen = () => {
  console.log('SSE 连接已建立');
};

// 接收消息（默认事件类型）
source.onmessage = (event) => {
  console.log('数据:', event.data);
  console.log('事件ID:', event.lastEventId);
};

// 错误处理
source.onerror = (event) => {
  if (source.readyState === EventSource.CLOSED) {
    console.log('连接已关闭');
  } else {
    console.log('连接错误，将自动重连...');
  }
};

// 监听自定义事件
source.addEventListener('customEvent', (event) => {
  const data = JSON.parse(event.data);
  // 处理自定义事件
});

// 手动关闭
source.close();
```

### 4.2 readyState 状态

| 状态 | 值 | 说明 |
|------|-----|------|
| `EventSource.CONNECTING` | 0 | 正在连接或重连中 |
| `EventSource.OPEN` | 1 | 连接已建立 |
| `EventSource.CLOSED` | 2 | 连接已关闭 |

### 4.3 自动重连机制

SSE 最优雅的特性之一：

```
Client                                          Server
  │                                               │
  │──── GET /events ─────────────────────────────►│
  │◄─── data: msg1 ───────                        │
  │◄─── data: msg2 ───────                        │
  │                    [连接意外断开]                │
  │                                               │
  │──── GET /events ─────────────────────────────►│  (自动重连)
  │    Last-Event-ID: 1002                        │  (带上最后收到的事件ID)
  │◄─── data: msg3 (从 msg2 之后开始)               │
```

- 浏览器自动执行重连，无需代码
- 通过 `Last-Event-ID` 头告知服务端断点位置
- 重连间隔由服务端的 `retry:` 字段控制，默认约 3 秒

## 5. 服务端实现

### 5.1 Python (FastAPI)

```python
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
import asyncio
import json

app = FastAPI()

@app.get("/events")
async def sse_endpoint(request: Request):
    async def event_stream():
        counter = 0
        while True:
            # 检查客户端是否断开
            if await request.is_disconnected():
                break

            counter += 1
            data = json.dumps({"count": counter, "time": str(asyncio.get_event_loop().time())})

            # SSE 格式输出
            yield f"id: {counter}\n"
            yield f"event: update\n"
            yield f"data: {data}\n\n"

            await asyncio.sleep(1)

    return StreamingResponse(
        event_stream(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",  # 禁用 nginx 缓冲
        }
    )
```

### 5.2 Python (Flask)

```python
from flask import Flask, Response
import time
import json

app = Flask(__name__)

@app.route('/events')
def sse_endpoint():
    def event_stream():
        counter = 0
        while True:
            counter += 1
            data = json.dumps({"count": counter})
            yield f"data: {data}\n\n"
            time.sleep(1)

    return Response(
        event_stream(),
        mimetype="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",
        }
    )
```

### 5.3 Node.js (Express)

```javascript
const express = require('express');
const app = express();

app.get('/events', (req, res) => {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive',
    'X-Accel-Buffering': 'no',
  });

  let counter = 0;
  const interval = setInterval(() => {
    counter++;
    const data = JSON.stringify({ count: counter, time: Date.now() });
    res.write(`id: ${counter}\n`);
    res.write(`data: ${data}\n\n`);
  }, 1000);

  // 客户端断开时清理
  req.on('close', () => {
    clearInterval(interval);
    res.end();
  });
});

app.listen(3000);
```

### 5.4 Go

```go
func sseHandler(w http.ResponseWriter, r *http.Request) {
    flusher, ok := w.(http.Flusher)
    if !ok {
        http.Error(w, "Streaming not supported", http.StatusInternalServerError)
        return
    }

    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")

    counter := 0
    for {
        counter++
        data := fmt.Sprintf(`{"count": %d, "time": "%s"}`, counter, time.Now().Format(time.RFC3339))
        fmt.Fprintf(w, "id: %d\n", counter)
        fmt.Fprintf(w, "data: %s\n\n", data)
        flusher.Flush()

        time.Sleep(1 * time.Second)
    }
}
```

## 6. AI/Agent 场景中的 SSE

### 6.1 LLM 流式输出

SSE 是实现 LLM 流式输出的最常见方式：

```
用户: "写一首诗"                  
      │                                        
      ▼                                        
Client ── POST /chat ─────────────► AI Server  
Client ◄── data: {"delta":"春"} ─── AI Server  
Client ◄── data: {"delta":"眠"} ─── AI Server  
Client ◄── data: {"delta":"不"} ─── AI Server  
Client ◄── data: {"delta":"觉"} ─── AI Server  
      ...                                      
Client ◄── data: [DONE] ──────────── AI Server  
```

**OpenAI 兼容的 SSE 流式格式**：

```
data: {"id":"chatcmpl-xxx","object":"chat.completion.chunk","choices":[{"delta":{"content":"春"}}]}

data: {"id":"chatcmpl-xxx","object":"chat.completion.chunk","choices":[{"delta":{"content":"眠"}}]}

data: [DONE]

```

### 6.2 MCP 中的 SSE 传输

MCP 使用 SSE 作为**远程传输方式**之一（另一种是 stdio）：

```
┌──────────────┐                           ┌──────────────┐
│ MCP Client   │                           │ MCP Server   │
│ (AI 应用)     │                           │ (远程)        │
│              │                           │              │
│              │── GET /sse ──────────────►│ 建立 SSE 通道  │
│              │  Accept: text/event-stream│ (Server→Client)│
│              │                           │              │
│              │── POST /message ─────────►│ 发送请求       │
│              │  {jsonrpc: "2.0", ...}    │ (Client→Server)│
│              │                           │              │
│              │◄─ data: {jsonrpc: 2.0} ──│ 通过 SSE 响应   │
│              │                           │ (Server→Client)│
└──────────────┘                           └──────────────┘
```

**MCP SSE 的关键设计**：
- SSE 通道用于 **Server → Client** 的消息（响应、通知）
- 独立的 HTTP POST 端点用于 **Client → Server** 的请求
- 每条 SSE 消息承载一个完整的 JSON-RPC 消息

### 6.3 Agent 状态推送

Agent 执行任务时，通过 SSE 向客户端推送实时状态：

```
event: agent_plan
data: {"steps": ["分析需求", "搜索代码", "生成修改", "运行测试"]}

event: agent_status
data: {"step": "搜索代码", "status": "in_progress", "progress": 25}

event: agent_message
data: {"role": "agent", "content": "正在搜索相关的函数定义..."}

event: tool_call
data: {"tool": "search_code", "args": {"pattern": "def handle"}}

event: agent_status
data: {"step": "搜索代码", "status": "completed", "progress": 50}

event: agent_status
data: {"step": "生成修改", "status": "in_progress", "progress": 50}
```

## 7. 生产环境注意事项

### 7.1 连接限制

HTTP/1.1 浏览器对同一域名的并发连接有限制（通常 6 个）。一个 SSE 连接占用一个，所以：

- **尽量使用 HTTP/2**：HTTP/2 支持多路复用，单连接可以承载多个 SSE 流
- **合并 SSE 端点**：一个 SSE 连接推送多种事件，而不是每种事件一个连接

### 7.2 代理和缓冲

```nginx
# Nginx 配置：关闭 SSE 响应的缓冲
location /events {
    proxy_pass http://backend;
    proxy_set_header Connection '';
    proxy_http_version 1.1;
    proxy_buffering off;          # 关键：关闭缓冲
    proxy_cache off;              # 关键：关闭缓存
    chunked_transfer_encoding on;
}
```

> `X-Accel-Buffering: no` 响应头告诉 Nginx 不要缓冲这个响应。

### 7.3 连接保活

```nginx
# 增加超时时间
proxy_read_timeout 86400s;    # 24 小时
proxy_send_timeout 86400s;
```

服务端可以定期发送注释作为心跳：

```
data: {"type": "heartbeat"}\n\n
```

### 7.4 断线恢复

服务端通过 `id:` 记录事件序列号，重连时：

```python
last_event_id = request.headers.get("Last-Event-ID")
if last_event_id:
    # 从 last_event_id + 1 开始重放事件
    start_from = int(last_event_id) + 1
else:
    start_from = 0
```

### 7.5 安全性

- 和普通 HTTP 一样使用 HTTPS（`https://`）
- 支持 Cookie 认证（同源）和 Token 认证（`Authorization` 头）
- 注意 CORS 配置（跨域 SSE 需要服务端配合）

## 8. SSE 与其他技术对比

### 8.1 完整决策矩阵

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 服务端推送（AI 流式输出、通知、日志） | **SSE** | 简单、兼容性好、自动重连 |
| 双向高频通信（聊天、游戏、协作） | **WebSocket** | 全双工、低延迟 |
| 简单状态查询（幂等、低频） | **短轮询** | 实现最简单 |
| 低频查询但要低延迟 | **长轮询** | HTTP-only 环境可用 |
| 实时视频/音频 | **WebRTC** | 专为此设计 |
| IoT 设备推送 | **MQTT** | 轻量级、适合弱网 |

### 8.2 常见误用

| 误用 | 应该用 |
|------|--------|
| 用 WebSocket 做单向推送（只是服务端推 AI 输出） | SSE 更简单、更兼容 |
| 用 SSE 做双向通信（客户端频繁发数据） | WebSocket 更高效 |
| 用短轮询模拟实时推送 | SSE 省带宽、低延迟 |

## 9. 总结

| 维度 | 要点 |
|------|------|
| **本质** | 基于 HTTP 的服务端单向推送技术 |
| **协议层** | 标准 HTTP/1.1 或 HTTP/2，无需升级 |
| **数据格式** | `text/event-stream`，纯文本，`data:` + `event:` + `id:` + `retry:` |
| **关键优势** | 自动重连、断点续传、HTTP/2 兼容、代理友好 |
| **实现复杂度** | 极低（比 WebSocket 简单得多） |
| **AI 场景** | LLM 流式输出（OpenAI 格式）、MCP 远程传输、Agent 状态推送 |
| **核心局限** | 单向——服务端推客户端，不能客户端频繁推服务端 |

> **一句话总结**：SSE 就是「永不关闭的 HTTP 响应」——用最简单的协议，解决最常见的服务端推送问题。
