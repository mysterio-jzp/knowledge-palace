## 1. 背景：LLM 的「信息孤岛」问题

### 1.1 问题描述

大语言模型（LLM）本身是一个封闭系统。它能回答问题，但知识截止于训练数据。当 AI 应用需要访问外部数据（数据库、API、文件系统、第三方服务）时，传统做法是每个应用各自实现一套集成代码。

这就产生了类似 LSP 诞生前的 M×N 问题：

```
数据源 M = 10（数据库、GitHub、Slack、文件系统...）
AI 应用 N = 5（Claude Desktop、Cursor、自定义 Agent...）
需要的集成数量 = 10 × 5 = 50 套
```

### 1.2 MCP 的解决方案

MCP 由 Anthropic 于 2024 年底推出，核心理念直接继承自 LSP：

> **用统一的协议，让任何 AI 应用（Host）都能通过标准接口连接任何数据源（Server），获取上下文信息。**

```
┌──────────────┐     MCP (JSON-RPC)      ┌──────────────┐
│               │ ◄────────────────────►  │               │
│  AI 应用       │                         │  MCP Server   │
│  (Host/Client) │                         │  (数据源)      │
│               │                         │               │
│  如：Claude    │                         │  如：GitHub    │
│  Desktop       │                         │  API、数据库    │
│  Cursor        │                         │  文件系统等     │
└──────────────┘                         └──────────────┘
```

效果：

```
数据源 M = 10，AI 应用 N = 5
需要的集成数量 = 10（MCP Server）+ 5（Host 适配） = 15 套
```

### 1.3 MCP 与 LSP 的关系

MCP 受 LSP 直接启发，但不是 LSP 的「变体」，而是同一理念在不同领域的应用：

| 维度 | LSP | MCP |
|------|-----|-----|
| 提出者 | 微软 (2016) | Anthropic (2024) |
| 解决的问题 | 编辑器 ↔ 语言服务的集成碎片化 | AI 应用 ↔ 数据源的集成碎片化 |
| Server 提供什么 | 代码智能（补全、诊断、跳转） | 上下文（资源、工具、提示模板） |
| Client（消费者） | 编辑器/IDE | AI 模型 / AI 应用 |
| 传输层 | stdio, TCP, Pipe | stdio, SSE (HTTP) |
| 消息格式 | JSON-RPC 2.0 | JSON-RPC 2.0 |
| 能力协商 | ✅ | ✅ |
| Server 推送 | ✅ 诊断推送 | ✅ 资源变更通知 |

> 可以说：**MCP 就是「LLM 时代的 LSP」**。

## 2. 核心架构

### 2.1 三角模型

MCP 架构包含三个角色，与 LSP 有所不同：

```
┌──────────────────────────────────────────────────────┐
│                    MCP Host                           │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ Claude   │  │ Cursor   │  │ 自建Agent │           │
│  │ Desktop  │  │          │  │          │           │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘           │
│       │             │             │                  │
│       │     ┌───────┴───────┐     │                  │
│       │     │               │     │                  │
│       └────►│  MCP Client   │◄────┘                  │
│             │  (协议层)       │                        │
│             └───────┬───────┘                        │
└─────────────────────┼────────────────────────────────┘
                      │ MCP (JSON-RPC 2.0)
          ┌───────────┼───────────┐
          │           │           │
    ┌─────┴─────┐ ┌───┴───┐ ┌───┴─────────┐
    │  MCP      │ │ MCP   │ │  MCP        │
    │  Server A │ │Server │ │  Server C    │
    │ (数据库)   │ │(文件)  │ │  (第三方API) │
    └───────────┘ └───────┘ └─────────────┘
```

### 2.2 角色定义

| 角色 | 说明 | 示例 |
|------|------|------|
| **MCP Host** | 实际的 AI 应用，集成 LLM 并与用户交互 | Claude Desktop、Cursor、自建聊天应用 |
| **MCP Client** | 协议客户端层，与 MCP Server 建立一对一连接。一个 Host 可以有多个 Client，每个 Client 连接一个 Server | Host 内部使用的库（如 `mcp` Python SDK） |
| **MCP Server** | 轻量级服务，通过 MCP 暴露特定能力 | GitHub Server、Postgres Server、Filesystem Server |

> **关键区别**：LSP 中 Client 是编辑器插件、Server 是语言服务器。MCP 中 Client 被嵌入在 Host 内部，Server 是数据/工具提供方。两者概念恰好「错位」了。

## 3. 核心原语（Primitives）

MCP Server 通过三种核心原语向 AI 模型暴露能力：

```
┌─────────────────────────────────────────────────────┐
│                  MCP Server                          │
│                                                     │
│  ┌───────────┐  ┌───────────┐  ┌───────────────┐   │
│  │ Resources │  │   Tools   │  │   Prompts     │   │
│  │  (资源)    │  │  (工具)    │  │   (提示模板)   │   │
│  └─────┬─────┘  └─────┬─────┘  └──────┬────────┘   │
│        │              │               │             │
│        ▼              ▼               ▼             │
│  ┌─────────────────────────────────────────────┐   │
│  │         MCP Client → AI 模型                  │   │
│  └─────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘
```

### 3.1 Resources（资源）

Resources 是 **只读** 的数据，类似 REST API 中的 GET 端点。AI 模型可以读取但不能修改。

**两种类型**：

| 类型 | 说明 | 示例 |
|------|------|------|
| **TextResourceContents** | 文本内容（UTF-8 字符串） | 数据库查询结果、API 返回值、文件内容 |
| **BlobResourceContents** | 二进制内容（Base64 编码） | 图片、PDF、音频文件 |

**资源寻址**：每个 Resource 有一个唯一的 URI：

```
file:///home/user/project/README.md    # 文件系统中的文件
postgres://database/users/table        # 数据库中的表
github://owner/repo/issues/42          # GitHub Issue
```

**资源模板**：支持参数化的 URI 模板，用于动态资源：

```
github://owner/repo/issues/{issue_number}   # 动态 GitHub Issue
file:///project/src/{module}/__init__.py   # 动态文件路径
```

**资源能力**：
- `resources/list` — 列出所有可用资源
- `resources/read` — 读取指定资源
- `resources/subscribe` — 订阅资源变更通知
- `notifications/resources/updated` — 资源变更时 Server 推送通知

### 3.2 Tools（工具）

Tools 是 **可执行的操作**，允许 AI 模型**修改状态或产生副作用**。这是 MCP 区别于纯数据协议的关键能力。

| 特性 | 说明 |
|------|------|
| **模型可见** | Tool 的 name、description、inputSchema 直接暴露给 LLM 作为 function calling 的候选 |
| **用户确认** | 执行前 Host 可以向用户请求确认（安全机制） |
| **有副作用** | 可以创建文件、发送消息、修改数据库等 |

**Tool 定义示例**：

```json
{
  "name": "create_issue",
  "description": "在 GitHub 仓库中创建一个 Issue",
  "inputSchema": {
    "type": "object",
    "properties": {
      "owner": { "type": "string", "description": "仓库所有者" },
      "repo": { "type": "string", "description": "仓库名" },
      "title": { "type": "string", "description": "Issue 标题" },
      "body": { "type": "string", "description": "Issue 描述（Markdown）" }
    },
    "required": ["owner", "repo", "title"]
  }
}
```

**工具相关的方法**：
- `tools/list` — 列出所有可用工具及其 inputSchema
- `tools/call` — 调用指定工具，传入参数，获取执行结果

**Tool 的执行流**：

```
用户提问 "帮我给项目创建一个 Issue"
        │
        ▼
Host 将 Tool 列表（含 inputSchema）发送给 LLM
        │
        ▼
LLM 决定调用 create_issue(owner="foo", repo="bar", title="...")
        │
        ▼
Host 通过 MCP Client 调用 Server: tools/call
        │
        ▼
MCP Server 执行创建，返回结果 { "issue_url": "https://..." }
        │
        ▼
Host 将结果返回 LLM，LLM 向用户汇报
```

### 3.3 Prompts（提示模板）

Prompts 是**可复用的提示词模板**，由 Server 预定义，支持参数化。

**用途**：
- 标准化常见交互的提示词格式
- 让 AI 以特定角色或风格回复
- 提供上下文增强模板（如「分析这个代码库」+ 注入文件列表）

**Prompt 定义示例**：

```json
{
  "name": "code_review",
  "description": "对指定文件进行代码审查",
  "arguments": [
    {
      "name": "file_path",
      "description": "要审查的文件路径",
      "required": true
    },
    {
      "name": "language",
      "description": "编程语言",
      "required": false
    }
  ]
}
```

当用户选择这个 Prompt 时，Server 返回具体的提示词内容（可能是多轮消息），然后由 LLM 处理。

**提示相关方法**：
- `prompts/list` — 列出所有可用提示模板
- `prompts/get` — 获取指定提示的详细信息

## 4. 协议细节

### 4.1 传输层（Transport）

MCP 支持两种传输方式：

| 传输方式 | 适用场景 | 特点 |
|---------|---------|------|
| **stdio** | 本地进程通信 | 简单可靠，Server 作为子进程启动 |
| **SSE (Server-Sent Events)** | 远程通信 | 基于 HTTP，支持认证，Server 独立部署 |

**stdio 模式**：

```bash
# 启动 MCP Server（以 filesystem server 为例）
npx -y @modelcontextprotocol/server-filesystem /path/to/allowed/dir
```

Host 启动 Server 子进程，通过 stdin 发送 JSON-RPC 请求，stdout 接收响应。

**SSE 模式**：

```
POST /sse HTTP/1.1              ← Client 建立 SSE 连接（接收 Server → Client 消息）
Host: mcp-server.example.com

POST /messages HTTP/1.1         ← Client 发送 Client → Server 消息
Content-Type: application/json

{"jsonrpc":"2.0","method":"tools/call",...}
```

SSE 模式需要先建立事件流通道，再通过独立的 HTTP endpoint 发送消息。适合 Server 独立部署的远程场景。

### 4.2 消息格式

与 LSP 完全相同，使用 JSON-RPC 2.0。支持四种消息类型：

```json
// Request
{ "jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": { ... } }

// Response
{ "jsonrpc": "2.0", "id": 1, "result": { ... } }

// Notification
{ "jsonrpc": "2.0", "method": "notifications/resources/updated", "params": { ... } }

// Error
{ "jsonrpc": "2.0", "id": 1, "error": { "code": -32000, "message": "..." } }
```

### 4.3 生命周期

与 LSP 几乎一致：

```
初始化 → 运行 → 关闭
```

1. **初始化阶段**：

```
Client ──── initialize ──────────► Server  (能力声明)
Client ◄──── InitializeResult ──── Server  (服务端能力 + 协议版本)
Client ──── initialized (notif) ──► Server  (握手完成)
```

2. **运行阶段**：正常的资源读取、工具调用、提示获取
3. **关闭阶段**：`shutdown` 请求 + `exit` 通知

### 4.4 能力协商（Capability Negotiation）

MCP 的 `initialize` 阶段与 LSP 一样，双方声明能力。

**ServerCapabilities**：

```json
{
  "resources": {
    "subscribe": true,        // 支持资源变更订阅
    "listChanged": true       // 支持资源列表变更通知
  },
  "tools": {
    "listChanged": true       // 支持工具列表变更通知
  },
  "prompts": {
    "listChanged": true       // 支持提示列表变更通知
  }
}
```

**ClientCapabilities**：

```json
{
  "roots": {
    "listChanged": true       // 支持根目录列表变更
  },
  "sampling": {}              // 支持 LLM 采样（让 Server 请求 Client 调用 LLM）
}
```

## 5. 高级特性

### 5.1 Sampling（反向 LLM 调用）

这是一个强大但容易被忽略的特性：**MCP Server 可以请求 MCP Client 帮它调用 LLM**。

```
                    通常方向
  MCP Client ──────────────────────► MCP Server
            (发送请求)

                    Sampling 方向
  MCP Client ◄────────────────────── MCP Server
            (Server 请求 Client 调用 LLM)
```

**使用场景**：
- Server 需要「智能处理」：如 Server 获取了大量数据，需要 LLM 来总结
- Server 作为 Agent 的中间层：先获取数据，让 LLM 分析，再决定下一步

**方法**：`sampling/createMessage`

### 5.2 Roots（根目录）

Server 可以请求 Host 提供「项目根目录」信息，了解哪些文件对用户重要。

```
Server  ──── roots/list ────────► Client
Client  ◄─── [{uri: "file:///project"}, ...] ──── Server
```

### 5.3 通知（Notifications）

Server 可以主动推送通知：

| 通知 | 说明 |
|------|------|
| `notifications/resources/updated` | 资源内容变更 |
| `notifications/resources/list_changed` | 资源列表变更 |
| `notifications/tools/list_changed` | 工具列表变更 |
| `notifications/prompts/list_changed` | 提示列表变更 |

这让 Server 可以动态地变化可用的资源和工具，无需重启。

### 5.4 Progress（进度报告）

长时间操作（如大文件读取）可以通过 `notifications/progress` 推送进度：

```json
{
  "method": "notifications/progress",
  "params": {
    "progressToken": "abc123",
    "progress": 50,
    "total": 100
  }
}
```

## 6. MCP 与 Tool Calling / Function Calling 的关系

这是最容易混淆的概念，需要清晰区分：

| 维度 | MCP | OpenAI Function Calling |
|------|-----|------------------------|
| **层级** | 协议层（传输 + 发现 + 执行） | API 层（LLM 输出格式） |
| **谁定义工具** | MCP Server（动态发现） | 开发者手动定义 |
| **工具发现** | `tools/list` 动态获取 | 每次请求手动传入 tools 参数 |
| **工具执行** | MCP Client → MCP Server 链路 | 开发者自己实现函数调用逻辑 |
| **通用性** | 跨模型、跨平台 | 仅限支持该格式的模型 |
| **认证/安全** | 协议内建支持（OAuth 等） | 开发者自建 |

**两者是互补关系**，不是取代：

```
┌──────────────────────────────────────────────────┐
│                 AI 应用 (Host)                     │
│                                                   │
│   ① MCP Client 从 Server 获取 Tool 列表            │
│   ② 将 Tool 转为 LLM 能理解的 function calling 格式 │
│   ③ LLM 返回 function call                        │
│   ④ MCP Client 通过 tools/call 执行                │
└──────────────────────────────────────────────────┘
```

也就是说，**MCP 负责工具的发现和执行，Function Calling 负责让 LLM 选择和调用工具**。

## 7. MCP SDK

### 7.1 Python SDK

官方提供 `mcp` Python 包：

```bash
pip install mcp
```

**创建 MCP Server**：

```python
from mcp.server import Server, NotificationOptions
from mcp.server.models import InitializationCapabilities
from mcp.server.stdio import stdio_server
import mcp.types as types

# 创建 Server 实例
server = Server("my-server")

@server.list_tools()
async def handle_list_tools() -> list[types.Tool]:
    return [
        types.Tool(
            name="get_weather",
            description="获取指定城市的天气",
            inputSchema={
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名"}
                },
                "required": ["city"]
            }
        )
    ]

@server.call_tool()
async def handle_call_tool(
    name: str, arguments: dict
) -> list[types.TextContent | types.ImageContent | types.EmbeddedResource]:
    if name == "get_weather":
        city = arguments["city"]
        # 调用真正的天气 API
        weather = f"{city} 今天晴天，25°C"
        return [types.TextContent(type="text", text=weather)]
    raise ValueError(f"Unknown tool: {name}")

async def main():
    async with stdio_server() as (read_stream, write_stream):
        await server.run(
            read_stream,
            write_stream,
            InitializationCapabilities(
                sampling={},  # 不需要 sampling
            ),
        )

if __name__ == "__main__":
    import asyncio
    asyncio.run(main())
```

**关键装饰器**：
| 装饰器 | 用途 |
|--------|------|
| `@server.list_resources()` | 列出资源 |
| `@server.read_resource()` | 读取资源 |
| `@server.list_tools()` | 列出工具 |
| `@server.call_tool()` | 执行工具 |
| `@server.list_prompts()` | 列出提示 |
| `@server.get_prompt()` | 获取提示详情 |

### 7.2 TypeScript SDK

```bash
npm install @modelcontextprotocol/sdk
```

```typescript
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";

const server = new Server(
  { name: "my-server", version: "1.0.0" },
  { capabilities: { tools: {} } }
);

server.setRequestHandler("tools/list", async () => ({
  tools: [{
    name: "get_weather",
    description: "获取指定城市的天气",
    inputSchema: {
      type: "object",
      properties: {
        city: { type: "string", description: "城市名" }
      },
      required: ["city"]
    }
  }]
}));

const transport = new StdioServerTransport();
await server.connect(transport);
```

## 9. Claude Desktop 中的 MCP 配置示例

Claude Desktop 是 MCP 最广泛使用的 Host 应用。配置方式：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "/Users/me/Documents",
        "/Users/me/Projects"
      ]
    },
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_xxxxxxxxxxxx"
      }
    },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres"],
      "env": {
        "DATABASE_URL": "postgresql://user:pass@localhost:5432/mydb"
      }
    }
  }
}
```

配置后，Claude Desktop 启动时会自动拉起这些 MCP Server，AI 就能直接读取文件、操作 GitHub、查询数据库。

## 10. MCP 与 AI Agent 工程

### 10.1 MCP 作为 Agent 的工具基础设施

对于 AI Agent 工程，MCP 的重要价值在于：

- **标准化工具接口**：所有 Agent 用同样的方式连接工具和数据源，不必为每个 Agent 重新集成
- **动态工具发现**：Agent 启动时通过 `tools/list` 获取可用工具，无需硬编码
- **安全隔离**：工具运行在独立的 Server 进程中，权限可精细控制
- **跨平台复用**：一个 MCP Server 可以连接 Claude Desktop、Cursor、自建 Agent 等多个 Host

### 10.2 典型的 Agent + MCP 架构

```
┌──────────────────────────────────────┐
│         Agent Host                   │
│  ┌────────────────────────────┐     │
│  │      Agent Runtime          │     │
│  │  • 任务规划                 │     │
│  │  • LLM 推理                 │     │
```

## 11. MCP 的局限性与挑战

| 挑战 | 说明 |
|------|------|
| **版本早期** | MCP 规范仍在快速迭代中，API 可能 breaking change |
| **SSE 传输限制** | SSE 模式在复杂网络环境下稳定性不如 stdio |
| **认证体系** | 虽然规范中有 OAuth 支持，但实现还不够完整 |
| **工具冲突** | 多个 Server 暴露同名工具时缺少命名空间机制 |
| **可观测性** | 缺少标准的日志和监控接口 |
| **安全审计** | 工具调用链的可追溯性有待加强 |
| **LLM 适配** | 不同 LLM 对 function calling 格式的支持差异需要 Host 适配 |

## 12. 与 LSP 的完整对比

| 维度 | LSP | MCP |
|------|-----|-----|
| **发布时间** | 2016 年 | 2024 年 |
| **提出者** | 微软 | Anthropic |
| **服务对象** | 人类开发者（通过编辑器） | AI 模型（通过 AI 应用） |
| **Server 提供** | 代码智能（补全、诊断、跳转） | 上下文 + 工具（资源、工具、提示） |
| **数据方向** | 主要是 Server → Client | 双向：数据读取 + 工具执行 |
| **副作用** | 极少（格式化是唯一边界操作） | 工具执行可以产生任意副作用 |
| **传输方式** | stdio, TCP, Pipe | stdio, SSE (HTTP) |
| **能力协商** | ✅ | ✅ |
| **动态发现** | 静态（初始化时确定） | 动态（Resource/Tool 可以运行时变更） |
| **安全机制** | 无需（本地进程） | 需要（用户确认、权限控制） |
| **协议规范稳定性** | 非常稳定（3.17 是当前主要版本） | 快速迭代中 |
| **生态成熟度** | 极其成熟，几乎覆盖所有语言 | 快速增长中 |

### 13.3 自己写一个 Python MCP Server 的完整示例

```python
# weather_server.py
import asyncio
import json
import httpx
from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.server.models import InitializationCapabilities
import mcp.types as types

server = Server("weather-server")

@server.list_tools()
async def list_tools() -> list[types.Tool]:
    return [
        types.Tool(
            name="get_current_weather",
            description="获取指定城市的当前天气信息",
            inputSchema={
                "type": "object",
                "properties": {
                    "city": {
                        "type": "string",
                        "description": "城市名称，如 'Beijing'、'Shanghai'"
                    }
                },
                "required": ["city"]
            }
        )
    ]

@server.call_tool()
async def call_tool(name: str, arguments: dict) -> list[types.TextContent]:
    if name == "get_current_weather":
        city = arguments["city"]
        # 这里可以调用真实的天气 API
        # async with httpx.AsyncClient() as client:
        #     resp = await client.get(f"https://api.weather.com/...")
        weather_info = f"{city} 当前天气：晴，温度 22°C，湿度 45%"
        return [types.TextContent(type="text", text=weather_info)]
    raise ValueError(f"Unknown tool: {name}")

async def main():
    async with stdio_server() as (read, write):
        await server.run(
            read, write,
            InitializationCapabilities(sampling={})
        )

if __name__ == "__main__":
    asyncio.run(main())
```

运行：`python weather_server.py`（配合 Claude Desktop 或其他 MCP Host 使用）

## 14. 总结

| 维度 | 要点 |
|------|------|
| **解决什么问题** | AI 应用与数据源的集成碎片化（M×N 问题） |
