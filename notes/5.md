## 1. 方案目标
- 在容器内提供“用户级隔离执行环境”（nsjail），用于安全运行命令/脚本。
- 通过 ossfs 将对象存储挂载为本地目录，供任务读写文件。
- 实现“系统代码与用户数据分离”：
  - 系统脚本只读
  - 用户工作区可写
- 支持多用户动态隔离（按 `username` 划分目录）。
---
## 2. 总体架构
- 宿主机 / 容器内目录约定：
  - 用户数据根：`/srv/sandboxes/<username>`
  - jail 内挂载：`/workspace`（映射到该用户目录）
  - 系统脚本目录：`/opt/opencode/runtime`（只读挂载）
  - OSS 挂载点：例如 `/app/ossfs2-bucket`（容器启动后执行 mount）
- 执行链路：
  1. 上层 Python 解释器接收任务（含 `username`）
  2. 根据 `username` 生成隔离策略
  3. 通过 nsjail 执行目标命令（统一入口）
  4. 任务读写 `\/workspace`，共享或读取 ossfs 挂载内容
---
## 3. nsjail 设计要点
### 3.1 安全边界
- 必须通过 nsjail 启动进程，不允许直接本机执行。
- 仅挂载必要目录：
  - `/workspace`（用户可写）
  - 系统依赖目录 `/usr` `/bin` `/lib*`（只读）
  - 系统 worker 目录 `/opt/opencode/runtime`（只读）
- 可选隔离：
  - `clone_newns/newpid/newipc/newuts/newnet/newuser`
  - 深入理解这些 namespace 的含义 → [[nsjail 技术详解：Linux Namespace 与进程隔离原理]]
### 3.2 多用户隔离
- 输入 `username` 后动态映射：
  - host: `/srv/sandboxes/<username>`
  - jail: `/workspace`
- `username` 严格校验（建议正则白名单）
- `realpath` 校验防越界和符号链接绕过
### 3.3 资源限制
- `time_limit`
- `rlimit_as`（内存）
- `rlimit_nproc`（进程数）
- `rlimit_fsize`（文件大小）
- 超时回收：`TERM -> KILL`（进程组）
### 3.4 常见问题
- `clone(...) failed: Operation not permitted`
  - 说明容器权限不足（需 `--privileged` 或 `cap_add` + seccomp 配置）
- `execve('rg') failed: No such file or directory`
  - jail 内路径/挂载/PATH 不完整，建议用绝对路径执行可执行文件
---
## 4. ossfs 设计要点
### 4.1 配置文件
- 建议通过 `COPY` 放入镜像：
  - `/etc/ossfs2.conf`
- 权限建议：
  - `root:root` + `chmod 600`
### 4.2 挂载时机
- 不建议在 Dockerfile `RUN` 阶段挂载（构建期无效）
- 应在容器运行时执行：
  - `ENTRYPOINT/CMD` 或 `docker exec` 触发 `ossfs2 mount ...`
### 4.3 权限与运行参数
- FUSE 挂载通常需要较高权限：
  - 调试可用 `--privileged`
  - 生产建议最小权限化（`cap_add` + `/dev/fuse` + 安全选项）
- 挂载后可用 `df -h` / `mount` 校验
---
## 5. Docker / Compose 建议
- `WORKDIR` 统一（如 `/app`），避免路径拼接混乱
- Compose 中 `entrypoint` 使用 shell 才能串联 `&&`
- `services.<name>.entrypoint` 必须位于服务节点下（避免 YAML 结构错误）
- 不要把全局代理写死在镜像；按命令注入更可控
---
## 6. Python 解释器层建议（与 nsjail 配合）
- 统一入口：`run(username, cmd, ...)`
- 禁止 `shell=True`
- 禁止 `sh -c` / `bash -c` 这类二次注入路径
- 所有文件操作通过 jail 内路径执行
- 对工具结果做大小限制与分页策略（避免上下文爆炸）
---
## 7. 文件工具策略（实践总结）
- `read`：
  - 文本：`offset/limit` + token/size 限制 + `readFileState` 去重（`file_unchanged`）
  - 图片：超 token 自动压缩（严格模式可压缩后仍超限则报错）
  - PDF：建议“文本提取优先”；提取不到文本报错
- `edit/write`：
  - 要求先读再改（mtime 防并发覆盖）
  - 仅 regular file
  - 路径必须在 `/workspace` 内
---
## 8. 风险与缓解
- 风险：仅 Python 层路径校验可被绕过
  - 缓解：nsjail 硬隔离 + 最小挂载 + 只读系统目录
- 风险：容器权限过大（`--privileged`）
  - 缓解：先跑通再收敛权限（capabilities、seccomp、apparmor）
- 风险：OSS 凭据泄露
  - 缓解：配置文件最小权限，优先 secret 注入
- 风险：大结果回灌上下文
  - 缓解：持久化 + 摘要/分块检索 + 证据引用机制
---
## 9. 建议落地顺序
1. 跑通最小链路：容器 -> ossfs 挂载 -> nsjail 执行 `echo/ls`
2. 固化目录约定与用户映射规则
3. 接入统一 Python 执行器（所有命令必须过 nsjail）
4. 实装 read/edit/write 工具限制与回收机制
5. 增加监控与清理策略（缓存、日志、磁盘占用）
6. 收敛权限到生产可接受基线
---
## 10. 当前结论
- `nsjail + ossfs` 方案可行，且能同时满足：
  - 安全隔离执行
  - 面向对象存储的数据访问
  - 多用户动态隔离
- 关键成功条件是：
  - 路径映射正确
  - 容器权限与 namespace 能力匹配
  - 系统代码与用户数据严格分层
  - 工具输出与资源有上限控制

## 11. 架构特点补充（nsjail + ossfs）
### 11.1 nsjail 架构特点
- **定位**：进程级沙箱执行器（非完整容器平台），强调“受限执行”而非应用编排。
- **核心机制**：
  - Linux namespaces（pid/net/mount/ipc/uts/user） — 详见 [[nsjail 技术详解：Linux Namespace 与进程隔离原理]]
  - rlimit/cgroup（资源约束）
  - seccomp-bpf（syscall 过滤） — 详见 [[seccomp-bpf 技术详解：系统调用过滤原理与实践]]
  - chroot/mount bind（文件系统视图裁剪）
- **安全模型**：默认“白名单式最小暴露”更易达成（只挂必要目录）。
- **运行模式**：适合“短生命周期命令执行”，可作为解释器后端统一调用。
### 11.2 ossfs 架构特点
- **定位**：通过 FUSE 把对象存储映射成 POSIX 风格目录。
- **本质**：对象存储语义（最终一致、对象接口）被“近似”成文件系统语义。
- **优势**：
  - 业务代码可复用文件 API（open/read/write/list）
  - 降低改造成本
- **限制**：
  - 对随机写、rename、锁语义、低延迟 IO 不友好
  - 小文件高并发场景性能波动明显
  - 强依赖网络质量与后端对象存储响应
### 11.3 组合架构价值（为什么是 nsjail + ossfs）
- `nsjail` 解决“**执行安全边界**”
- `ossfs` 解决“**数据接入与共享存储**”
- 二者组合适合“多租户任务执行 + 统一对象存储数据面”的平台型场景。

## 12. 横向对比（沙箱工具）
> 说明：以下为工程实践常见对比，数据为区间级经验值（用于选型方向，不作为基准测试结论）。
### 12.1 候选工具一览
- **nsjail**
- **bubblewrap (bwrap)**
- **gVisor**
- **Kata Containers**
- **Firecracker（通常配 microVM 平台）**
- **Docker/LXC（配 seccomp/apparmor/rootless）**
- **chroot + namespaces 手工方案**
### 12.2 对比表
| 方案 | 隔离强度 | 性能开销 | 复杂度 | 典型场景 | 备注 |
|---|---|---:|---:|---|---|
| nsjail | 高（进程级） | 低~中 | 中 | 不可信命令执行、在线任务沙箱 | 安全/性能平衡好 |
| bwrap | 中~高 | 低 | 低~中 | 桌面/CLI 沙箱、文件视图隔离 | 轻量，功能更聚焦 |
| gVisor | 高 | 中 | 中~高 | K8s 多租户、容器隔离增强 | syscall 拦截更强 |
| Kata | 很高（VM级） | 中~高 | 高 | 强隔离多租户 | 安全边界更硬，资源更重 |
| Firecracker | 很高（microVM） | 中 | 高 | Serverless/短任务隔离 | 启动快但平台化成本高 |
| Docker+安全配置 | 中 | 低 | 低 | 常规服务容器化 | 默认隔离不等于强沙箱 |
| 手工 chroot/ns | 中 | 低 | 高（维护） | 定制化极强环境 | 容易踩安全细节坑 |
### 12.3 nsjail 相对优劣
**优点**
- 安全能力完整：namespace + rlimit + seccomp + chroot/bind mount。
- 性能损耗相对可控，适合高频短任务。
- 比 microVM 类方案更轻量，落地速度快。
- 可精确控制“可见目录”和“可执行能力”。
**缺点**
- Linux 依赖强（跨平台不友好）。
- 在容器内嵌套使用时，权限/内核策略容易踩坑（你已遇到 clone 权限问题）。
- 策略配置复杂度高于简单容器命令。
- 若规则设计不当，仍可能出现“可用但不安全”假象。
---
## 13. ossfs 横向对比（对象存储挂载方案）
| 方案 | 语义兼容 | 性能表现 | 易用性 | 典型问题 |
|---|---|---|---|---|
| ossfs | 中 | 中（网络敏感） | 高 | 小文件/随机写性能、FUSE权限 |
| s3fs 类 | 中 | 中 | 高 | 一致性与元数据开销 |
| goofys | 中（偏读优化） | 中~高 | 中 | POSIX 语义不完全 |
| rclone mount | 中 | 中 | 中 | 长时稳定性调优要求高 |
| 直连 SDK（不挂载） | 低（需改代码） | 高 | 低 | 改造成本高，但语义清晰 |
**结论**：
- 如果目标是“低改造快速上线”：`ossfs` 合理。
- 如果目标是“高性能+强一致语义”：优先考虑 **直连 SDK/网关层抽象**，而非 FUSE 挂载。
---
## 14. 选型建议（针对你当前场景）
- 当前以“安全执行 + 快速落地”为第一目标：继续 `nsjail + ossfs` 是合理路径。
- 中期优化方向：
  1. 执行面：把 `--privileged` 收敛到最小权限（capabilities + seccomp 配置）。
  2. 数据面：识别热路径，逐步从 ossfs 迁移为 SDK 直连（至少写路径先迁移）。
  3. 观测面：增加任务级指标（成功率、超时率、平均执行时长、挂载失败率）。
