## 1. 背景：HTTP+SSE 的时代局限

### 1.1 MCP 初代远程传输

在 MCP 协议 2024-11-05 版本中，远程通信使用 **HTTP + SSE** 方案：

```
┌──────────────┐                    ┌──────────────┐
│ MCP Client   │                    │ MCP Server   │
│              │                    │              │
│              │── GET /sse ───────►│ ① 建立 SSE 通道
│              │  Accept: text/...  │   (Server→Client)
│              │                    │              │
│              │── POST /messages ─►│ ② 发送请求
│              │  body: JSON-RPC    │   (Client→Server)
│              │                    │              │
│              │◄─ SSE: data ──────│ ③ 服务端响应
│              │                    │   (通过 SSE 通道)
└──────────────┘                    └──────────────┘
```

这个设计有**三个致命缺陷**：

| 缺陷 | 后果 |
|------|------|
| **连接不可恢复** | SSE 断开后无法续传，上下文全部丢失 |
| **强制长连接** | 服务器必须维持高可用长连接，资源压力大 |
| **双端点耦合** | `/sse` 和 `/messages` 两个端点耦合，架构复杂 |

### 1.2 Streamable HTTP 的诞生

2025 年 3 月 26 日，MCP 协议发布关键更新：**用 Streamable HTTP 替代 HTTP+SSE 作为远程传输方式**。

> Streamable HTTP 并非全新发明的协议，而是对 HTTP 的**巧妙运用**——用单个端点，按需在「普通 JSON 响应」和「SSE 流式响应」之间灵活切换。

## 2. 核心设计

### 2.1 单一端点 + 按需流式

```
旧方案：HTTP+SSE                      新方案：Streamable HTTP
─────────────────                    ────────────────────────
/sse          (GET, 接收推送)        /mcp  (POST/GET 统一端点)
/messages     (POST, 发送消息)             │
      两个端点                               │ 按需选择：
                                            ├─ 简单请求 → JSON 响应
                                            └─ 复杂请求 → SSE 流式响应
```

**核心理念**：不是「总是流式」，而是「需要时才流式」。服务器根据请求复杂度自主决定响应方式。

### 2.2 三种服务器模式

Streamable HTTP 支持三种服务器部署模式，灵活度远超前代：

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **无状态服务器** | 每次请求独立，不维持任何状态 | 简单工具服务（如天气查询、计算器） |
| **支持流式输出的无状态服务器** | 无状态，但复杂请求可升级为 SSE 流 | 需要进度反馈的工具（如长时间计算） |
| **有状态服务器** | 维持会话上下文，通过 Session ID 绑定 | 多轮对话、Agent 编排等复杂场景 |

## 3. 协议细节

### 3.1 端点设计

| 规则 | 说明 |
|------|------|
| **端点数量** | 单一 HTTP 端点（称为 **MCP 端点**），如 `https://example.com/mcp` |
| **支持方法** | POST（客户端→服务端）和 GET（服务端→客户端） |
| **安全要求** | 必须验证 `Origin` 头（防 DNS 重绑定攻击）|
| **本地绑定** | 本地运行时应仅绑定 `127.0.0.1` |
| **认证** | 应对所有连接实施适当认证 |

### 3.2 POST 请求（Client → Server）

客户端发送 JSON-RPC 消息到服务器：

```http
POST /mcp HTTP/1.1
Host: example.com
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2025-11-25
MCP-Session-Id: abc123def456

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": { ... }
}
```

**POST 请求头要求**：

| 头 | 必须 | 说明 |
|----|------|------|
| `Accept` | ✅ | 必须同时包含 `application/json` 和 `text/event-stream` |
| `Content-Type` | ✅ | `application/json` |
| `MCP-Protocol-Version` | ✅ | 协商后的协议版本 |
| `MCP-Session-Id` | 有状态时必须 | 服务器分配的会话 ID |

**服务器根据请求类型决定响应方式**：

```
输入的 JSON-RPC 消息类型：

  通知(Notification) 或 响应(Response)
  │
  └─► 返回 HTTP 202 Accepted（无响应体）

  请求(Request)
  │
  ├─► 简单请求 → Content-Type: application/json（单个 JSON 响应）
  │
  └─► 复杂请求 → Content-Type: text/event-stream（SSE 流式响应）
```

### 3.3 GET 请求（Server → Client 监听）

客户端可以通过 GET 请求建立从服务器接收消息的通道：

```http
GET /mcp HTTP/1.1
Host: example.com
Accept: text/event-stream
MCP-Protocol-Version: 2025-11-25
MCP-Session-Id: abc123def456
```

服务器响应 `Content-Type: text/event-stream`，通过 SSE 主动向客户端推送：
- JSON-RPC **请求**（服务器请求客户端执行操作）
- JSON-RPC **通知**（服务器告知客户端状态变更）
- **但不能**发送 JSON-RPC 响应（除非是恢复流）

### 3.4 SSE 流行为规则

Streamable HTTP 中的 SSE 流遵循以下精细规则：

```
① 初始事件
   Server ──► "id: 1\ndata: \n\n"  (空 data，仅分配事件 ID，供断线恢复用)

② 消息推送
   Server ──► "id: 2\ndata: {通知/请求}\n\n"
   Server ──► "id: 3\ndata: {通知/请求}\n\n"

③ 连接关闭 ≠ 流终止
   Server 可以在发送带 ID 的事件后关闭 HTTP 连接
   客户端应当通过重连来「轮询」SSE 流

④ retry 字段
   Server 关闭连接前可发送: "retry: 3000\n\n"
   客户端必须等待指定毫秒数后重连

⑤ 最终响应
   SSE 流应当最终包含与 POST 请求对应的 JSON-RPC 响应
   发送响应后 Server 应当终止 SSE 流

⑥ 断连 ≠ 取消
   SSE 断连不解释为客户端取消请求
   取消必须显式发送 CancelledNotification
```

### 3.5 会话管理

服务器通过 `MCP-Session-Id` 头管理会话：

```
初始化阶段：
Client ──── POST /mcp ────────────► Server
          { "method": "initialize", ... }

Client ◄──── HTTP 200 ───────────── Server
           MCP-Session-Id: sess_abc123
           { "result": { ... } }

后续所有请求均携带会话 ID：
Client ──── POST /mcp ────────────► Server
           MCP-Session-Id: sess_abc123
           { "method": "tools/list", ... }
```

| 规则 | 说明 |
|------|------|
| **分配** | 服务器在 `InitializeResult` 响应头中返回 `MCP-Session-Id` |
| **ID 要求** | 全局唯一、加密安全（UUID、JWT 或加密哈希） |
| **字符限制** | 仅可见 ASCII（0x21-0x7E） |
| **客户端携带** | 所有后续请求必须携带 |
| **会话终止** | 服务器可以随时终止，之后返回 HTTP 404 |
| **客户端重建** | 收到 404 时重新初始化 |
| **显式终止** | 客户端可以发送 `DELETE /mcp` 带着会话 ID 终止 |

### 3.6 流可恢复性

这是 Streamable HTTP 相比旧方案的**最大改进**：

```
正常通信：
Server ──── id: 42 ───► Client
Server ──── id: 43 ───► Client
Server ──── id: 44 ───► Client
           [连接意外断开]

客户端自动重连：
Client ──── GET /mcp ─────────────► Server
           Last-Event-ID: 43       (告知最后收到的事件)

Server 从 id=44 开始重放：
Server ──── id: 44 ───► Client
Server ──── id: 45 ───► Client
```

| 规则 | 说明 |
|------|------|
| **事件 ID 分配** | 可选，ID 在会话内全局唯一 |
| **客户端重连** | 发送 GET 请求，携带 `Last-Event-ID` 头 |
| **服务器重放** | 可选重放断连后的消息，但不能重放其他流的消息 |
| **恢复方式** | 始终通过 GET 请求进行（无论原始流是 POST 还是 GET 启动的） |

### 3.7 多连接与消息分发

- 客户端可以同时维持**多个 SSE 流连接**
- 服务器必须将每条消息**仅在一个连接流上发送**，不可广播
- 消息丢失风险通过流可恢复性缓解

## 4. 与 HTTP+SSE 的对比

### 4.1 架构对比

```
旧方案 (HTTP+SSE)：                    新方案 (Streamable HTTP)：

┌──────────┐        ┌──────────┐        ┌──────────┐        ┌──────────┐
│ Client   │        │ Server   │        │ Client   │        │ Server   │
│          │──GET──►│ /sse     │        │          │        │          │
│          │◄─SSE──│          │        │          │──POST─►│          │
│          │        │          │        │          │◄─JSON──│ /mcp     │
│          │──POST─►│ /msg     │        │          │  或     │ (单端点)  │
│          │        │          │        │          │◄─SSE───│          │
└──────────┘        └──────────┘        │          │──GET──►│          │
                                         │          │◄─SSE───│          │
         双端点耦合                               └──────────┘        └──────────┘

                                                        单一端点按需响应
```

### 4.2 能力矩阵

| 维度 | HTTP+SSE (2024-11-05) | Streamable HTTP (2025-03-26+) |
|------|----------------------|-------------------------------|
| 端点数量 | 2 个（`/sse` + `/messages`） | **1 个**（MCP 端点） |
| 无状态支持 | ❌ 不支持 | ✅ 完全支持 |
| 会话管理 | 无标准化机制 | `MCP-Session-Id` 标准头 |
| 协议版本 | 无版本头 | `MCP-Protocol-Version` 头 |
| 流恢复 | ❌ 断开即丢失 | ✅ `Last-Event-ID` 续传 |
| 按需流式 | ❌ 始终流式 | ✅ 服务器自主选择 JSON 或 SSE |
| 连接管理 | 强制长连接 | **可选**长连接（Server 可主动关闭） |
| retry 控制 | 无标准化 | 标准化 `retry` 字段 |
| 显式取消 | 无 | `CancelledNotification` |
| 多连接 | 不支持 | ✅ 支持多个 SSE 流 |
| 基础设施兼容 | ⚠️ 需特殊配置 | ✅ 「只是 HTTP」 |

## 5. 为什么不用 WebSocket？

官方团队详细评估了 WebSocket，最终决定暂时不采用：

| 原因 | 说明 |
|------|------|
| **RPC 场景不匹配** | 无状态 RPC 风格的服务每次调用都建立 WebSocket 太重 |
| **浏览器请求头限制** | WebSocket 连接无法附加 `Authorization` 等自定义请求头 |
| **升级限制** | 只有 GET 能升级为 WebSocket，POST 需要两步升级 |
| **兼容性负担** | 引入 WebSocket 会大幅增加客户端/服务端兼容性组合 |
| **SSE 可模拟** | 浏览器中 SSE 可用第三方库完整模拟，WebSocket 不能 |

> 官方保持开放态度：如果实践中 SSE 不够用，未来可能重新评估 WebSocket。同时不阻止社区自行扩展。

## 6. 迁移指南

### 6.1 服务器端迁移

**渐进式方案**（推荐）：

```
1. 保留旧端点 /sse 和 /messages（向后兼容旧客户端）
2. 新增 MCP 端点 /mcp（支持 Streamable HTTP）
3. 新旧端点并存运行
4. 逐步淘汰旧端点
```

### 6.2 客户端兼容探测

客户端需要自动识别服务器支持的传输类型：

```
步骤 1：尝试 Streamable HTTP
  Client ──── POST /mcp ──────────► Server
            { "method": "initialize" }
            Accept: application/json, text/event-stream

  若成功 → 服务器支持 Streamable HTTP，使用新传输

  若失败 (400/404/405) →

步骤 2：降级到旧 HTTP+SSE
  Client ──── GET /sse ───────────► Server
            Accept: text/event-stream

  若收到 endpoint 事件 → 服务器是旧 HTTP+SSE，使用旧传输
```

### 6.3 无状态服务器示例

最简单的 Streamable HTTP 实现（无状态工具服务器）：

```python
# 伪代码
@app.post("/mcp")
async def handle_mcp(request):
    body = await request.json()

    if body["method"] == "initialize":
        # 始终响应，但不分配 Session ID
        return JSONResponse({"result": {"protocolVersion": "2025-11-25", ...}})

    elif body["method"] == "tools/list":
        # 直接返回工具列表
        return JSONResponse({"result": {"tools": [...]}})

    elif body["method"] == "tools/call":
        # 简单工具 → JSON 响应
        if body["params"]["name"] == "get_weather":
            return JSONResponse({"result": {"content": [{"type": "text", "text": "晴 25°C"}]}})

        # 复杂工具（需要进度反馈）→ SSE 流式响应
        elif body["params"]["name"] == "long_task":
            return StreamingResponse(
                long_task_stream(),
                media_type="text/event-stream"
            )
```

### 6.4 有状态服务器示例

```python
@app.post("/mcp")
async def handle_mcp(request):
    session_id = request.headers.get("MCP-Session-Id")
    body = await request.json()

    if body["method"] == "initialize":
        # 分配 Session ID
        session_id = str(uuid.uuid4())
        response = JSONResponse({"result": { ... }})
        response.headers["MCP-Session-Id"] = session_id
        return response

    # 后续请求验证 Session
    if not session_id or session_id not in sessions:
        return JSONResponse({"error": ...}, status_code=404)

    # ... 正常处理

@app.delete("/mcp")
async def terminate_session(request):
    session_id = request.headers.get("MCP-Session-Id")
    del sessions[session_id]
    return Response(status_code=200)
```

## 7. 与已有协议的关系

### 7.1 在 MCP 传输层中的位置

```
MCP 协议

├── 消息格式：JSON-RPC 2.0
│
└── 传输层（Transport）
    ├── stdio           ← 本地进程间通信（最常用）
    ├── SSE (旧)        ← 远程传输 v1（已废弃，2024-11-05）
    └── Streamable HTTP ← 远程传输 v2（当前标准，2025-03-26+）
```

### 7.2 与 LSP / ACP 的联系

| 协议 | 远程传输方案 |
|------|-------------|
| **LSP** | stdio、TCP Socket、Pipe |
| **MCP** | stdio、Streamable HTTP |
| **ACP** | stdio、HTTP、WebSocket（设计中） |

> 三大协议都在向 HTTP 靠拢——因为它兼容一切基础设施。

### 7.3 协议栈全景

```
┌─────────────────────────────────────────────────────┐
│                    Agent 应用层                       │
│                                                     │
│         ACP (编辑器 ↔ Agent)                         │
│               │                                     │
│               ▼                                     │
│         MCP (Agent ↔ 数据源/工具)                     │
│               │                                     │
│               ▼                                     │
│    ┌──────────────────────────┐                     │
│    │     MCP 传输层             │                    │
│    │  ┌──────────┬──────────┐ │                    │
│    │  │  stdio   │Streamable│ │                     │
│    │  │ (本地)    │  HTTP    │ │                    │
│    │  │          │ (远程)    │ │                    │

│    └──────────────────────────┘                     │
```

## 8. 总结

| 维度 | 要点 |
|------|------|
| **本质** | MCP 协议的新一代远程传输方式，替代 HTTP+SSE |
| **核心创新** | 单一端点 + 按需流式（JSON 响应 vs SSE 流自由切换） |
| **三大模式** | 无状态 / 无状态+流式 / 有状态——覆盖所有场景 |
| **最大改进** | 流可恢复（`Last-Event-ID` 断点续传） |
| **会话管理** | `MCP-Session-Id` 标准化会话绑定 |
| **兼容性** | 「只是 HTTP」——兼容所有 HTTP 基础设施 |
| **命名由来** | "Streamable" 意为「可流式化」——需要时才流式，不是「始终流式」 |

> **一句话**：Streamable HTTP 把旧方案的「双端点强制流式」变成了「单端点按需流式」——既支持无状态的简单 REST 风格调用，又保留了复杂场景下 SSE 流式的全部能力。
