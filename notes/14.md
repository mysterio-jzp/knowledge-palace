## Temporal简介

Temporal是一个新兴的分布式工作流引擎。如果你在工作中遇到过以下这些场景，都可以来了解一下Temporal这个底层引擎：

1. 跨服务、跨时间周期的复杂业务流程
2. 业务工作流建模（BPM）
3. DevOps工作流
4. Saga分布式事务
5. BigData数据处理和分析Pipeline
6. Serverless函数编排

这些场景看上去互相没有太大关联，但有一个共同点：需要**编排**（Orchestration）。

Temporal解决的关键痛点，就是**分布式系统中的编排问题**。

### 编排的本质是什么

要理解编排，可以借助和 Orchestration 对应的另一个概念：Choreography。

举个例子，我们开发微服务时，经常借助消息队列（MQ）做事件驱动的业务逻辑，实现最终一致的、跨多个服务的数据流，这属于 Choreography。而一旦引入 MQ，可能会遇到下面一系列问题：

- 消息时序问题
- 重试幂等问题
- 事件和消息链路追踪问题
- 业务逻辑过于分散的问题
- 数据已经不一致的校正对账问题

在复杂微服务系统中，MQ 是一个很有用的组件，但 MQ 不是银弹。如果过度依赖类似 MQ 的方案事件驱动，但又没有足够强大的消息治理方案，整个分布式系统将嘈杂不堪，难以维护。

如果转换思路，找一个“调度主体”，让所有消息的流转，都由这个“指挥家”来控制，这就是 Orchestration。

- **Choreography**：无界上下文，去中心化，每个组件只关注和发布自己的事件，完全异步，注重的是解耦。
- **Orchestration**：有界上下文，存在全局编排者，从全局建模成状态机，注重的是内聚。

**Temporal 的所有应用场景，都是有全局上下文、高内聚的“编排”场景**。比如 BPM 有明确的流程图，DevOps 和 BigData Pipeline 有明确的 DAG，长活事务有明确的执行和补偿流程。

Temporal 让我们像写正常代码一样写工作流代码，但并不一定在本机执行，哪一行在什么时间 yield，由服务端信令统一控制。很多分布式系统韧性问题也被封装掉了，比如分布式锁、宕机重试、过期重试导致的数据错误、并发消息处理时间差问题等。

### Temporal关键概念

1. **Workflow**
   - Workflow 是编排层关键概念。
   - 每种类型是注册到服务端的 WorkflowType。
   - 每个 WorkflowType 可创建任意多运行实例（WorkflowExecution）。
   - 每个 Execution 有唯一 WorkflowID；如果是 Cron / Continue-as-New，每次执行还会有唯一 RunID。
   - Workflow 可以有环，也可以嵌套子工作流（ChildWorkflow）。

2. **Activity**
   - Workflow 编排的对象主要是 Activity。
   - 编排 Activity 就像正常写代码一样，可用 if / for / while(true) 等逻辑结构调用 Activity 方法。
   - 要求具备确定性。

3. **Signal**
   - 对运行中的 WorkflowExecution 可发送带参数信号。
   - Workflow 中可等待或按条件处理信号，动态控制工作流执行逻辑。

## 5分钟上手Temporal

### 搭环境

#### 方法1：本地运行 Temporalite

本地调试一般没有性能和稳定性要求，建议下载 all-in-one Binary：Temporalite。

```bash
temporalite start --namespace default
```

下载 Binary 放到 PATH 后，一行命令启动即可连接 localhost:7233，也可以打开 Dashboard 查看运行状态：

- http://127.0.0.1:8233

#### 方法2：开发或产线环境 Helm 部署分布式 Temporal

Dev/Prod 环境建议用 Helm + Kubernetes 部署，存储层准备独立运维的 MySQL 或 PostgreSQL。

提前创建数据库 `temporal` 与 `temporal_visibility`，Helm install 完成后通过 admintools 初始化数据库 Schema。

```bash
helm dependency build  # optional

helm install -f values/values.mysql.yaml my-temporal . \
  --namespace temporal --create-namespace=true \
  --kube-context *** \
  --set elasticsearch.enabled=false \
  --set server.config.persistence.default.sql.user=*** \
  --set server.config.persistence.default.sql.password="***" \
  --set server.config.persistence.visibility.sql.user=*** \
  --set server.config.persistence.visibility.sql.password="***" \
  --set server.config.persistence.default.sql.host=*** \
  --set server.config.persistence.visibility.sql.host=***
```

如果连接 AWS Aurora，需要在 `values.mysql.yaml` 中补充：

```yaml
server:
  config:
    persistence:
      default:
        sql:
          connectAttributes:
            tx_isolation: 'READ-COMMITTED'
```

第一次 Install 后，admintools Pod 会正常运行，其他 Pod 可能因缺少数据库表失败。进入 admintools Pod 执行 Schema 初始化：

```bash
export SQL_PLUGIN=mysql
export SQL_HOST=mysql_host
export SQL_PORT=3306
export SQL_USER=mysql_user
export SQL_PASSWORD=mysql_password

cd /etc/temporal/schema/mysql/v57/temporal
temporal-sql-tool --connect-attributes "tx_isolation=READ-COMMITTED" --ep mysql-endpoint -u *** --password "***" --db temporal setup-schema -o -v 0.0 -f ./schema.sql

cd /etc/temporal/schema/mysql/v57/visibility
temporal-sql-tool --connect-attributes "tx_isolation=READ-COMMITTED" --ep mysql-endpoint -u *** --password "***" --db temporal_visibility setup-schema -o -v 0.0 -f ./schema.sql
```

之后等待其他 Pod 自动重启或手动删除，所有组件即可正常运行。Forward `temporal-web` 的 8080 端口后检查 UI。

### 写代码（Java示例）

先添加 SDK 依赖（Gradle）：

```groovy
dependencies {
    implementation('io.temporal:temporal-sdk:1.17.0')
}
```

#### 第1步：定义 Workflow 接口

```java
@WorkflowInterface
public interface MyWorkflow {
    @WorkflowMethod
    String execute(Object param);

    @QueryMethod
    List<String> getSomeStatus();

    @SignalMethod
    void manualComplete();
}
```

#### 第2步：定义 Activity 接口

```java
@ActivityInterface
public interface MyActivities {
    String doSometing(Object param);
}
```

#### 第3步：实现 Workflow 编排逻辑

```java
public class MyWorkflowImpl implements MyWorkflow {
    private final MyActivities activities;
    private boolean someSignal = false;

    public MyWorkflowImpl() {
        activities = Workflow.newActivityStub(MyActivities.class, ActivityOptions.newBuilder()
            .setStartToCloseTimeout(Duration.ofHours(1))
            .build());
    }

    @Override
    public String execute(Object param) {
        Workflow.sleep(Duration.ofSeconds(25));
        activities.doSomething();
        Workflow.await(() -> this.someSignal);

        Promise<String> promise = Async.function(() -> {
            log.info("do something async");
            return "Cancelled";
        });

        promise.get();
        return "Workflow Done!";
    }

    @Override
    public void manualComplete() {
        this.someSignal = true;
    }
}
```

#### 第4步：实现 Activity

```java
@Slf4j
@Service
public class MyActivitiesImpl implements MyActivities {
    @Override
    public String doSomething(Object param) {
        try {
            log.info("Activity: {}, {}",
                Activity.getExecutionContext().getInfo().getRunId(),
                Activity.getExecutionContext().getInfo().getActivityId());
        } catch (Exception e) {
            throw Activity.wrap(e);
        }

        Activity.getExecutionContext().heartbeat("I'm still running");
        return "Activity Done !";
    }
}
```

#### 第5步：初始化 Client / Worker 并注册

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class WorkflowManager {
    @Resource
    private DeployActivities myActivities;

    @Getter
    private WorkflowClient client;

    @PostConstruct
    public void initWorkflowFactory() {
        WorkflowServiceStubs service = WorkflowServiceStubs.newConnectedServiceStubs(
            WorkflowServiceStubsOptions.newBuilder()
                .setTarget("127.0.0.1:7233")
                .validateAndBuildWithDefaults(),
            Duration.ofSeconds(5));

        this.client = WorkflowClient.newInstance(service);
        WorkerFactory factory = WorkerFactory.newInstance(client);

        Worker worker = factory.newWorker("MyTaskQueue");
        worker.registerWorkflowImplementationTypes(MyWorkflow.class);
        worker.registerActivitiesImplementations(deployActivities);

        factory.start();
    }

    public <T> Stub<T> startWorkflow(Class<T> workflowType, Object... params) {
        String workflowId = UUID.randomUUID().toString();
        WorkflowOptions workflowOptions = WorkflowOptions.newBuilder()
            .setWorkflowId(workflowId)
            .setTaskQueue("MyTaskQueue")
            .build();

        T workflowStub = this.client.newWorkflowStub(workflowType, workflowOptions);
        return new Stub<>(workflowId, workflowStub);
    }

    @Data
    @AllArgsConstructor
    public static class Stub<T> {
        private String workflowId;
        private T stub;
    }
}
```

#### 第6步：启动一次 WorkflowExecution

```java
@Service
@RequiredArgsConstructor
public class WorkflowExecutor {

    @Resource
    private WorkflowManager workflowManager;

    public String startMyWorkflow(Object param) {
        String workflowId = UUID.randomUUID().toString();
        WorkflowOptions workflowOptions = WorkflowOptions.newBuilder()
            .setWorkflowId(workflowId)
            .setTaskQueue("MyTaskQueue")
            .build();

        WorkflowManager.Stub<MyWorkflow> myWorkflowStub =
            workflowManager.startWorkflow(MyWorkflow.class, param);
        myWorkflowStub.getStub().execute("Hello");
        return workflowId;
    }
}
```

## 实践与思考

### 实践历程

作者在 2022 年基于 Temporal 开发 DevOps 工作流引擎，覆盖 CI/CD/CV 与系统集成。前端使用 x6 做 DSL 和执行过程可视化，后端使用 Temporal SDK 处理编排逻辑。核心编排代码较少，更多精力可聚焦在业务开发。

在工作流引擎选型中，作者比较了 Jira Workflow、Temporal、Argo、Prefect、ConcourseCI、Petri Nets 等，结论偏向 Temporal 在动态编排、性能与通用性上的优势。

### 使用关键注意点

- 工作流代码必须**确定性**（使用 Workflow 库提供的 async、current time 等能力），非确定行为需显式记录副作用。
- 不要在 Activity 代码中调用 Workflow，编排逻辑应全部放在 Workflow 实现里。
- Workflow Stub 每次调用动态创建，不要尝试用 IoC 容器托管 Workflow 实例（Activity 实现可以托管）。
- Workflow 参数与返回值会持久化，避免自引用/递归结构对象导致序列化循环问题。
- 写 Workflow 代码时要切换到“上帝视角”：代码执行位置与时间都可能跨 Worker、跨时间跨度。

### 亮点和局限性

亮点：

1. 多语言 SDK 友好（Go/Java/TS/Python/PHP/C#/Ruby）。
2. 稳定性与性能较好，适合产线规模。
3. Web UI 查询 Workflow / Activity 方便。
4. 应用层灵活性高、场景广。
5. 中心化状态机 + 事件溯源模式下，韧性好、Bug 率低。
6. 对长时间跨度业务友好，可原生实现分布式 Timer/Cron。

局限：

1. 偏底层，不直接提供 Workflow-as-DSL/YAML，需要自行实现 DSL 与可视化。
2. 多语言与多框架生态仍在持续完善。
3. Cron 当前支持到分钟级，非秒级。

### 总结

作者认为 Temporal 本质上可理解为：

- 服务端：通过信令与队列调度实现中心化工作流引擎，通过事件溯源实现持久化长活事务与分布式可重入进程。
- 客户端：通过代理模式把本地函数调用转换为基于 gRPC 的分布式调度与状态存取。

Temporal 的三个关键特性：Resumable、Recoverable、Reactive。
