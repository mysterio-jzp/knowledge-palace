# 对话消息中间件选型与实现方案

## 文档信息

| 项目 | 内容 |
|------|------|
| 文档版本 | v2.0 |
| 更新日期 | 2026-01-23 |
| 适用场景 | 对话消息系统（区分 sessionId / chatId，要求顺序） |
| 推荐方案 | RocketMQ 5.x LiteTopic |

---

## 1. 背景与需求

### 1.1 业务场景
对话消息系统，需要处理区分 `sessionId`（会话级标识）和 `chatId`（单次消息标识）的消息。

### 1.2 核心需求

| 需求 | 描述 |
|------|------|
| **顺序保证** | 同一会话内的消息必须按发送顺序处理 |
| **高并发** | 支持大量并发会话同时进行 |
| **低延迟** | 消息从发送到消费的端到端延迟要求低 |
| **隔离性** | 不同会话的消息不应相互阻塞影响 |

---

## 2. 方案选型

### 2.1 主流消息中间件对比

| 中间件 | 顺序保证方式 | 高并发能力 | 适用场景 | 推荐度 |
|--------|-------------|-----------|----------|--------|
| **RocketMQ** | `sessionId` 哈希到同一队列 | 高（10万级/秒） | 金融级事务、顺序消息 | ⭐⭐⭐⭐⭐ |
| **Kafka** | 单 Partition 顺序 | 极高（120万/秒） | 日志管道、大数据流 | ⭐⭐⭐ |
| **Pulsar** | 单 Topic 顺序 | 高（95万/秒） | 云原生、多租户 | ⭐⭐⭐⭐ |
| **RabbitMQ** | 单队列顺序 | 中（万级/秒） | 复杂路由、业务解耦 | ⭐⭐ |

### 2.2 选型结论

**首选方案：RocketMQ 5.x LiteTopic**

- 每个 LiteTopic 天然保证顺序性（一个 LiteTopic = 一个队列）
- 支持百万级 Session 并发
- 自动生命周期管理（创建/删除），零运维
- 支持单 Consumer 动态订阅多个 LiteTopic，资源可控
- 支持断点续传，节点故障可恢复

## 3. LiteTopic 核心概念

### 3.1 什么是 LiteTopic

LiteTopic 是 RocketMQ 5.x 专为**海量临时性通道**场景设计的轻量级主题模型，每个 LiteTopic 在底层对应一个队列，天然保证顺序。

### 3.2 核心特性

| 特性 | 说明 |
|------|------|
| **一个 LiteTopic = 一个队列** | 天然保证顺序性，无需额外配置 |
| **百万级规模支持** | 可为每个 Session 创建独立通道 |
| **自动创建** | 首次发送或订阅时自动创建，无需预创建 |
| **自动删除** | 超过 TTL 无消息写入后自动删除 |
| **动态订阅** | 支持运行时动态增加/删除订阅 |
| **订阅关系可差异化** | 同一消费者组内可订阅不同 LiteTopic |

### 3.3 环境要求

| 要求 | 说明 |
|------|------|
| **服务端** | RocketMQ 5.0-rmq-20251024-1 及以上版本 |
| **客户端** | RocketMQ gRPC 5.1.0 及以上版本 |
| **协议** | 仅支持 gRPC 协议（端口默认 8081） |
| **消费模式** | `LITE_SELECTIVE` |

### 4.2 并发模型

**单 Consumer 实例支持并发处理多个 LiteTopic 的消息**：

| 维度 | 机制 |
|------|------|
| **并发粒度** | 队列粒度，SDK 自动管理 |
| **单队列顺序** | 同一 LiteTopic 的消息由同一线程串行处理 |
| **跨队列并行** | 不同 LiteTopic 的消息可被不同线程并行处理 |
| **线程复用** | 消费线程池大小固定，动态分配给不同队列 |

### 5.1 生产者实现（Python）

```python
import json
import time
from rocketmq.client import Producer, Message

class LiteTopicProducer:
    """LiteTopic 生产者（单例复用）"""
    
    def __init__(self, name_server: str, parent_topic: str, producer_group: str):
        self.parent_topic = parent_topic
        self.producer = Producer(producer_group)
        self.producer.set_name_server_address(name_server)
        self.producer.set_use_grpc(True)  # 启用 gRPC
        self.producer.start()
        print(f"LiteTopic producer started, parent topic: {parent_topic}")
    
    def send_to_session(self, session_id: str, chat_id: str, content: str, **kwargs):
        """
        发送消息到指定 Session 的 LiteTopic
        LiteTopic 会在首次发送时自动创建
        """
        message_body = {
            "chatId": chat_id,
            "sessionId": session_id,
            "content": content,
            "timestamp": int(time.time() * 1000),
            **kwargs
        }
        
        msg = Message(self.parent_topic)
        msg.set_keys(chat_id)
        msg.set_tags("dialogue")
        msg.set_body(json.dumps(message_body))
        # 关键：LiteTopic 名称直接使用 session_id
        msg.set_lite_topic(session_id)
        
        ret = self.producer.send(msg)
        print(f"Sent - sessionId: {session_id}, chatId: {chat_id}, msgId: {ret.msg_id}")
        return ret
    
    def shutdown(self):
        self.producer.shutdown()


# 全局单例生产者
_producer_instance = None

def get_producer(name_server: str, parent_topic: str, producer_group: str) -> LiteTopicProducer:
    """获取生产者单例"""
    global _producer_instance
    if _producer_instance is None:
        _producer_instance = LiteTopicProducer(name_server, parent_topic, producer_group)
    return _producer_instance
```

### 5.2 消费者实现（Python）- 单例 + 动态订阅

```python
import json
import threading
from typing import Dict, Callable, Optional
from rocketmq.client import LitePushConsumer, ConsumeStatus

class LiteTopicConsumer:
    """
    LiteTopic 消费者（单例 + 动态订阅）
    
    核心设计：
    - 单个 Consumer 实例
    - 动态订阅/退订多个 LiteTopic（每个 session 一个）
    - 队列间并行处理，队列内串行处理
    """
    
    def __init__(self, name_server: str, parent_topic: str, consumer_group: str):
        self.parent_topic = parent_topic
        self.consumer = LitePushConsumer(consumer_group)
        self.consumer.set_name_server_address(name_server)
        self.consumer.set_use_grpc(True)
        # 关键：设置 LITE_SELECTIVE 模式，支持动态差异化订阅
        self.consumer.set_consumer_mode("LITE_SELECTIVE")
        
        # 记录已订阅的 session 及其 handler（用于幂等和状态管理）
        self._handlers: Dict[str, Callable] = {}
        self._lock = threading.RLock()
        
        # 启动消费者
        self.consumer.start()
        print(f"LiteTopic consumer started, group: {consumer_group}")
    
    def subscribe_session(self, session_id: str, message_handler: Callable):
        """
        动态订阅 Session 的 LiteTopic
        
        会话建立时调用，运行时动态增加订阅，无需重启
        """
        with self._lock:
            # 幂等检查：避免重复订阅
            if session_id in self._handlers:
                return
            
            # 动态订阅
            self.consumer.subscribe_lite_topic(
                self.parent_topic,
                session_id,  # LiteTopic 名称 = session_id
                lambda msg: self._callback_wrapper(session_id, msg)
            )
            self._handlers[session_id] = message_handler
            print(f"Subscribed to session: {session_id}, total: {len(self._handlers)}")
    
    def unsubscribe_session(self, session_id: str):
        """
        动态退订 Session 的 LiteTopic
        
        会话结束时调用，释放订阅配额
        注意：退订不会删除 LiteTopic，只取消订阅关系
        """
        with self._lock:
            if session_id not in self._handlers:
                return
            
            self.consumer.unsubscribe_lite_topic(self.parent_topic, session_id)
            del self._handlers[session_id]
            print(f"Unsubscribed from session: {session_id}, remaining: {len(self._handlers)}")
    
    def _callback_wrapper(self, session_id: str, msg):
        """回调包装器，处理消息并确保顺序"""
        try:
            body = json.loads(msg.body)
            chat_id = body.get("chatId")
            content = body.get("content")
            
            print(f"Processing - sessionId: {session_id}, chatId: {chat_id}")
            
            # 调用业务处理函数
            handler = self._handlers.get(session_id)
            if handler:
                handler(session_id, body)
            else:
                print(f"Warning: no handler for session {session_id}")
            
            return ConsumeStatus.CONSUME_SUCCESS
        except Exception as e:
            print(f"Error processing message for session {session_id}: {e}")
            # 返回 SUSPEND 触发重试，但不阻塞其他 LiteTopic
            return ConsumeStatus.RECONSUME_LATER
    
    def get_active_session_count(self) -> int:
        """获取当前活跃的 Session 数量"""
        return len(self._handlers)
    
    def shutdown(self):
        """关闭消费者，同时退订所有会话"""
        with self._lock:
            for session_id in list(self._handlers.keys()):
                self.consumer.unsubscribe_lite_topic(self.parent_topic, session_id)
            self._handlers.clear()
        self.consumer.shutdown()
        print("LiteTopic consumer shutdown")


# 全局单例消费者
_consumer_instance = None

def get_consumer(name_server: str, parent_topic: str, consumer_group: str) -> LiteTopicConsumer:
    """获取消费者单例"""
    global _consumer_instance
    if _consumer_instance is None:
        _consumer_instance = LiteTopicConsumer(name_server, parent_topic, consumer_group)
    return _consumer_instance
```

## 6. 断点续传支持

### 6.1 实现代码

```python
class ResumableLiteTopicConsumer(LiteTopicConsumer):
    """支持断点续传的消费者"""
    
    def get_consumer_offset(self, session_id: str) -> Optional[int]:
        """获取指定 Session 的当前消费位点"""
        with self._lock:
            if session_id not in self._handlers:
                return None
            return self.consumer.get_offset(self.parent_topic, session_id)
    
    def resume_from_offset(self, session_id: str, offset: int):
        """从指定 Offset 恢复消费"""
        with self._lock:
            if session_id not in self._handlers:
                return
            self.consumer.seek(self.parent_topic, session_id, offset)
            print(f"Resumed session {session_id} from offset {offset}")
    
    def subscribe_session_with_resume(self, session_id: str, 
                                       message_handler: Callable,
                                       last_offset: Optional[int] = None):
        """订阅并支持断点续传"""
        self.subscribe_session(session_id, message_handler)
        if last_offset is not None:
            self.resume_from_offset(session_id, last_offset)
```

### 6.2 应用场景

**WebSocket 重连场景**：

```
┌─────────────────────────────────────────────────────────────────┐
│                    断点续传流程                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 客户端 WebSocket 断开                                       │
│  2. 服务端记录该 Session 的最后消费位点（存储到 Redis/DB）       │
│  3. 客户端重连，携带 session_id 和 last_offset                  │
│  4. 新节点调用 subscribe_session_with_resume()                  │
│  5. 从 last_offset 继续消费，消息不丢、不重复                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 7. LiteTopic 自动生命周期管理

### 7.1 生命周期流程图

```
┌─────────────────────────────────────────────────────────────────┐
│                    LiteTopic 自动生命周期                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ① 自动创建              ② 活跃期                ③ 自动删除      │
│                                                                 │
│  首次发送或订阅时    ──→   持续收发消息      ──→   超过 TTL 后    │
│  系统自动创建资源          正常使用             释放存储和配额    │
│                                                                 │
│  耗时：毫秒级            时长：业务决定         无需人工干预      │
│  对业务透明              按需使用              自动清理          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 7.2 自动创建机制

| 属性 | 说明 |
|------|------|
| **触发条件** | 首次发送消息（`set_lite_topic`）或首次订阅（`subscribe_lite_topic`） |
| **创建耗时** | 毫秒级，对业务透明 |
| **是否需要预创建** | 不需要 |
| **队列数量** | 每个 LiteTopic 默认 1 个队列，天然保证顺序 |

### 7.3 自动删除机制（TTL）

| 配置项 | 说明 |
|--------|------|
| **触发条件** | 距离最后一次消息写入超过 `expiration` 时间 |
| **删除粒度** | 整个 LiteTopic 被删除 |
| **配额释放** | 释放占用的订阅配额计数 |
| **建议 TTL** | 短会话 5-10 分钟，长会话 1-24 小时 |

### 7.4 重要提示

> **注意**：即使 LiteTopic 已从系统中删除，但若仍有消费者客户端保持对其的订阅关系，该订阅关系依然会被计入订阅总数，直至消费者停止订阅。

因此，**会话结束时必须主动调用 `unsubscribe_session()`**，释放订阅配额。

## 8. 订阅与退订机制详解

### 8.1 为什么需要动态退订？

**核心原因：释放订阅配额**

RocketMQ 实例对 LiteTopic 订阅数量有**硬性配额限制**。如果不退订，即使会话已结束，订阅关系仍被占用，会导致新会话无法建立订阅。

```
┌─────────────────────────────────────────────────────────────────┐
│                    订阅配额示例                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  假设实例限制：总订阅关系数 ≤ 10,000                            │
│                                                                 │
│  如果不退订：                                                   │
│  ├── Session 1 建立连接 → 订阅关系 +1                          │
│  ├── Session 2 建立连接 → 订阅关系 +1                          │
│  ├── ...                                                        │
│  └── Session 10,000 建立连接 → 订阅关系满，新会话失败 ❌        │
│                                                                 │
│  如果及时退订：                                                 │
│  ├── Session 结束 → 订阅关系 -1（释放配额）                     │
│  └── 新会话可以继续建立，形成良性循环 ✅                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 8.2 退订 vs 删除的区别

| 操作 | 作用范围 | 是否删除 LiteTopic | 是否释放订阅配额 |
|------|---------|-------------------|-----------------|
| `unsubscribe_session()` | 消费者侧：取消订阅关系 | ❌ **不会** | ✅ **会** |
| TTL 过期自动删除 | 服务端侧：删除 LiteTopic 资源 | ✅ **会** | ✅ **会**（删除后） |

**两者配合使用**：
- `unsubscribe` 主动释放订阅配额（会话结束时立即执行）
- TTL 自动清理数据存储（无消息后自动执行）

## 9. 线程模型与并发说明

### 9.1 核心结论

**单 Consumer 实例支持并发处理多个 LiteTopic 的消息**：

| 问题 | 答案 |
|------|------|
| 一个线程会处理多个队列吗？ | **不会**，一个线程固定绑定一个队列 |
| 多个线程会调用同一个回调函数吗？ | **会**，回调函数会被多个线程并发调用 |
| 回调函数需要线程安全吗？ | **需要**，因为可能被多个线程同时执行 |
| 同一队列的消息会并发执行吗？ | **不会**，同一队列串行执行 |
| 不同 Session 的消息会互相阻塞吗？ | **不会**，不同队列并行处理 |

### 9.2 线程安全注意事项

由于回调函数会被多个线程并发调用，需要注意：

**✅ 线程安全的写法**

```python
# 好的做法：使用局部变量
def message_callback(session_id: str, message: dict):
    # 局部变量，线程安全
    chat_id = message.get("chatId")
    content = message.get("content")
    return process(chat_id, content)

# 或者：使用线程局部存储
import threading
thread_local = threading.local()

def message_callback(session_id: str, message: dict):
    if not hasattr(thread_local, 'cache'):
        thread_local.cache = {}  # 每个线程有自己的缓存
    # 这样是安全的
```

**❌ 不安全的写法**

```python
# 危险：共享全局变量
global_counter = 0

def message_callback(session_id: str, message: dict):
    global global_counter
    global_counter += 1  # 多线程同时修改，数据会错乱！
    
    # 危险：共享对象
    shared_dict[session_id] = value  # 可能被其他线程同时修改
```

### 9.3 简化记忆

> **一个线程 = 一个队列 = 串行处理**
> **多个线程 = 多个队列 = 并行处理**
> **回调函数 = 被多个线程调用 = 需要线程安全**

## 11. 最佳实践总结

### 11.1 配置建议

| 配置项 | 建议值 | 说明 |
|--------|--------|------|
| `expiration`（TTL） | 1-24 小时 | 根据业务会话时长设置 |
| `consumer_count` | 1 个 | 单消费者即可，通过动态订阅管理 |
| `消费线程池大小` | SDK 自动管理 | 无需手动配置 |
| `幂等存储` | Redis + chatId | 防止重复消费 |

### 11.2 开发规范

1. **生产者**：使用单例，`sessionId` 作为 LiteTopic 名称
2. **消费者**：使用单例 + `LITE_SELECTIVE` 模式
3. **会话建立**：调用 `subscribe_session()` 动态订阅
4. **会话结束**：**必须**调用 `unsubscribe_session()` 释放配额
5. **幂等处理**：使用 `chatId` 做幂等，防止重复消费
6. **线程安全**：回调函数需考虑多线程并发调用场景

### 11.3 架构简化价值

采用 LiteTopic + 单 Consumer 动态订阅方案后：

| 传统方案问题 | LiteTopic 解决方案 |
|-------------|-------------------|
| 需维护 Session→Node 路由表 | **无需路由表**，消息精准投递 |
| 广播消费浪费资源 | **按需订阅**，精准消费 |
| 节点故障消息丢失 | **断点续传**，从 Offset 恢复 |
| 状态同步复杂 | **无状态扩容**，新节点动态订阅 |
| 顺序消息需分区键 | **天然有序**（1 LiteTopic = 1 队列） |

## 12. 关键要点速记

| 问题 | 答案 |
|------|------|
| LiteTopic 如何创建？ | **自动创建**：首次发送或订阅时自动创建 |
| LiteTopic 如何删除？ | **自动删除**：超过 TTL 无消息写入后自动删除 |
| 需要为每个 Session 创建独立 Consumer 吗？ | **不需要**：单 Consumer，动态订阅数千个 LiteTopic |
| 如何实现动态订阅？ | 使用 `LITE_SELECTIVE` 模式，运行时调用 `subscribe_lite_topic()` |
| 会话结束时必须退订吗？ | **必须**：释放订阅配额，防止新会话无法订阅 |
| 退订会删除 LiteTopic 吗？ | **不会**：只取消订阅关系，LiteTopic 由 TTL 自动删除 |
| 节点宕机后如何恢复？ | 新节点动态订阅原 LiteTopic，从 Offset 继续消费 |
| 回调函数需要注意什么？ | **线程安全**：会被多个线程并发调用 |
| 单 Consumer 支持并发吗？ | **支持**：队列间并行处理，互不影响 |

## 13. 总结

| 场景 | 推荐方案 |
|------|----------|
| 会话量 < 10万，团队熟悉 RocketMQ 4.x | 传统分区顺序方案（备选） |

**最终建议**：对于对话消息场景，优先采用 **LiteTopic + 单 Consumer 动态订阅方案**，为每个会话创建独立的轻量主题，实现物理隔离、天然顺序和断点续传，同时具备极低的动态创建开销和百万级规模支撑能力。
