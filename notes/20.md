## 1. 为什么需要 JSON-RPC？

### 1.1 RPC 的核心思想

**RPC (Remote Procedure Call，远程过程调用)** 的核心思想很简单：像调用本地函数一样调用远程服务。

```
本地调用：
result = add(1, 2)                    ← 直接调用

远程调用：
result = remote_call("add", [1, 2])   ← 通过网络调用远程服务器上的 add 函数
```

要实现远程调用，需要解决三个问题：
1. **怎么传**：数据如何编码（序列化）
2. **传什么**：怎么指定调用哪个方法、传什么参数
3. **协议无关**：不绑定特定传输方式（HTTP、WebSocket、stdio 都应该能用）

### 1.2 JSON-RPC 的答案

JSON-RPC 是一个**极简主义的 RPC 协议**，只用 JSON 就解决了全部三个问题：

| 问题 | JSON-RPC 解法 |
|------|--------------|
| 编码 | JSON（文本，可读，所有语言原生支持） |
| 语义 | `method` + `params` + `id` 三个字段 |
| 传输 | 协议无关（HTTP、stdio、WebSocket、TCP 随便用） |

> 协议规范仅约 **10 页**，是目前所有主流 RPC 协议中**最简单的**。

## 2. JSON-RPC 2.0 核心规范

### 2.1 四种消息类型

JSON-RPC 2.0 定义了四种消息类型：

```
                          JSON-RPC 消息
                               │
          ┌────────────────────┼────────────────────┐
          │                    │                    │
      Request              Notification           Batch
   (期待回复)              (不期待回复)           (批量请求)
          │
    ┌─────┴─────┐
    │           │
  Response    Error
 (成功响应)   (错误响应)
```

### 2.2 请求（Request）

一个完整的 JSON-RPC 请求包含四个字段：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "subtract",
  "params": [42, 23]
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `jsonrpc` | string | ✅ | 固定值 `"2.0"`，版本标识 |
| `id` | string / number / null | ✅ | 请求标识，用于匹配响应。**通知中无此字段** |
| `method` | string | ✅ | 调用的方法名，如 `"subtract"`、`"tools/call"` |
| `params` | array / object | 否 | 参数。数组为**按位置传参**，对象为**按名称传参** |

**两种传参方式**：

```json
// 按位置传参 (by-position)
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "subtract",
  "params": [42, 23]
}

// 按名称传参 (by-name)
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "subtract",
  "params": { "minuend": 42, "subtrahend": 23 }
}
```

### 2.3 通知（Notification）

通知是**不需要回复的请求**——没有 `id` 字段：

```json
{
  "jsonrpc": "2.0",
  "method": "update",
  "params": [1, 2, 3, 4, 5]
}
```

```json
{
  "jsonrpc": "2.0",
  "method": "log",
  "params": { "level": "info", "message": "Server started" }
}
```

| 特点 | 说明 |
|------|------|
| **无 `id` 字段** | 不需要匹配响应 |
| **单向** | 发完即忘，不期待回复 |
| **不可批处理** | 通知不能在 Batch 中发送 |
| **典型用途** | 日志、状态更新、事件推送 |

### 2.4 成功响应（Response）

当请求被成功处理时：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": 19
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `jsonrpc` | string | ✅ | 固定值 `"2.0"` |
| `id` | — | ✅ | 必须与请求的 `id` 完全相同（类型和值） |
| `result` | any | ✅ | 返回结果，可以是任意 JSON 类型 |

> ⚠️ `Result` 和 `Error` **互斥**——成功响应有 `result` 无 `error`，错误响应有 `error` 无 `result`。

### 2.5 错误响应（Error）

当请求处理失败时：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32601,
    "message": "Method not found",
    "data": "The method 'foobar' does not exist"
  }
}
```

Error 对象包含三个字段：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `code` | number | ✅ | 错误码（整数） |
| `message` | string | ✅ | 简短描述（单句，不含换行） |
| `data` | any | 否 | 附加信息（堆栈跟踪、详细原因等） |

## 3. 标准错误码

JSON-RPC 2.0 定义了五类标准错误码：

| 错误码 | 名称 | 说明 |
|--------|------|------|
| `-32700` | Parse error | 无效 JSON。服务端收到无法解析的数据 |
| `-32600` | Invalid Request | 发送的 JSON 不是有效的请求对象 |
| `-32601` | Method not found | 方法不存在或不可用 |
| `-32602` | Invalid params | 方法参数无效 |
| `-32603` | Internal error | JSON-RPC 内部错误 |

**自定义错误码**范围：

```
-32768 ~ -32000    保留给预定义错误（未来扩展）
-32000 ~ -32099    保留给实现定义的服务器错误
其余范围          可用于应用自定义错误
```

## 4. 批量请求（Batch）

### 4.1 基本用法

客户端可以一次发送多个请求（JSON 数组），服务端按顺序返回响应数组：

```json
// 请求（JSON 数组）
[
  { "jsonrpc": "2.0", "id": 1, "method": "add", "params": [1, 2] },
  { "jsonrpc": "2.0", "id": 2, "method": "add", "params": [3, 4] },
  { "jsonrpc": "2.0", "method": "notify", "params": ["hello"] }
]

// 响应（JSON 数组，通知无响应）
[
  { "jsonrpc": "2.0", "id": 1, "result": 3 },
  { "jsonrpc": "2.0", "id": 2, "result": 7 }
]
```

### 4.2 批处理规则

| 规则 | 说明 |
|------|------|
| **空数组** | 服务端应返回 Invalid Request 错误 |
| **全是通知** | 服务端不返回任何内容 |
| **单个请求** | 必须返回单个响应对象，不能包装在数组中 |
| **执行顺序** | 服务端可以任意顺序执行（不保证顺序） |
| **通知不允许** | 通知（无 `id` 的消息）不能出现在 Batch 中 |

## 5. 协议规则总结

### 5.1 客户端行为

| 规则 | 规范 |
|------|------|
| 发送结构 | 所有请求严格是 JSON 对象或数组（Batch） |
| `jsonrpc` 字段 | 必须为 `"2.0"` |
| `id` 类型 | null、number、string 之一 |
| `id` 顺序 | 不要求连续、有序，只要求匹配 |
| 通知 | 客户端不应对通知设置 `id` |
| 重试 | 客户端自行决定，规范不规定 |

### 5.2 服务端行为

| 规则 | 规范 |
|------|------|
| 解析失败 | 返回 Parse error（-32700） |
| 结构无效 | 返回 Invalid Request（-32600） |
| 请求批处理 | 逐个处理，逐响应 |
| 通知无响应 | 服务端不得对通知返回响应 |
| `id` 匹配 | 响应中的 `id` 必须与原请求完全一致 |
| 批量响应 | 可以按任意顺序返回，客户端按 `id` 匹配 |

## 6. JSON-RPC 1.0 vs 2.0

| 维度 | 1.0 | 2.0 |
|------|-----|-----|
| `jsonrpc` 字段 | 无 | `"2.0"` |
| `id` 字段 | 必填（无法支持通知） | 可选（无 `id` = 通知） |
| 错误码 | 简单字符串 | 结构化 `{code, message, data}` |
| 命名参数 | 不支持 | 支持（`params` 可以是对象） |
| 批量请求 | 不支持 | 支持（JSON 数组） |
| 错误时 `id` | null | 保留原请求 `id` |

> 现在所有现代协议（LSP、MCP、ACP）都基于 **JSON-RPC 2.0**。

## 7. JSON-RPC 传输层

JSON-RPC 的核心优势是**传输无关**——以下方式都可以：

### 7.1 HTTP

```http
POST /rpc HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "getUser",
  "params": { "userId": 123 }
}
```

### 7.2 stdio（标准输入输出）

```
┌──────────────┐                    ┌──────────────┐
│ Client       │                    │ Server       │
│              │──── stdin ────────►│              │
│              │    JSON-RPC 消息    │  (子进程)     │
│              │◄─── stdout ───────│              │
└──────────────┘                    └──────────────┘
```

这是 LSP 和 MCP 最常用的本地通信方式。Client 启动 Server 作为子进程，通过 stdin 发送 JSON-RPC 请求，stdout 读取响应。

### 7.3 WebSocket

```javascript
// 客户端
ws.send(JSON.stringify({
  jsonrpc: "2.0",
  id: 1,
  method: "subscribe",
  params: { channel: "updates" }
}));

ws.onmessage = (event) => {
  const response = JSON.parse(event.data);
  // 处理响应或通知
};
```

### 7.4 TCP Socket

```json
{"jsonrpc":"2.0","id":1,"method":"ping"}\n
```

LSP 支持通过 TCP Socket 连接远程 Language Server。

## 8. 在 LSP / MCP / ACP 中的应用

JSON-RPC 2.0 是这三个协议共同的**消息格式层**：

```
┌─────────────────────────────────────────────────┐
│               LSP / MCP / ACP                   │
│                                                  │
│    各自的方法语义（补全、工具调用、会话管理...）        │
│                                                  │
├─────────────────────────────────────────────────┤
│              JSON-RPC 2.0                        │
│                                                  │
│    Request / Response / Notification / Error     │
│                                                  │
├─────────────────────────────────────────────────┤
│              传输层 (stdio / HTTP / TCP)         │
└─────────────────────────────────────────────────┘
```

### 8.1 各协议的方法命名风格

| 协议 | 方法示例 | 命名风格 |
|------|---------|---------|
| **LSP** | `textDocument/completion`、`textDocument/hover` | 领域/操作 |
| **MCP** | `tools/list`、`resources/read`、`prompts/get` | 原语/操作 |
| **ACP** | `session/prompt`、`session/new`、`fs/read_text_file` | 模块/操作 |

### 8.2 LSP 中的实际消息

```json
// LSP 请求：请求代码补全
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "textDocument/completion",
  "params": {
    "textDocument": { "uri": "file:///main.go" },
    "position": { "line": 10, "character": 15 }
  }
}

// LSP 通知：文档被打开
{
  "jsonrpc": "2.0",
  "method": "textDocument/didOpen",
  "params": {
    "textDocument": {
      "uri": "file:///main.go",
      "languageId": "go",
      "version": 1,
      "text": "package main\n\nimport \"fmt\"\n..."
    }
  }
}
```

### 8.3 MCP 中的实际消息

```json
// MCP 请求：列出可用工具
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}

// MCP 通知：资源已更新
{
  "jsonrpc": "2.0",
  "method": "notifications/resources/updated",
  "params": {
    "uri": "file:///project/config.json"
  }
}
```

### 8.4 ACP 中的实际消息

```json
// ACP 请求：发送用户提示
{
  "jsonrpc": "2.0",
  "id": 5,
  "method": "session/prompt",
  "params": {
    "sessionId": "sess_abc123",
    "prompt": [{ "type": "text", "text": "修复这个 bug" }]
  }
}

// ACP 通知：取消当前操作
{
  "jsonrpc": "2.0",
  "method": "session/cancel",
  "params": {
    "sessionId": "sess_abc123"
  }
}
```

## 9. 与其他 RPC 协议对比

| 协议           | 序列化      | 复杂度   | 可读性   | 适用场景                 |
| ------------ | -------- | ----- | ----- | -------------------- |
| **JSON-RPC** | JSON     | ★☆☆☆☆ | ✅ 极高  | 简单服务、跨语言、LSP/MCP/ACP |
| **gRPC**     | Protobuf | ★★★★☆ | ❌ 不可读 | 高性能微服务、强类型           |
| **XML-RPC**  | XML      | ★★☆☆☆ | ⚠️ 一般 | 遗留系统                 |
| **SOAP**     | XML      | ★★★★★ | ⚠️ 极差 | 企业遗留系统               |
| **REST**     | JSON/任意  | ★★☆☆☆ | ✅ 高   | Web API              |
| **GraphQL**  | JSON     | ★★★☆☆ | ✅ 高   | 灵活查询、前端驱动            |

### JSON-RPC 的取舍

| 优势 | 劣势 |
|------|------|
| 极简，协议仅 10 页 | 无 Schema（无强类型校验） |
| 人类可读，调试友好 | 文本编码比二进制慢 |
| 传输无关（HTTP/stdio/WS/TCP） | 无流式控制（依赖传输层） |
| 所有语言原生支持 JSON | 无内置服务发现 |
| 批量请求减少往返 | 无压缩（纯文本） |
| 通知机制（单向消息） | 无连接状态管理 |

> JSON-RPC 选择了**简单**而非**性能**。它不适合每秒百万次的高频调用，但在 LSP/MCP/ACP 这类「人机交互速率」的场景中，简洁性远胜一切。

## 10. 在 AI Agent 中的特殊价值

### 10.1 为什么 AI 协议都选 JSON-RPC

LSP、MCP、ACP 不约而同选择 JSON-RPC 2.0 不是巧合：

| 原因 | 说明 |
|------|------|
| **可读性** | AI 正在生成 JSON-RPC 调用时，可以「看到并理解」自己发了什么 |
| **调试友好** | 开发者可以直接看日志中的 JSON 消息排查问题 |
| **工具链成熟** | 几乎所有语言都有现成的 JSON 序列化库 |
| **传输灵活** | stdio 用于本地进程，HTTP 用于远程——同一套协议 |
| **与 LLM function calling 格式天然兼容** | OpenAI 的 function calling 本质就是结构化的 JSON |

### 10.2 JSON-RPC 通知 = Agent 实时推送

Agent 执行任务时，通过 JSON-RPC Notification 推送状态，客户端无需轮询：

```json
// Agent 通知：工具调用进度
{ "jsonrpc": "2.0", "method": "notifications/progress",
  "params": { "token": "abc", "progress": 50, "total": 100 } }

// Agent 通知：状态变更
{ "jsonrpc": "2.0", "method": "session/update",
  "params": { "sessionId": "xxx", "update": { "sessionUpdate": "agent_message_chunk", ... } } }
```

## 11. 总结

| 维度 | 要点 |
|------|------|
| **本质** | 极简的远程过程调用协议，用 JSON 描述一切 |
| **消息类型** | Request（有 id）、Response（有 result）、Error（有 error）、Notification（无 id） |
| **批量请求** | 支持 JSON 数组一次发送多个请求 |
| **错误码** | 5 个标准码（-32700 ~ -32603），支持自定义 |
| **传输** | 协议无关——HTTP、stdio、WebSocket、TCP 都可以 |
| **核心哲学** | **少即是多**——用最少的概念解决最核心的问题 |
| **在 AI 协议栈中的位置** | LSP、MCP、ACP 的消息格式基础层 |

> **一句话**：JSON-RPC 2.0 是 AI Agent 协议栈的「通用语言」——LSP 用它查询代码语义，MCP 用它调用远程工具，ACP 用它指挥 Agent。理解 JSON-RPC = 理解所有上层协议的共同语法。
