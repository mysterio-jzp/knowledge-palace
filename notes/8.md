> seccomp-bpf 是 Linux 内核提供的系统调用防火墙。如果说 Namespace 限制了"你能看到什么"，那 seccomp 限制了"你能做什么"。

## 1. 一句话理解

进程运行在用户态，任何底层操作（读写文件、创建进程、开网络连接）最终都要通过 **系统调用（syscall）** 进入内核态完成。Linux 有 400+ 个 syscall，但一个正常程序只需要其中很小一部分。

**seccomp-bpf 就是给进程装上一个 syscall 防火墙——只放行需要的，其余一律拦截。**

```
正常进程：代码 → 任意 syscall → 内核（真正执行）→ 硬件/文件/网络

seccomp 后：
  代码 → 任意 syscall →【必然先 trap 进入内核态】
                        ↓
                  内核态 BPF 过滤（syscall handler 入口处）
                        ↓
            ┌───────────┴───────────┐
            ↓                       ↓
    放行（白名单内）          拦截（白名单外）
            ↓                       ↓
    真正执行 syscall 主体    不执行主体，直接：
    操作硬件/文件/网络        SIGKILL 进程 / 返回 errno

```

### 1.1 关键认知：先 trap 进内核，再 BPF 过滤

新手最容易踩的坑：以为 seccomp"在用户态就把不合法的 syscall 拦下了"。**错了**。

syscall 的 trap 是 CPU 层面的硬切换——`syscall` 指令 / `int 0x80` 软中断会把 CPU 从 Ring 3（用户态）强制切到 Ring 0（内核态），这一步**任何进程都无法跳过**，BPF 过滤器也无从干预。

所以 seccomp 的过滤点在内核态、且是 syscall handler 的最入口处：

1. 进程执行 `syscall` 指令 → **强制陷入内核态**（所有 syscall 必经，BPF 无法提前拦截）
2. 内核在真正调用 `sys_xxx()` 之前，先跑 BPF 程序
3. BPF 返回 `SECCOMP_RET_ALLOW` 放行；`KILL_PROCESS` / `KILL_THREAD` 直接 SIGKILL（syscall 主体从未执行）；`ERRNO` 不执行主体、返回错误码给进程
4. 只有放行后，syscall 才会真正去碰硬件 / 文件 / 网络

**一句话**：seccomp 拦截的是"syscall 主体有没有资格执行"，不是"syscall 有没有资格进入内核"。白名单外的 syscall 同样进过内核，只是刚进门就被 BPF 赶出去了。

## 2. seccomp 的演进

### 2.1 第一代：strict mode（已废弃）

最早出现在 Linux 2.6.12（2005年），只能做一件事：把进程锁死，只允许四个 syscall 通过——`read`、`write`、`exit`、`sigreturn`。其他任何调用直接 `SIGKILL`。

```c
// strict mode — 全有或全无
prctl(PR_SET_SECCOMP, SECCOMP_MODE_STRICT);
// 之后这个进程只能 read/write/exit/sigreturn
// 连 malloc 都不行（需要 brk/mmap）
```

太极端，几乎只有写安全研究的人用。

### 2.2 第二代：seccomp-bpf（2012年至今）

引入 BPF（Berkeley Packet Filter）作为过滤语言，让用户自定义规则：哪些 syscall 可以过、带什么条件、拦截时是杀进程还是返回错误码。

```c
// 安装 BPF 过滤器
prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog);
```

这一下从"全有或全无"变成了"想怎么拦就怎么拦"。

## 3. BPF：过滤器怎么工作

### 3.1 BPF 的本质

BPF 是一套**在内核中运行的微型虚拟机**。你给它一段 BPF 字节码（指令序列），内核将它翻译后挂载到某个 hook 点上，每次事件触发时执行。

seccomp 用的不是完整的 eBPF（extended BPF），而是经典 BPF（cBPF），指令更少更简单：

```
每条 BPF 指令结构：
┌──────────┬──────┬─────┐
│ opcode   │ jt   │ jf  │    （共 8 字节）
└──────────┴──────┴─────┘
  操作码     真跳转  假跳转
```

### 3.2 过滤器执行流程

```
进程调用 syscall(N) 
    │
    ▼
内核陷入 → seccomp 钩子被触发
    │
    ▼
BPF 程序逐条执行：
    ld [0]              # 载入 seccomp_data.nr（本次 syscall 编号）
    jeq #57, ACCEPT, NEXT   # 如果是 read(0) → 放行，否则继续
    jeq #63, ACCEPT, NEXT   # 如果是 write(1) → 放行，否则继续
    jeq #60, ACCEPT, NEXT   # 如果是 exit(60) → 放行，否则继续
    ret KILL               # 以上都不是 → 杀进程
    │
    ▼
结果：ACCEPT / KILL / TRAP / ERRNO
```

### 3.3 seccomp_data 结构

每次 syscall 触发时，BPF 程序可以访问这个结构体：

```c
struct seccomp_data {
    int   nr;                   // syscall 编号（最常用）
    __u32 arch;                 // 调用方的体系架构（x86_64 vs x86 vs ARM）
    __u64 instruction_pointer;  // 触发 syscall 的指令地址
    __u64 args[6];              // syscall 的 6 个参数（可用来做细粒度检查）
};
```

> **为什么需要 `arch`？** 防止 32/64 位交叉攻击。同一个 syscall 在 x86_64 和 x86 上的编号可能不同，攻击者可能先切换到 32 位模式来绕过规则。好的 seccomp 规则第一条总是检查 `arch`。

### 3.4 四种处置动作

| 动作 | 效果 | 使用场景 |
|------|------|---------|
| `SECCOMP_RET_ALLOW` | 放行，正常执行 | 白名单内的 syscall |
| `SECCOMP_RET_KILL` | 杀进程 + SIGSYS | 绝对不应该被调用的 syscall |
| `SECCOMP_RET_ERRNO` | 返回错误码，进程继续运行 | 不想杀进程但要告知"不允许" |
| `SECCOMP_RET_TRAP` | 发送 SIGSYS 给进程（可捕获） | 调试、日志记录 |

**实践中最常用的组合**：最后一条规则不写 `KILL` 而是写 `ERRNO`，这样即使漏了某个白名单 syscall，程序也不至于直接挂掉，而是拿到一个错误码有机会优雅降级。

## 4. nsjail 中的 seccomp-bpf

### 4.1 两种配置方式

#### 方式一：Kafel 策略语言（推荐）

手写 BPF 字节码不现实。[Google Kafel](https://github.com/google/kafel) 是一个高级 DSL，编译成 BPF 规则：

```policy
# nsjail 的默认 Kafel 策略（简化版）
POLICY sandbox {
    # 1. 架构检查 — 防止 32/64 位逃逸
    DENY {
        arch != x86_64
    }
    
    # 2. 文件操作（允许正常的读写操作）
    USE {
        read, write, openat, close, stat, fstat, lseek,
        pread64, readv, mmap, munmap, brk
    }
    
    # 3. 进程控制（允许基本进程管理）
    USE {
        exit, exit_group, getpid, gettid,
        rt_sigaction, rt_sigreturn, rt_sigprocmask,
        clone, execve
    }
    
    # 4. 约束 clone — 可以创建子进程，但不能创建新的 namespace
    ALLOW clone {
        args[0] == (CLONE_VM | CLONE_VFORK)
    }
    
    # 5. 拒绝危险操作
    DENY {
        mount, umount2, pivot_root,  # 文件系统操作
        ptrace, process_vm_readv,     # 进程注入
        init_module, finit_module,    # 内核模块加载
        kexec_load, kexec_file_load,  # 内核替换
        reboot,                       # 系统重启
        bpf                           # BPF 程序加载（防止嵌套绕过）
    }
}
USE ALLOW {
    # 6. 其余 syscall 默认允许
    # （这是一种宽松策略，适合内部可信代码）
}
```

#### 方式二：直接在 nsjail 配置中引用

```ini
# nsjail.cfg
seccomp_policy_file: "/etc/nsjail/seccomp.kafel"
```

或者内联（短策略）：

```ini
seccomp_string: "POLICY sandbox { KILL { arch != x86_64 } USE { read, write, openat, close, exit, exit_group } }"
```

### 4.2 默认策略 vs 自定义策略

| 策略类型 | syscall 数量 | 安全性 | 适用场景 |
|---------|:-----------:|--------|---------|
| nsjail 默认 | ~200 个 | 中 | 通用脚本执行 |
| 自定义白名单 | 50-100 个 | 高 | 特定工具（如只跑 Python） |
| 极度收紧 | 20-30 个 | 最高 | 纯数学计算、无 I/O |

### 4.3 一个针对 Python 执行的白名单策略

```policy
POLICY python_sandbox {
    # 架构检查
    KILL { arch != x86_64 }
    
    # === 文件 I/O ===
    USE {
        read, write, openat, close,
        stat, fstat, lstat, lseek,
        getdents64,              # 列目录
        readlink,                # 读符号链接
        mmap, munmap, mprotect,
        brk,                     # 堆扩展
        madvise,                 # 内核内存建议
    }
    
    # === 进程管理 ===
    USE {
        exit, exit_group,
        getpid, gettid, getuid, getgid,
        rt_sigaction, rt_sigreturn,
        rt_sigprocmask,
        clone, execve, wait4,
        arch_prctl,              # x86_64 特定（设置 FS 基址）
        set_robust_list, get_robust_list,  # futex 相关
    }
    
    # === clone 参数限制 ===
    # 允许正常的 fork/vfork，拒绝创建 namespace
    ALLOW clone {
        args[0] == (CLONE_VM | CLONE_VFORK)
        || args[0] == (CLONE_VM | CLONE_VFORK | CLONE_SETTLS)
        || args[0] == (CLONE_VM | CLONE_VFORK | CLONE_CHILD_SETTID)
    }
    
    # === 时间 ===
    USE { clock_gettime, gettimeofday, nanosleep }
    
    # === 网络（如果允许） ===
    USE {
        socket, connect, bind, listen, accept,
        sendto, recvfrom, getsockname, getpeername,
        setsockopt, getsockopt, shutdown,
        sendfile,                  # 文件高效传输
    }
    
    # === Python 解释器特定 ===
    USE {
        futex,                    # 锁/条件变量
        sched_getaffinity,        # CPU 亲和性
        sched_yield,              # 线程让步
        getrandom,                # os.urandom()
        epoll_create1, epoll_ctl, epoll_wait,  # asyncio 事件循环
        eventfd2,                 # 线程间通知
        timerfd_create, timerfd_settime,       # Python 定时器
        membarrier,               # 内存屏障
        rseq,                     # 重启序列
        prlimit64,                # 资源限制查询
    }
    
    # === DNS 查询（UDP） ===
    USE {
        recvmsg, sendmsg,         # Python 常用网络 syscall
    }
    
    # === 显式拒绝 ===
    KILL {
        mount, umount2, chroot, pivot_root,
        ptrace, process_vm_readv, process_vm_writev,
        init_module, finit_module, delete_module,
        kexec_load, kexec_file_load, reboot,
        bpf, seccomp,             # 防止嵌套 sandbox 绕过
        iopl, ioperm,             # I/O 端口直接访问
        acct,                     # 进程记账开关
        settimeofday, adjtimex, clock_settime,  # 改时间
    }
}
```

## 5. seccomp 的防御原理：纵深防御中的最后一环

沙箱安全是分层递进式防御（defense in depth）。seccomp 在这一体系中的位置：

```
┌─────────────────────────────────────────────┐
│ Layer 1: Namespace 隔离                      │
│ "看不到就不危险"  — 限制资源视图              │
├─────────────────────────────────────────────┤
│ Layer 2: rlimit / cgroup                    │
│ "用不完就不危险" — 限制资源消耗              │
├─────────────────────────────────────────────┤
│ Layer 3: chroot / mount bind               │
│ "找不到就不危险" — 限制文件系统访问           │
├─────────────────────────────────────────────┤
│ Layer 4: capabilities                      │
│ "没权限就不危险" — 剥夺 root 特权            │
├─────────────────────────────────────────────┤
│ Layer 5: seccomp-bpf   ← 本文焦点          │
│ "调不了就不危险" — 限制系统调用面            │
└─────────────────────────────────────────────┘
```

**seccomp 解决的是前四层都挡不住的缺口**。比如：

- Namespace 隔离了文件系统视图，但进程仍然可以调用 `reboot()` — 不会成功，但调用本身可能触发内核 bug
- User NS 映射了 UID，但进程可以调用 `init_module()` 尝试加载恶意内核模块
- Capabilities 限制了特权操作，但内核中存在过只凭特定 syscall 参数就能触发的漏洞

**seccomp 是最后的兜底**——就算前四层全部失效，进程能调用的 syscall 还是被清单锁死的。

## 6. seccomp-bpf 的限制

### 6.1 只审 syscall，不审参数语义

```
seccomp 能审查：socket(AF_INET, SOCK_STREAM, 0)
                → "syscall #41 放行" ✓

seccomp 审不了：socket 具体连接了哪个 IP
                → 需要 nftables/代理做内容级过滤 ✗
```

### 6.2 规则复杂度上限

BPF 程序有指令数量限制（经典 BPF 最多 4096 条）。对于需要大量条件判断的场景（如按文件路径过滤），seccomp 力不从心。

### 6.3 不是所有东西都走 syscall

现代 CPU 支持用户态自旋锁（`futex` 的某些快速路径），纯用户态代码可以完全不触发 seccomp 就执行。但对于我们关注的沙箱场景（Python 代码执行），一切 I/O 都会经过 syscall，覆盖是充分的。

### 6.4 维护成本

随着程序依赖变化（升级 Python 版本、新增依赖库），白名单需要持续维护。漏掉的 syscall 会导致 `SIGKILL`，对线上稳定性要求高。

## 7. 实战：如何为一个程序生成 seccomp 策略

### 7.1 strace 收集 syscall 历史

```bash
# 跑一遍程序的正常流程，收集所有用到的 syscall
strace -f -c python3 -c "import requests; print(requests.get('https://example.com').status_code)" 2>&1 | tail -20

# 输出示例：
# % time     seconds  usecs/call     calls    errors syscall
# ------ ----------- ----------- --------- --------- ----------------
#  35.21    0.000918          17        53           read
#  18.45    0.000481          10        48           futex
#  12.31    0.000321          10        31           mmap
#   8.52    0.000222           8        27           close
#   5.87    0.000153          10        15           write
#   ...
```

### 7.2 提取纯 syscall 名称列表

```bash
# 抓出本周用的所有 syscall，去重
strace -f -e trace=all python3 your_script.py 2>&1 | \
  grep -oP '^\w+|^\[pid \d+\] \w+' | \
  sed 's/\[pid [0-9]*\] //' | \
  sort -u
```

### 7.3 翻译成 Kafel 策略

```bash
# 生成 Kafel USE 块
echo "USE {" 
strace -f python3 your_script.py 2>&1 | \
  grep -oP '^\w+' | sort -u | tr '\n' ', '
echo "}"
```

然后加上架构检查、危险 syscall 拒绝、clone 参数限制，就是一份可用的策略。

## 8. 与其他隔离层的关系

| 机制 | 拦截维度 | 粒度 | 覆盖盲区 |
|------|---------|------|---------|
| **Namespace** | 资源视图（看什么） | 命名空间级 | 不能限制操作本身 |
| **rlimit/cgroup** | 资源用量（用多少） | 进程级 | 不能限制特定 syscall |
| **Capabilities** | 特权（有没有权） | 能力集 | 普通用户也能调的危险 syscall |
| **seccomp-bpf** | 系统调用（做什么） | syscall 级 | 不审参数语义、不审用户态 |

> 防御深度不是指"每个都做一点"，而是指"每个都做好，任何一个都能兜底"。seccomp 的价值在于：即使 Namespace 被绕过、User NS 映射出错、capabilities 配置疏漏——进程能做的事情也被 seccomp 限制在已知范围内。

## 9. 在 nsjail 配置中的完整示例

```ini
# nsjail.cfg — 结合 namespace + seccomp + rlimit 的完整沙箱配置

# === Namespace 隔离 ===
clone_newns: true
clone_newpid: true
clone_newnet: true       # 无网络场景（如需网络用 clone_newnet: false + 外部 netns）
clone_newuser: true
clone_newipc: true
clone_newuts: true

# === 文件系统 ===
chroot: "/jail"
mount {
    src: "/bin"
    dst: "/bin"
    is_bind: true
    rw: false
}
# ... 其他只读挂载 ...

# === 用户映射 ===
uid_mapping { inside_id: "0"; outside_id: "1000"; count: "1"; }

# === 资源限制 ===
rlimit_as: 512          # 512MB 虚拟内存
rlimit_cpu: 30          # 30 秒 CPU 时间
rlimit_nproc: 32        # 最多 32 个进程
rlimit_fsize: 104857600 # 100MB 文件大小

# === seccomp 规则（白名单） ===
seccomp_policy_file: "/etc/nsjail/seccomp.kafel"
# 或内联:
# seccomp_string: "POLICY sandbox { KILL { arch != x86_64 } USE { ... } }"
```
