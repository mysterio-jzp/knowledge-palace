## 1. 背景：编辑器与 Coding Agent 的集成碎片化

### 1.1 问题描述

2024-2025 年，AI Coding Agent 迎来爆发式增长。Claude Code、Cursor、GitHub Copilot、Cody、Continue、Aider 等大量 Agent 涌现，它们需要与 VS Code、JetBrains IDE、Zed、Neovim 等各种编辑器集成。

问题随之而来：

```
Agent 数量 M = 10，编辑器数量 N = 8
需要的集成数量 = 10 × 8 = 80 套
```

每个 Agent 都要为每个编辑器写适配层，每个编辑器都要对接每个 Agent 的 API。这是 LSP 解决过的同一个问题，只是对象从「语言服务」变成了「AI Agent」。

### 1.2 ACP 的诞生

**Agent Client Protocol (ACP)** 由 **JetBrains** 和 **Zed** 联合发起，于 2025 年首次公开。核心理念：

> **任何支持 ACP 的编辑器，都可以使用任何支持 ACP 的 Coding Agent —— 就像 LSP 让任意编辑器使用任意语言服务一样。**

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐          │
│  │ VS Code  │  │ JetBrains│  │   Zed    │  ...     │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘          │
│       │             │             │                  │
│       ▼             ▼             ▼                  │
│  ┌─────────────────────────────────────────────┐    │
│  │           ACP (标准协议层)                    │    │
│  └─────────────────────────────────────────────┘    │
│       ▲             ▲             ▲                  │
│       │             │             │                  │
│  ┌────┴─────┐  ┌────┴─────┐  ┌────┴─────┐          │
│  │ Claude   │  │ GitHub   │  │ 自建     │  ...     │
│  │ Code     │  │ Copilot  │  │ Agent    │          │
│  └──────────┘  └──────────┘  └──────────┘          │
│                                                      │
└──────────────────────────────────────────────────────┘
```

**效果**：10 个 Agent + 8 个编辑器 → 10 + 8 = 18 个适配，而非 80 个定制集成。

### 1.3 与 LSP 的类比定位

| 维度 | LSP | ACP |
|------|-----|-----|
| 协议提出者 | 微软 (2016) | JetBrains + Zed (2025) |
| Client 是什么 | 编辑器插件 | 代码编辑器 (IDE) |
| Server 是什么 | 语言服务器 | Coding Agent |
| 标准化什么 | 代码智能查询（补全/诊断/跳转） | Agent 交互流程（会话/提示/工具/文件操作） |
| 数据方向 | 主要是 Server → Client | 双向：交互控制 + 内容流 |
| 会话概念 | 无（每次请求独立） | 有（session 贯穿多轮对话） |

> **ACP 是 LSP 在 AI 时代的自然延伸。**如果说 LSP 标准化了「编辑器如何向语言服务提问」，ACP 标准化了「编辑器如何与 AI Agent 对话和协作」。

## 2. 核心架构

### 2.1 角色定义

ACP 中只有两个直接角色（与 LSP 类似，比 MCP 的三角色模型更简洁）：

```
┌──────────────────────────────────────┐
│             Client                    │
│          (代码编辑器/IDE)              │
│                                      │
│  • 管理环境 (cwd, 文件系统)            │
│  • 处理用户交互                        │
│  • 控制资源访问                        │
│  • 渲染 Agent 输出                     │
│  • 提供 UI 层 (diff 展示等)            │
└──────────────┬───────────────────────┘
               │  ACP (JSON-RPC 2.0)
               │
┌──────────────┴───────────────────────┐
│             Agent                     │
│       (Coding Agent 进程)             │
│                                      │
│  • 调用 LLM                           │
│  • 执行工具                            │
│  • 修改代码                            │
│  • 规划和推理                          │
└──────────────────────────────────────┘
```

| 角色 | 说明 | 示例 |
|------|------|------|
| **Client** | 代码编辑器/IDE，提供用户交互界面 | VS Code、JetBrains IDE、Zed、Neovim |
| **Agent** | 利用生成式 AI 自主修改代码的程序 | Claude Code、GitHub Copilot Agent、Cody、Continue |

> Agent 通常作为 Client 的**子进程**运行（stdio 模式），也可以作为远程服务独立部署（HTTP/WebSocket 模式）。

### 2.2 部署模式

| 模式 | 通信方式 | 适用场景 |
|------|---------|---------|
| **本地 Agent** | JSON-RPC over stdio | 低延迟、本地运行、安全可控 |
| **远程 Agent** | HTTP 或 WebSocket | Agent 托管在云端、需要 GPU 等专有资源 |

> ⚠️ 远程 Agent 的完整支持仍在开发中，官方正与多家 Agent 平台协作完善。

## 3. 协议基础

### 3.1 JSON-RPC 2.0 消息格式

与 LSP、MCP 相同，ACP 也基于 JSON-RPC 2.0：

- **请求（Request）**：包含 `id`、`method`、`params`，期待响应
- **响应（Response）**：包含 `id`、`result`（成功）或 `error`（失败）
- **通知（Notification）**：包含 `method`、`params`，不含 `id`，无需响应

### 3.2 文件路径约定

- 所有文件路径**必须为绝对路径**
- 行号从 **1** 开始计数（而非 0）

### 3.3 文本渲染

- 用户可读文本的默认格式为 **Markdown**
- 这样设计的好处：提供足够富文本表现力，同时不强制编辑器支持 HTML 渲染

## 4. 完整生命周期

ACP 的交互遵循严格的三阶段生命周期：

```
┌─────────────────────────────────────────────────────────┐
│                    阶段 1：初始化                         │
│                                                         │
│  Client ──── initialize ──────────► Agent               │
│  (协议版本 + Client 能力 + Client 信息)                    │
│                                                         │
│  Client ◄──── InitializeResult ─── Agent                │
│  (协商后协议版本 + Agent 能力 + Agent 信息)                │
│                                                         │
│  Client ──── authenticate (如需要) ─► Agent              │
│                                                         │
├─────────────────────────────────────────────────────────┤
│                   阶段 2：会话设置                         │
│                                                         │
│  ┌─ 新建会话：                                           │
│  │  Client ──── session/new ────────► Agent              │
│  │  (cwd + MCP Servers 配置)                             │
│  │  Client ◄──── { sessionId } ────── Agent              │
│  │                                                      │
│  └─ 恢复会话（需 loadSession 能力）：                     │
│     Client ──── session/load ───────► Agent              │
│     (sessionId + cwd)                                    │
│     Agent  → → → 回放历史消息 → → → Client               │
│     Client ◄──── { result: null } ─── Agent              │
│                                                         │
├─────────────────────────────────────────────────────────┤
│                   阶段 3：提示词交互                        │
│                                                         │
│  Client ──── session/prompt ───────► Agent               │
│  (sessionId + 用户消息内容块)                              │
│                                                         │
│  Agent ──── session/update ────────► Client (多次)       │
│  (计划、文本流、工具调用进度)                               │
│                                                         │
│  Agent ──── session/request_permission ► Client (可选)    │
│  (需要用户授权的工具调用)                                  │
│                                                         │
│  Client ──── session/cancel ───────► Agent (可随时取消)   │
│                                                         │
│  Agent ──── session/prompt 响应 ───► Client              │
│  ({ stopReason: "end_turn" | ... })                     │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

## 5. 初始化阶段详解

### 5.1 initialize 请求

```json
{
  "jsonrpc": "2.0",
  "id": 0,
  "method": "initialize",
  "params": {
    "protocolVersion": 1,
    "clientCapabilities": {
      "fs": {
        "readTextFile": true,
        "writeTextFile": true
      },
      "terminal": true
    },
    "clientInfo": {
      "name": "my-client",
      "title": "My Editor",
      "version": "1.0.0"
    }
  }
}
```

### 5.2 InitializeResult 响应

```json
{
  "jsonrpc": "2.0",
  "id": 0,
  "result": {
    "protocolVersion": 1,
    "agentCapabilities": {
      "loadSession": true,
      "promptCapabilities": {
        "image": true,
        "audio": true,
        "embeddedContext": true
      },
      "mcp": {
        "http": true,
        "sse": true
      }
    },
    "agentInfo": {
      "name": "my-agent",
      "title": "My Agent",
      "version": "1.0.0"
    },
    "authMethods": []
  }
}
```

### 5.3 能力字段详解

**ClientCapabilities**：

| 能力 | 说明 |
|------|------|
| `fs.readTextFile` | Client 支持代理读取文件 |
| `fs.writeTextFile` | Client 支持代理写入文件 |
| `terminal` | Client 支持所有 `terminal/*` 方法 |

**AgentCapabilities**：

| 能力 | 说明 |
|------|------|
| `loadSession` | 支持 `session/load` 恢复会话 |
| `promptCapabilities.image` | 支持在 prompt 中接收图像 |
| `promptCapabilities.audio` | 支持在 prompt 中接收音频 |
| `promptCapabilities.embeddedContext` | 支持在 prompt 中嵌入资源内容 |
| `mcp.http` | 支持通过 HTTP 连接 MCP Server |
| `mcp.sse` | 支持通过 SSE 连接 MCP Server |

> **基准要求**：所有 Agent 必须支持 `session/prompt` 中的 `ContentBlock::Text` 和 `ContentBlock::ResourceLink`。

### 5.4 版本协商规则

1. Client 发送自己支持的最新协议版本
2. Agent 若支持该版本 → 响应相同版本
3. Agent 若不支持 → 响应自己支持的最新版本
4. Client 若不支持 Agent 响应的版本 → **断开连接**并通知用户

## 6. 会话管理

### 6.1 创建新会话：`session/new`

```json
// 请求
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "session/new",
  "params": {
    "cwd": "/home/user/project",
    "mcpServers": [
      {
        "name": "filesystem",
        "command": "/path/to/mcp-server",
        "args": ["--stdio"],
        "env": [
          { "name": "API_KEY", "value": "xxx" }
        ]
      }
    ]
  }
}

// 响应
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "sessionId": "sess_abc123def456"
  }
}
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `cwd` | string | ✅ | 当前工作目录（绝对路径） |
| `mcpServers` | array | 否 | Agent 应连接的 MCP Server 列表 |

**MCP Server 配置支持三种传输类型**：

| 类型 | 配置方式 | 备注 |
|------|---------|------|
| **Stdio（默认）** | `command` + `args` | 所有 Agent 必须支持 |
| **HTTP** | `type: "http"` + `url` + `headers` | 可选，检查 `mcpCapabilities.http` |
| **SSE** | `type: "sse"` + `url` + `headers` | 可选，已被 MCP 规范弃用 |

### 6.2 恢复会话：`session/load`

前提是 Agent 在 initialize 中声明了 `loadSession: true`。

```json
// 请求
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "session/load",
  "params": {
    "sessionId": "sess_789xyz",
    "cwd": "/home/user/project"
  }
}
```

**加载流程**：

```
Client ──── session/load ──────────────────────► Agent
                                                    │
Agent ──── session/update (历史消息1) ──────────► Client
Agent ──── session/update (历史消息2) ──────────► Client
Agent ──── session/update (历史消息3) ──────────► Client
   ...                                              │
Agent ──── { result: null } ───────────────────► Client
                                                    │
   [对话恢复，可继续发送 session/prompt]              │
```

### 6.3 session/update 通知

`session/update` 是 Agent 向 Client 推送信息的核心通知，可包含：

| 更新类型 (sessionUpdate) | 说明 |
|--------------------------|------|
| `agent_message_chunk` | Agent 生成的文本内容 |
| `user_message_chunk` | 历史会话中的用户消息（加载时用） |
| `tool_call` | 工具调用请求 |
| `tool_call_update` | 工具调用状态更新（in_progress/completed） |
| `plan` | Agent 的任务分步计划 |
| `available_commands_update` | 可用命令列表变更 |
| `mode_change` | Agent 运行模式变更 |

## 7. 提示词交互轮次（Prompt Turn）

这是 ACP 最核心的交互模式。一个 Turn 从用户消息开始，到 Agent 完成响应结束。

### 7.1 完整时序图

```
Client                                    Agent
  │                                         │
  │──── session/prompt ────────────────────►│  ① 发送用户消息
  │  (文本 + 图片 + 文件引用等)               │
  │                                         │  ② LLM 推理
  │◄─── session/update (plan) ─────────────│  ③ 输出计划
  │◄─── session/update (message chunk) ────│  ③ 输出文本流
  │◄─── session/update (tool_call) ────────│  ③ 工具调用请求
  │                                         │  ④ 检查：有待处理工具
  │◄─── session/request_permission ────────│  ⑤ 请求用户确认
  │──── 授权响应 ──────────────────────────►│
  │◄─── session/update (tool in_progress) ─│  ⑤ 工具开始执行
  │◄─── session/update (tool completed) ───│  ⑤ 工具执行完成
  │                                         │  ⑥ 结果返回 LLM （回到②循环）
  │                                         │  ...
  │                                         │  ④ 检查：无待处理工具
  │◄─── session/prompt 响应 ───────────────│     返回 StopReason
  │  ({ stopReason: "end_turn" })          │
  │                                         │
```

### 7.2 session/prompt 请求

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "session/prompt",
  "params": {
    "sessionId": "sess_abc123def456",
    "prompt": [
      {
        "type": "text",
        "text": "分析这段代码的潜在问题"
      },
      {
        "type": "resource",
        "resource": {
          "uri": "file:///home/user/project/main.py",
          "mimeType": "text/x-python",
          "text": "def process_data(items):\n    for item in items:\n        print(item)"
        }
      }
    ]
  }
}
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `sessionId` | string | ✅ | 会话 ID |
| `prompt` | ContentBlock[] | ✅ | 消息内容数组，可包含文本、图像、文件等 |

**ContentBlock 类型**：

| 类型 | 说明 | 是否必支持 |
|------|------|-----------|
| `text` | 纯文本 `{ type: "text", text: "..." }` | ✅ 基准必须 |
| `resource` | 资源引用（URI + MIME + 内容） | ✅ 基准必须 |
| `image` | 图像内容 | 可选（需 `promptCapabilities.image`） |
| `audio` | 音频内容 | 可选（需 `promptCapabilities.audio`） |

### 7.3 session/prompt 响应

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "stopReason": "end_turn"
  }
}
```

### 7.4 StopReason 枚举

| 值 | 说明 |
|------|------|
| `end_turn` | LLM 不请求更多工具调用，正常完成响应 |
| `max_tokens` | 达到 Token 上限 |
| `max_turn_requests` | 超过单轮 LLM 请求次数上限 |
| `refusal` | Agent 拒绝继续 |
| `cancelled` | 被客户端通过 `session/cancel` 取消 |

### 7.5 取消机制：`session/cancel`

客户端可随时取消正在进行的轮次：

```json
{
  "jsonrpc": "2.0",
  "method": "session/cancel",
  "params": {
    "sessionId": "sess_abc123def456"
  }
}
```

| 角色 | 取消后的行为要求 |
|------|----------------|
| Client | 立即标记所有待处理的工具调用为 `cancelled` |
| Client | 用 `cancelled` 结果响应所有挂起的权限请求 |
| Agent | 尽快停止所有 LLM 请求和工具调用 |
| Agent | 捕获中止异常，返回 `cancelled` 停止原因 |

### 7.6 权限确认：`session/request_permission`

当 Agent 需要执行可能产生副作用的操作时，会先请求 Client 确认：

```
Agent ──── session/request_permission ──► Client
          { toolCallId, toolName, arguments }

Client ── 响应 (allow/deny) ────────────► Agent
```

## 8. Client 端方法（Client 暴露给 Agent）

### 8.1 文件系统操作

| 方法 | 说明 | 能力要求 |
|------|------|---------|
| `fs/read_text_file` | Agent 请求 Client 读取文件内容 | `fs.readTextFile` |
| `fs/write_text_file` | Agent 请求 Client 写入文件内容 | `fs.writeTextFile` |

> **设计理念**：ACP 中不是 Agent 直接操作文件系统，而是**Agent 请求 Client 代为操作**。这给了 Client 完全的权限控制能力——Client 可以拦截、审计或拒绝任何文件操作。

### 8.2 终端操作

| 方法 | 说明 | 能力要求 |
|------|------|---------|
| `terminal/create` | 创建新终端 | `terminal` |
| `terminal/output` | 获取终端输出和退出状态 | `terminal` |
| `terminal/wait_for_exit` | 等待终端命令退出 | `terminal` |
| `terminal/kill` | 强制终止终端命令 | `terminal` |
| `terminal/release` | 释放终端资源 | `terminal` |

> LSP 中没有终端概念，ACP 新增这一能力体现了 Coding Agent 的特殊需求——Agent 需要执行 shell 命令来运行测试、构建、安装依赖等。

## 9. 可选方法

### 9.1 session/set_mode

允许 Client 在不同操作模式间切换：

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "session/set_mode",
  "params": {
    "sessionId": "sess_abc123",
    "mode": "plan"
  }
}
```

典型模式：`craft`（直接执行）、`plan`（先规划再执行）、`ask`（仅回答问题）。

## 10. ACP 与 MCP 的关系

ACP 和 MCP **不是竞争关系，而是互补关系**。ACP 内置了 MCP 集成：

```
┌─────────────────────────────────────────────────────┐
│                    Client (编辑器)                    │
│                                                     │
│  ┌─────────────────────────────────────────────┐    │
│  │              Agent (ACP Server)               │    │
│  │                                              │    │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐  │    │
│  │  │ MCP      │  │ MCP      │  │ MCP      │  │    │
│  │  │ Client 1 │  │ Client 2 │  │ Client 3 │  │    │
│  │  └────┬─────┘  └────┬─────┘  └────┬─────┘  │    │
│  └───────┼──────────────┼──────────────┼───────┘    │
└──────────┼──────────────┼──────────────┼────────────┘
           │              │              │
     ┌─────┴─────┐  ┌─────┴─────┐  ┌─────┴─────┐
     │ 文件系统   │  │ 数据库     │  │ GitHub    │
     │ MCP Server│  │ MCP Server│  │ MCP Server│
     └───────────┘  └───────────┘  └───────────┘
```

**关系梳理**：

| 维度 | ACP | MCP |
|------|-----|-----|
| 标准化什么 | 编辑器 ↔ Agent 交互 | AI 应用 ↔ 数据源/工具 交互 |
| 谁调用谁 | Client 调用 Agent 方法；Agent 调用 Client 方法 | Host 调用 MCP Server 方法 |
| MCP 如何关联 | ACP 允许 Client 在创建会话时配置 MCP Server，Agent 内部连接它们 | MCP 是 ACP 的一个「子协议」 |
| 角色映射 | Client = 编辑器；Agent = Coding Agent | Host = AI 应用；Server = 数据源 |

> 简单说：**ACP 管「编辑器怎么和 Agent 对话」，MCP 管「Agent 怎么连外部工具」。**两者结合就构成了完整的 AI 编程体验：编辑器通过 ACP 调度 Agent，Agent 通过 MCP 获取上下文和执行工具。

## 11. 三大协议对比总览

| 维度 | LSP | MCP | ACP |
|------|-----|-----|-----|
| **发布时间** | 2016 | 2024 | 2025 |
| **提出者** | 微软 | Anthropic | JetBrains + Zed |
| **标准化什么** | 编辑器 ↔ 语言服务 | AI 应用 ↔ 数据源/工具 | 编辑器 ↔ Coding Agent |
| **Server 做什么** | 代码智能（补全、诊断） | 提供上下文/执行工具 | AI 自主编程（调用 LLM + 工具） |
| **会话概念** | 无（请求独立） | 无（请求独立） | 有（session 跨轮次） |
| **终端操作** | 无 | 无 | 有（terminal/*） |
| **文件操作** | 有（textDocument/*） | 有（但非核心） | 有（fs/*，通过 Client 代理） |
| **用户确认** | 不需要 | 需要（工具调用） | 需要（session/request_permission） |
| **取消机制** | 有（$/cancelRequest） | 无标准机制 | 有（session/cancel） |
| **MCP 集成** | 无 | 本身即 MCP | 内置 MCP Server 配置 |
| **扩展性** | 自定义方法 | 社区 Server | _ 前缀方法 + _meta 字段 |
| **传输方式** | stdio, TCP, Pipe | stdio, SSE(HTTP) | stdio, HTTP, WebSocket |
| **数据复用** | — | — | 尽可能复用 MCP 的 JSON 类型定义 |

### 三者的分层关系

```
┌──────────────────────────────────────────────────────┐
│                    用户交互层                          │
│                                                      │
│   ┌──────────┐                                       │
│   │ 编辑器     │ ← 人机交互界面                         │
│   └────┬─────┘                                       │
├────────┼──────────────────────────────────────────────┤
│   ACP  │ 标准化「编辑器 ↔ Coding Agent」交互            │
│        │ (会话管理、提示流转、权限控制、取消机制)          │
├────────┼──────────────────────────────────────────────┤
│   MCP  │ Agent 通过 MCP 连接外部数据源和工具             │
│        │ (文件系统、数据库、API、搜索引擎等)              │
├────────┼──────────────────────────────────────────────┤
│   LSP  │ Agent 通过 LSP 理解代码语义                    │
│        │ (符号表、诊断、类型信息、引用关系)               │
└────────┴──────────────────────────────────────────────┘
```

> 三个协议的分工：
> - **ACP**：编辑器与 Agent 之间的「指挥系统」
> - **MCP**：Agent 连接外部世界的「感觉器官和手」
> - **LSP**：Agent 理解代码语义的「语法分析器」

## 12. 扩展性机制

ACP 提供了标准化的扩展机制，在保持互操作性的同时支持自定义功能。

### 12.1 _meta 字段

协议中**所有类型**都包含 `_meta` 字段（`{ [key: string]: unknown }`），可用于附加自定义信息：

```json
{
  "jsonrpc": "2.0",
  "method": "session/prompt",
  "params": {
    "sessionId": "sess_abc123",
    "prompt": [{ "type": "text", "text": "Hello" }],
    "_meta": {
      "traceparent": "00-80e1...7a08-01",
      "zed.dev/debugMode": true
    }
  }
}
```

> `_meta` 中根级保留键名：`traceparent`、`tracestate`、`baggage`（用于 W3C Trace Context）。

### 12.2 扩展方法

以 `_` 开头的方法名保留给自定义扩展：

```json
// 自定义请求（包含 id，期待响应）
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "_zed.dev/workspace/buffers",
  "params": { "language": "rust" }
}

// 自定义通知（不含 id，单向）
{
  "jsonrpc": "2.0",
  "method": "_zed.dev/file_opened",
  "params": { "path": "/home/user/project/src/main.rs" }
}
```

| 行为 | 规范 |
|------|------|
| 无法识别的自定义请求 | 必须返回 Method not found 错误 (-32601) |
| 无法识别的自定义通知 | 应该静默忽略 |

### 12.3 声明自定义能力

```json
{
  "result": {
    "agentCapabilities": {
      "loadSession": true,
      "_meta": {
        "zed.dev": {
          "workspace": true,
          "fileNotifications": true
        }
      }
    }
  }
}
```

## 14. 与 AI Agent 工程的关系

### 14.1 ACP 提供了 Agent 的标准化外壳

对于构建 AI Agent 框架的开发者：

- **如果做 Agent（服务端）**：实现 ACP 协议即可对接所有支持 ACP 的编辑器，无需为每个编辑器写插件
- **如果做编辑器集成（客户端）**：实现 ACP 协议即可接入所有 ACP 兼容的 Agent

### 14.2 ACP + MCP + LSP = Agent 三件套

现代 AI Coding Agent 的完整技术栈：

```
ACP ← 编辑器如何调用 Agent
 MCP ← Agent 如何获取上下文和工具
 LSP ← Agent 如何理解代码语义
```

### 14.3 潜在应用场景

- **自研 Agent 对接多编辑器**：一次实现 ACP，兼容 VS Code、JetBrains、Zed
- **企业内部 Agent 平台**：通过 ACP 统一管理多个 Agent 实例
- **Agent 市场**：类似 LSP 让语言服务可插拔，ACP 让 Agent 可插拔

| **核心理念** | LSP for AI Agents：标准化编辑器 ↔ Agent 交互 |
| **发起组织** | JetBrains + Zed（2025） |

| **与 LSP 关系** | 继承 LSP 的 "Client-Server 标准化" 理念 |
| **扩展性** | `_meta` 字段 + `_` 前缀方法 + 能力声明 |
| **生态现状** | 新协议（2025），JetBrains 和 Zed 主导，快速增长 |
