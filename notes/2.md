## 1. 执行摘要

本文档描述了一个基于 API 级约束解码的 LLM 输出控制系统，该系统能够在文本生成过程中强制遵守 JSON Schema 规范。通过在模型推理的关键节点注入约束过滤器，系统实现了确定性结构化输出，同时保持推理性能开销在可接受范围内。

### 1.1 核心价值

- **确定性保证**：输出格式错误率为零，无需额外的校验和重试逻辑
- **低性能开销**：端到端推理延迟增加控制在 5% 以内
- **模型无关性**：支持所有主流 Transformer 架构，无需修改模型权重
- **灵活扩展性**：支持复杂 JSON Schema 特性，包括嵌套对象、数组、多选项约束

### 1.2 适用场景

- Agent 系统的结构化输出要求
- 需要可靠 JSON 格式的 API 调用
- 数据提取和信息抽取任务
- 与外部工具和系统对接的自动化流程

## 2. 系统架构概览

### 2.1 分层架构

系统采用四层架构设计，从上到下依次为：应用接口层、约束管理层、运行时执行层、LLM 推理层。各层职责明确，通过标准化的数据接口进行通信。

**应用接口层**：提供多种接入方式，包括 REST API、Python SDK、WebSocket 和 gRPC，支持不同场景的集成需求。该层负责接收用户的 Schema 定义和生成请求，并将结果返回给调用方。

**约束管理层**：核心智能层，负责将用户的 JSON Schema 编译为可执行的状态机。该层仅在初始化或 Schema 变更时工作，结果会被缓存以供后续请求复用。

**运行时执行层**：负责在每次生成步骤中追踪状态机位置、生成约束掩码，并与 LLM 推理层协调。该层是性能关键路径，需要极低的延迟。

**LLM 推理层**：封装具体的模型推理引擎，输出原始的 logits 供上层处理。该层不感知任何约束逻辑，保持模型的通用性。

### 2.2 核心数据流

整个生成过程遵循"前向传播-约束过滤-概率转换-采样决策"的循环模式。

当用户输入 Prompt 后，系统首先完成 Tokenization，将文本转换为模型可处理的数字序列。随后，LLM 执行一次前向传播，输出下一个位置的原始分数向量，即 logits。这个向量的大小等于词汇表容量，通常包含 5 万到 10 万个元素。

在模型网络外部，约束解码器根据当前状态机位置，生成一个等长的布尔掩码，标记哪些 token 在语法上是合法的。系统将该掩码应用到 logits 上，将所有非法 token 的分数设为负无穷。

接着，经过温度缩放后的 logits 通过 Softmax 函数转换为概率分布。此时，所有非法 token 的概率精确为零，合法 token 的概率重新归一化后总和为一。最后，采样器根据这个受限的概率分布选择下一个 token，状态机根据所选 token 更新到新状态，循环继续直到达到终止条件。

## 3. 核心组件详细设计

### 3.1 Schema 解析与编译

#### 3.1.1 解析阶段

系统首先将用户提供的 JSON Schema（可能是复杂的嵌套结构和约束条件）转换为内部抽象语法树。这个过程包括词法分析和语法分析两个子阶段。

解析器识别 Schema 中的类型定义，包括对象类型、数组类型、基本类型以及组合类型。对于对象类型，记录其属性集合、必填字段列表以及是否允许额外属性。对于数组类型，记录其元素类型的约束以及长度限制。对于字符串、数字、布尔值等基本类型，记录其格式约束如正则表达式、数值范围等。对于组合类型，记录其一或多个条件分支。

#### 3.1.2 编译阶段

抽象语法树被编译成确定有限自动机，这是约束解码的核心数据结构。编译过程分为三个子步骤：

**第一步：生成非确定有限自动机**。系统为每个 Schema 节点生成对应的自动机片段，并通过 epsilon 转移将它们连接起来。非确定性表现为一个状态可能有多个相同输入字符的转移目标，或者存在不需要输入就能进行的转移。

**第二步：确定化处理**。采用子集构造算法，将非确定自动机转换为确定自动机。确定化的核心思想是，将非确定自动机中可能同时存在的多个状态，视为确定自动机中的一个复合状态。这一步保证了每个状态对于每个输入都有唯一的转移目标，大大简化了运行时的处理逻辑。

**第三步：最小化优化**。通过合并等价状态，减少自动机的状态数量。两个状态等价的条件是，它们出发的所有可能输入序列都会到达相同类型的接受状态。最小化处理可以显著降低运行时的内存占用和状态追踪开销。

#### 3.1.3 预计算优化

完成自动机构建后，系统进行两项关键的预计算优化：

**Token 类型分类**：分析词汇表中所有 token 的字符串形式，将其归类为有限的类型集合，如左花括号、右花括号、双引号、冒号、逗号、数字、字符串字面量等。这个分类可以预计算并永久存储。

**状态掩码预计算**：对于自动机中的每个状态，预先计算出在该状态下所有合法的 token ID 集合，并以位掩码的形式存储。位掩码使用每个比特位代表一个 token 的合法性，将词汇表大小的布尔数组压缩为连续的内存块。对于 5 万词汇量，只需要约 6.25 KB 的存储空间。

### 3.2 运行时执行引擎

#### 3.2.1 状态追踪器

状态追踪器维护当前生成过程中自动机的位置。由于确定化处理保证了唯一转移，追踪器只需要记录一个当前状态标识符，无需维护复杂的多状态集合。

在每个 token 生成后，追踪器查询预计算的转移表，获取从当前状态经过该 token 应到达的新状态。转移表是一个二维数组，第一维是状态编号，第二维是 token ID，存储目标状态编号和合法性标志。这个查询操作的时间复杂度是常数级别。

追踪器还维护一个历史栈，记录到达当前状态所经过的状态序列。这在调试和错误恢复时非常有用，虽然正常情况下约束保证了不会出错，但作为安全机制保留。

#### 3.2.2 掩码生成器

掩码生成器的职责是根据当前状态，快速输出对应的约束掩码。由于状态掩码已经预计算，该步骤实际上只是一个内存读取操作。

系统采用了零拷贝设计，掩码生成器返回指向预计算掩码的只读引用，而不是复制数据。这避免了运行时的不必要内存分配，对性能至关重要。

掩码应用发生在 GPU 上，由专门的 CUDA 内核完成。该内核接收 logits 张量和掩码张量，并行地将每个 token 对应的 logit 值与掩码比特位进行与操作。如果掩码位为 0，对应的 logit 值被原子地替换为负无穷。这个操作完全在 GPU 上进行，不需要 CPU-GPU 数据传输。

#### 3.2.3 采样决策器

采样决策器负责在受限的概率分布上作出最终选择。它包括以下几个步骤：

**温度缩放**：用户指定的温度参数被用于调整 logits 的相对差异。温度大于一时，logits 被压缩，概率分布趋向均匀，输出更具随机性；温度小于一时，logits 被放大，高分 token 的概率更加突出，输出更确定。

**Softmax 转换**：将缩放后的 logits 转换为概率分布。这个数学函数确保输出值在零到一之间，且总和为一。由于非法 token 的 logits 已经是负无穷，其指数结果为零，自然在概率分布中消失。

**Top-p 过滤**：如果启用，采样器将概率按降序排序，累积概率达到指定阈值后，截断其余低概率 token。这能有效过滤掉长尾的不合理选择，同时保留一定随机性。

**最终采样**：从处理后的概率分布中随机抽取一个 token。采样算法使用 Gumbel-Max 技巧或其变体，保证在数学上等价于按概率分布随机选择。

### 3.3 状态机示例

以下示例展示了从简单 JSON Schema 到确定性有限自动机的完整编译过程。

#### 输入 Schema

```json
{
  "type": "object",
  "properties": {
    "name": {"type": "string"}
  }
}
```

这个 Schema 定义了一个包含单个属性 "name" 的对象，属性值必须为字符串类型。

#### 编译后的 DFA

状态机包含从初始状态到接受状态的完整路径，每个状态明确规定了下一步允许的 token 类型。

**状态 0（初始状态）**
- 接受状态：否
- 合法 token：左花括号 `{`
- 遇到左花括号后转移到状态 1

**状态 1（期待属性名或对象结束）**
- 接受状态：否
- 合法 token：双引号 `"` 或右花括号 `}`
- 遇到双引号后转移到状态 2（开始读取属性名）
- 遇到右花括号后转移到状态 8（接受状态，表示空对象）

**状态 2（正在读取属性名的字符）**
- 接受状态：否
- 合法 token：任意非双引号字符（实际为字符串字面量 "name" 的组成部分）
- 遇到属性名字符时保持在状态 2
- 当属性名读取完毕后，遇到双引号 `"` 时转移到状态 3

**状态 3（属性名结束，期待冒号）**
- 接受状态：否
- 合法 token：冒号 `:`
- 遇到冒号后转移到状态 4

**状态 4（期待属性值开始）**
- 接受状态：否
- 合法 token：双引号 `"`（因为 Schema 规定值为字符串类型）
- 遇到双引号后转移到状态 5

**状态 5（正在读取字符串值的字符）**
- 接受状态：否
- 合法 token：任意非双引号字符
- 遇到字符串内容字符时保持在状态 5
- 遇到双引号 `"`（字符串值结束）时转移到状态 6

**状态 6（属性值结束，期待对象闭合或下一个属性）**
- 接受状态：否
- 合法 token：右花括号 `}` 或逗号 `,`
- 遇到右花括号后转移到状态 7
- 遇到逗号后返回状态 1（继续处理下一个属性）

**状态 7（接受状态）**
- 接受状态：是
- 无出边转移，表示对象已正确闭合，生成可结束

**状态 8（接受状态，空对象）**
- 接受状态：是
- 无出边转移，表示空对象生成完成

#### 状态机行为说明

当系统开始生成时，处于状态 0。模型要输出下一个 token，只能从词汇表中选择左花括号。这强制了 JSON 对象的正确开始。

在状态 1，系统允许两种情况：如果模型认为对象为空，可以选择右花括号直接进入状态 8 结束；否则必须选择双引号开始属性名。

一旦进入状态 2，模型只能生成字符串 "name" 的组成 token。这些 token 可能是单个 "name" 整体，也可能是 "nam" 和 "e" 的分片，取决于 tokenizer 的实现。模型可以连续生成多个字符 token，直到遇到双引号才离开此状态。

状态 3 强制要求输出冒号，这是 JSON 语法中属性名和值之间的分隔符。

状态 4 后进入字符串值的生成：先输出双引号，然后在状态 5 中生成任意字符串内容（不包含双引号），最后再输出双引号闭合。

状态 6 提供了两种选择：如果对象只有这一个属性，输出右花括号进入接受状态；如果还有更多属性，输出逗号回到状态 1 继续处理。

整个过程从 token 到 token 都被状态机严格控制，确保了最终输出 100% 符合 JSON 语法规范。

## 4. 性能优化策略

### 4.1 编译时优化

**一次性编译，多次复用**：同一个 JSON Schema 可以被编译一次，编译结果保存在缓存中。后续使用相同 Schema 的请求直接复用编译结果，避免重复计算。缓存键基于 Schema 的标准化哈希值生成。

**状态压缩**：自动机的状态使用 32 位整数编号，状态数量通常不超过几千个。转移表使用稀疏存储格式，对于大多数状态来说，合法转移的数量远小于词汇表大小，稀疏存储可以节省大量内存。

**位掩码向量化**：预计算的位掩码以 CPU 缓存行对齐的方式存储，确保内存访问效率。掩码应用时使用单指令多数据流指令进行批量处理。

### 4.2 运行时优化

**零拷贝架构**：掩码和转移表在整个运行时过程中以只读方式使用，从不复制。多个并发请求可以安全地共享同一份编译结果，只需维护各自的状态指针。

**GPU 常驻内存**：所有编译产物和预计算掩码直接加载到 GPU 显存中，避免运行时的 CPU-GPU 数据传输。状态追踪器在 CPU 上运行，仅需要将当前状态编号传递给 GPU。

**融合内核**：约束掩码应用、温度缩放和 Softmax 可以融合成一个 CUDA 内核，减少内核启动开销和中间结果的显存读写。融合后的内核在 GPU 上一次性完成所有操作，直接输出采样所需的概率分布。

### 4.3 缓存策略

**LRU 缓存**：对于频繁使用的 Schema，系统维护最近最少使用缓存。缓存容量可以配置，默认值基于可用内存和典型 Schema 复杂度自动调整。

**部分缓存**：对于超大型 Schema，系统可以缓存子结构的编译结果。例如，复杂的用户定义类型和枚举定义可以单独编译，在多个 Schema 中共享。

## 5. 错误处理与边界情况

### 5.1 约束违反处理

虽然理论上约束解码保证不会产生非法 token，但实际部署中仍可能遇到异常情况，例如模型生成的 logits 由于数值精度问题导致所有合法 token 的概率都为零。针对这种情况，系统实现了多级降级策略。

**第一级降级：重新归一化**。系统在合法 token 集合内重新进行 Softmax，强制分配概率。

**第二级降级：回退采样**。从所有合法 token 中均匀随机选择一个，虽然可能导致语义质量下降，但保证了语法正确性。

**第三级降级：强制终止**。如果所有降级策略都失败，系统终止生成并返回现有的部分结果，同时在响应中标记截断状态。

### 5.2 无限循环保护

某些 Schema 可能导致状态机在有限状态空间内无限循环，例如允许空对象的递归定义。系统实现了以下保护机制：

**步数限制**：每个生成请求有最大步数限制，超过后强制终止。

**重复状态检测**：追踪器记录最近的状态序列，如果发现状态循环且循环内没有消费实际数据，触发中断。

**用户控制**：调用方可以通过参数设置允许的最大循环次数，默认值为 1000。

### 5.3 Schema 复杂度限制

为了保障性能，系统对 Schema 的复杂度施加了软硬限制：

**软限制**：可配置的告警阈值。当自动机状态数量超过阈值时，记录警告日志，但仍继续处理。

**硬限制**：不可逾越的上限。当状态数量超过硬限制时，直接拒绝该 Schema，返回错误信息。

典型限制值：状态数不超过 10,000 个，转移数不超过 100,000 条。绝大多数实际应用的 JSON Schema 远低于这个复杂度。

## 6. 与主流框架的集成模式

### 6.1 原生 API 集成

OpenAI、Anthropic 等云服务提供商已经在各自的 API 中内置了约束解码支持。调用方只需在请求中添加参数即可启用，无需关心底层实现细节。这种集成方式最简洁，但受限于云服务商的 Schema 支持能力和严格模式要求。

### 6.2 推理引擎插件

VLLM、llama.cpp、Hugging Face TGI 等开源推理引擎都提供了约束解码的插件机制。用户可以通过配置文法文件或直接传入 JSON Schema 来启用约束。这些实现直接集成在推理引擎的解码循环中，性能最优。

### 6.3 框架中间件

LangChain、LlamaIndex 等 Agent 框架在输出解析器层实现了约束解码。它们通常采用混合策略：优先尝试使用底层模型的原生结构化输出能力，如果不支持则降级到基于提示词的模拟方案，并在框架层面添加校验和重试逻辑。

## 7. 测试与验证方法

### 7.1 功能验证

系统通过三类测试用例验证功能正确性：

**语法正确性测试**：生成大量符合约束的输出，并用独立的 JSON Schema 校验器验证。期望错误率为零。

**边界条件测试**：测试 Schema 的各种边界情况，包括空对象、空字符串、最大最小值、嵌套深度极限等。

**组合类型测试**：验证 oneOf、anyOf、allOf 等复杂约束的正确处理，确保多分支路径都能正确导航。

### 7.2 性能基准测试

性能测试关注三个核心指标：

**延迟开销**：在相同硬件环境下，对比启用和不启用约束解码的端到端延迟。基准测试使用标准负载，包括短响应的对话场景和长响应的数据生成场景。

**吞吐量**：测量系统在并发请求下的处理能力，包括批处理场景和混部场景。

**内存消耗**：监控不同复杂度的 Schema 编译结果的内存占用，以及并发请求时的累计内存消耗。

### 7.3 压力测试

压力测试模拟极端情况，包括超大词汇表模型、超长生成、超复杂 Schema 等。测试目的是发现系统在极限条件下的瓶颈和退化行为，为容量规划提供依据。

## 8. 限制与最佳实践

### 8.1 已知限制

**与函数调用的互斥性**：当前主流模型 API 不允许在同一请求中同时使用约束输出和函数调用。如果需要两者，必须拆分为多个请求或在 Agent 层面进行编排。

**严格模式的硬性要求**：使用最可靠的严格模式时，Schema 必须满足特定条件，包括所有字段都必须在 required 数组中列出，必须显式设置 additionalProperties 为 false，不能使用 patternProperties 等 JSON Schema 扩展特性。

**数值校验的局限性**：严格模式下，像 minimum、maximum、maxLength 等约束关键字不会在生成时强制执行。模型可能生成不符合这些校验规则的数值或字符串，需要应用层进行二次校验。

### 8.2 最佳实践

**Schema 设计原则**：尽量保持 Schema 扁平化，避免过深的嵌套。对于大对象优先拆分为多个小的子对象使用引用。合理使用 required 字段，明确哪些字段绝对不能缺失。

**性能调优建议**：对于固定的 Schema，可以在应用启动时预编译并缓存。对于需要高吞吐量的场景，增加批处理大小可以摊销编译和内核启动开销。在延迟敏感的场景，可以适当提高温度参数以减少采样等待时间。

**降级策略配置**：根据应用对可靠性和语义质量的不同要求，配置不同的降级策略。金融和医疗等严肃应用可能更倾向于强制终止，而内容生成场景可能更接受降级回退。
