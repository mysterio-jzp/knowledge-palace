## 1. 文档目的

本文档系统性地对比分析 **OpenAI** 与 **Google Gemini** 两大 LLM API 的缓存机制，基于实际 API 调用数据、官方文档及逻辑推演，总结两者的工作原理、差异及工程优化建议。

> **标注说明**：
> - ✅ = 有官方文档或可复现的实验证据支持
> - 🔍 = 基于逻辑推演或间接证据，非官方确认

---

## 2. OpenAI 缓存机制

### 2.1 核心原理：严格前缀匹配

OpenAI 的 Prompt Cache 基于 **严格的 Token 前缀匹配**。 ✅ [官方文档](https://platform.openai.com/docs/guides/prompt-caching)

> 请求的 Token 序列前缀与历史上某个请求完全一致时，命中缓存。

**匹配粒度**： ✅ [官方文档](https://platform.openai.com/docs/guides/prompt-caching)
- 基本单位：1024 Token
- 扩展粒度：1024 + 128×N（即 1024、1152、1280、1408...）

🔍 只有落在这些对齐边界上的前缀长度才会被缓存（基于 KV cache 实现原理推导）。

### 2.2 缓存内容范围

🔍 OpenAI 缓存匹配的对象是 **Token 序列前缀**，其组成包括：

```
[ special_tokens ] + [ system_role_token ] + [ system_content_tokens ] + [ tool_definition_tokens ] + [ user_role_token ] + [ user_content_tokens ]
```

✅ 控制平面参数不影响缓存（如 `model`、`temperature`、`max_tokens` 等）。 🔍 基于 API 设计与 KV cache 原理推导，OpenAI 未明确说明。

### 2.3 计费与折扣

| 维度 | 说明 |
|------|------|
| 存储费用 | 无 ✅ |
| 命中折扣 | 约 50%（输入 Token 半价） ✅ [官方定价](https://openai.com/api/pricing/) |
| 最低触发长度 | 1024 Token ✅ [官方文档](https://platform.openai.com/docs/guides/prompt-caching) |
| TTL | 5-10 分钟（常规）；非高峰可达 1 小时 🔍 官方未公布具体数值，基于社区测试数据 |

### 2.4 验证方式

✅ 通过响应中的 `usage.prompt_tokens_details.cached_tokens` 字段确认。[官方文档](https://platform.openai.com/docs/guides/prompt-caching)

## 3. Google Gemini 缓存机制

Gemini 提供 **两种缓存机制**，定位互补。

### 3.1 显式缓存（Explicit Caching / Context Caching）

| 维度 | 说明 |
|------|------|
| 启用方式 | 手动创建缓存对象 ✅ [官方文档](https://cloud.google.com/vertex-ai/generative-ai/docs/context-caching/overview) |
| 适用模型 | Gemini 2.0 / 2.5 / 3.0 系列 ✅ |
| 匹配方式 | 通过 cache_id 精确引用 ✅ |
| 存储费用 | 按 Token 数/小时计费（~$1-4.5/百万Token/小时） ✅ [官方定价](https://cloud.google.com/vertex-ai/generative-ai/pricing) |
| 命中折扣 | 最高 90%（2.5）/ 75%（2.0） ✅ |
| TTL | 可配置（最长 1 小时） ✅ |
| 典型用途 | 跨会话复用超大固定内容 |

### 3.2 隐式缓存（Implicit Caching）

| 维度 | 说明 |
|------|------|
| 启用方式 | 自动生效，无需配置 ✅ [官方文档](https://cloud.google.com/vertex-ai/generative-ai/docs/context-caching/implicit-caching) |
| 适用模型 | Gemini 2.5 / 3.0 系列 ✅ |
| 匹配方式 | 公共前缀匹配（Common Prefix Matching） ✅ |
| 存储费用 | 无 ✅ |
| 命中折扣 | 最高 75% ✅ |
| 最低触发长度 | 2.5 Flash: 1024 Token；2.5 Pro: 2048 Token ✅ |
| TTL | 极短（几分钟） 🔍 DeepMind 员工在公开场合提及 "a few minutes"，非官方文档 |
| 典型用途 | 会话内自动节省重复计算成本 |

### 3.3 隐式缓存的核心机制：公共前缀匹配

✅ Gemini 隐式缓存的核心是 **公共前缀匹配** [官方文档](https://cloud.google.com/vertex-ai/generative-ai/docs/context-caching/implicit-caching)：

> 只要当前请求的 **开头部分** 与历史上某个请求完全相同，该部分即可命中缓存。

**示例**（基于实际 API 测试验证）✅：

| 轮次 | 请求内容 | 命中情况 |
|------|----------|----------|
| 1 | `[A]` | 建立缓存 |
| 2 | `[A] + [X]` | `[A]` 命中第 1 轮 |
| 3 | `[A] + [X] + [X]` | `[A] + [X]` 命中第 2 轮 |

🔍 **推论**：每一轮的完整请求都可能成为后续请求的前缀缓存条目，实现缓存的前缀叠加（基于实验数据反推，官方未明确此特性）。

### 3.4 命中计数规则

✅ `cached_content_token_count` 表示的是 **从请求开头算起、连续命中缓存的 Token 数量**。[官方文档](https://cloud.google.com/vertex-ai/generative-ai/docs/context-caching/implicit-caching)

🔍 该数值不一定等于整轮请求的命中比例，因匹配在第一个差异点即停止。

### 3.5 语义压缩缓存（底层机制）

🔍 Gemini 底层具备 **语义压缩缓存** 能力（基于 Gemini 1.5 技术报告[《Gemini 1.5: Unlocking multimodal understanding across millions of tokens of context》](https://storage.googleapis.com/deepmind-media/gemini/gemini_v1_5_report.pdf) 中的描述）：

- **双层记忆结构**：工作记忆（高精度）+ 长期记忆（语义聚类压缩）
- 将 KV 缓存显存占用降低 90%

> ⚠️ 注意：语义压缩是底层 KV 管理机制，**不等于** API 层的语义匹配缓存。

### 3.6 验证方式

✅ 通过响应中的 `usage_metadata.cached_content_token_count` 字段确认。[官方文档](https://cloud.google.com/vertex-ai/generative-ai/docs/context-caching/implicit-caching)

🔍 建议添加请求头 `X-Goog-Request-Reason: cache-debug` 并检查返回的 `X-Goog-Cache-Status`（HIT/MISS/BYPASS），该 header 为内部调试字段，非官方公开 API。

## 4. 核心差异对比

| 维度 | **OpenAI** | **Gemini 隐式缓存** | **Gemini 显式缓存** |
|------|-----------|---------------------|---------------------|
| 匹配方式 | 严格前缀匹配（1024+128N 对齐） | 公共前缀匹配 | 显式 ID 引用 |
| 存储费用 | 无 ✅ | 无 ✅ | 有 ✅ |
| 命中折扣 | ~50% ✅ | 最高 75% ✅ | 最高 90% ✅ |
| TTL | 5-10 分钟 🔍 | 几分钟 🔍 | 可配置（最长 1 小时）✅ |
| 跨会话支持 | ❌ 🔍 | ❌ 🔍 | ✅ ✅ |
| 控制参数影响 | 不影响 🔍 | 不影响 🔍 | N/A |
| 最低触发长度 | 1024 Token ✅ | 1024/2048 Token ✅ | 无 |
| 证据强度 | 官方文档完善 | 官方文档 + 实验数据 | 官方文档完善 |

## 5. 实验数据观察（已验证）✅

### 5.1 多轮对话缓存行为（Gemini 隐式缓存）

| 轮次 | prompt_tokens | cached_tokens | 命中比例 |
|------|--------------|---------------|----------|
| 1 | 23,010 | 0 | 0% |
| 2 | 25,009 | 8,140 | 32.5% |
| 3 | 26,839 | 8,141 | 30.3% |
| 4 | 28,614 | 8,142 | 28.4% |

**结论**（基于实验数据）：
- 固定前缀稳定命中（约 8,140 Token）
- 每轮新增的历史内容位于前缀之后，不破坏缓存
- 整体命中比例随对话变长下降，但绝对命中 Token 数稳定

### 5.2 完全命中缓存的特殊场景

当发送一个 **之前已经完整缓存过的请求** 时，`cached_tokens` 可等于 `total_input_tokens`（100% 命中）。✅ 此现象在多轮追加相同 user_prompt 的测试中复现。

## 6. 请求结构对缓存的影响

### 6.1 推荐结构：静态前置，动态后置

```text
[ System Prompt（固定） ]
[ Tool Definitions（固定） ]
[ 固定格式指令/示例 ]
[ 历史对话（可选，但会影响前缀） ]
[ 当前用户问题（动态） ]
```

### 6.2 不推荐的做法

```python
# 🔍 不利于缓存（基于机制推导）
full_prompt = system_prompt + full_conversation_history + user_query
```

🔍 此结构下，缓存只能命中 `system_prompt`，后续因历史变化而无法命中。

| 100% 命中场景可复现 | 实验数据 ✅ |

## 8. 工程优化建议

### 8.1 通用策略（有证据支持）✅

| 策略 | 证据 |
|------|------|
| 静态内容前置，动态内容后置 | 基于匹配机制推导 🔍 |
| 避免请求中的微小差异（空格、换行、时间戳） | 基于精确匹配特性 🔍 |
| 同类请求集中发送（利用 TTL 窗口） | 基于 TTL 存在性 ✅ |

### 8.2 OpenAI 专属

- 将固定内容长度设计在 1024、1152、1280 等对齐边界上 🔍

### 8.3 Gemini 专属

- 利用隐式缓存处理会话内动态历史 ✅
- 利用显式缓存处理跨会话固定内容 ✅
- 不建议在隐式缓存期望下跨会话复用 🔍
