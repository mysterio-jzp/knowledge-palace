## 1. 背景：编辑器碎片化问题

### 1.1 在 LSP 出现之前

假设市面上有 **M** 种编程语言（Python、Go、Rust、TypeScript...）和 **N** 种编辑器/IDE（VS Code、Vim、Emacs、Sublime Text、JetBrains...）。每个编辑器想要支持每种语言的智能功能（自动补全、跳转定义、错误提示等），都需要为每种语言单独实现一套逻辑。

这就是经典的 **M × N 问题**：

```
语言数量 M = 10，编辑器数量 N = 5
需要的实现数量 = 10 × 5 = 50 套
```

每种语言在每种编辑器中都要重复实现解析器、类型检查器、自动补全引擎等。这显然是巨大的工程浪费。

### 1.2 LSP 的解决方案

LSP 的核心思想来自 **编译器前端/后端分离** 的经典设计：将「理解代码」这件事从编辑器中剥离出来，交给一个独立运行的 **语言服务器（Language Server）**。

```
┌──────────────┐     LSP (JSON-RPC)     ┌──────────────┐
│               │ ◄──────────────────►  │               │
│  Editor/IDE   │                        │   Language    │
│  (Client)     │                        │   Server      │
│               │                        │               │
└──────────────┘                        └──────────────┘
```

这样，每种语言只需实现一个 Language Server，所有支持 LSP 的编辑器都能复用：

```
语言数量 M = 10，编辑器数量 N = 5
需要的实现数量 = 10（Server）+ 5（Client 适配） = 15 套
```

## 2. 核心概念

### 2.1 三个角色

| 角色 | 说明 | 例子 |
|------|------|------|
| **Language Server** | 理解某种编程语言的独立进程，提供代码智能服务 | `gopls`（Go）、`rust-analyzer`（Rust）、`pyright`（Python） |
| **Language Client** | 嵌入在编辑器/IDE 中的插件，负责与 Server 通信并展示结果 | VS Code 的 LSP 扩展框架、Neovim 的 `nvim-lspconfig` |
| **Protocol** | Client 与 Server 之间的通信约定，基于 JSON-RPC 2.0 | 由微软定义和维护的规范 |

### 2.2 通信方式

LSP 使用 **JSON-RPC 2.0** 作为消息格式，支持三种传输方式：

- **Stdio**（标准输入/输出）：最常用，Server 作为子进程启动，通过 stdin/stdout 通信。简单可靠，无需网络配置。
- **TCP Socket**：通过网络端口通信，适合远程开发场景。
- **Pipe**（命名管道）：Windows 上常用。

## 3. 协议细节

### 3.1 JSON-RPC 2.0 消息结构

LSP 中的每一条消息都是一个 JSON-RPC 2.0 消息，分为四种类型：

**Request（请求）** — 期待回复：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "textDocument/completion",
  "params": {
    "textDocument": { "uri": "file:///path/to/file.go" },
    "position": { "line": 10, "character": 15 }
  }
}
```

**Response（响应）** — 对请求的回复：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": { }
}
```

**Notification（通知）** — 无需回复：

```json
{
  "jsonrpc": "2.0",
  "method": "textDocument/didOpen",
  "params": {
    "textDocument": {
      "uri": "file:///path/to/file.go",
      "languageId": "go",
      "version": 1,
      "text": "package main\n\n..."
    }
  }
}
```

**Error（错误响应）**：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32601,
    "message": "Method not found"
  }
}
```

### 3.2 关键设计原则

- **无状态 vs 有状态**：Server 是有状态的——它会在内存中维护已打开文档的抽象语法树（AST）、符号表等。但协议层面不要求 Server 持久化这些状态。
- **异步通信**：Client 和 Server 之间的消息是异步的。Client 可以连续发送多个请求而不等前一个返回。
- **Server 推送**：Server 可以主动向 Client 推送诊断信息（错误/警告），无需 Client 轮询。
- **取消机制**：通过 `$/cancelRequest` 通知取消仍在处理的请求（当用户在快速输入时，旧的补全请求可以被取消）。

## 4. 生命周期

LSP 连接有严格的生命周期阶段：

```
初始化 → 运行 → 关闭
```

### 4.1 初始化握手

```
Client                                Server
  │                                      │
  │──── initialize ────────────────────► │  (客户端能力 + 工作区根路径)
  │                                      │
  │ ◄─── InitializeResult ───────────── │  (服务端能力)
  │                                      │
  │──── initialized (notification) ────► │  (握手完成，可以开始正常通信)
  │                                      │
```

`initialize` 请求中，Client 声明自己能处理哪些功能（如 `completion`、`hover`、`definition` 等），Server 响应自己能提供哪些能力。双方取交集作为后续可用的功能。

### 4.2 运行阶段

初始化完成后进入运行阶段。主要活动包括：

- **文档同步**：Client 通知 Server 文档的打开、修改、关闭
- **请求响应**：Client 发送功能请求（补全、跳转等），Server 返回结果
- **诊断推送**：Server 主动推送错误和警告

### 4.3 关闭

```
Client ──── shutdown ────────► Server  (Server 停止服务，但进程仍存活)
Client ◄──── result ────────── Server
Client ──── exit (notification) ► Server  (Server 进程终止)
```

## 5. 核心能力详解

### 5.1 文档同步

文档同步是所有功能的基础。有三种同步模式：

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| **Full** | 每次变更发送整个文档内容 | 简单实现，小文件 |
| **Incremental** | 只发送变更的 diff（TextDocumentContentChangeEvent） | 大文件，高效 |
| **None** | Server 只跟踪打开/关闭，不关心内容 | Server 不需要实时分析时 |

**关键通知**：

- `textDocument/didOpen` — 文档被打开
- `textDocument/didChange` — 文档内容变更
- `textDocument/didClose` — 文档被关闭
- `textDocument/didSave` — 文档被保存

### 5.2 诊断（Diagnostics）

Server 分析代码后，主动通过 `textDocument/publishDiagnostics` 通知将诊断结果推送给 Client。

```json
{
  "uri": "file:///path/to/main.go",
  "diagnostics": [
    {
      "range": {
        "start": { "line": 10, "character": 4 },
        "end":   { "line": 10, "character": 8 }
      },
      "severity": 1,
      "code": "unused-var",
      "source": "gopls",
      "message": "variable 'foo' is declared but not used"
    }
  ]
}
```

- `severity`：1 = Error、2 = Warning、3 = Info、4 = Hint

### 5.3 代码补全（Completion）

用户输入时，Client 发送补全请求，Server 返回候选列表。

**触发方式**：

- **手动触发**：用户按 Ctrl+Space
- **自动触发**：输入特定字符（如 `.`、`->`）时自动弹出

**补全项结构**：

```json
{
  "label": "fmt.Println",
  "kind": 3,
  "detail": "func Println(a ...any) (n int, err error)",
  "documentation": "Println formats using the default formats...",
  "insertText": "Println(${1:args})",
  "insertTextFormat": 2
}
```

- `kind`：`CompletionItemKind` 枚举，定义了 ~25 种补全类型
- `insertTextFormat = 2`：表示支持 Snippet 语法（占位符 `${1:...}`）

`CompletionItemKind` 枚举完整列表：

| 值 | 名称 | 说明 |
|----|------|------|
| 1 | Text | 纯文本 |
| 2 | Method | 方法 |
| 3 | Function | 函数 |
| 4 | Constructor | 构造函数 |
| 5 | Field | 字段 |
| 6 | Variable | 变量 |
| 7 | Class | 类 |
| 8 | Interface | 接口 |
| 9 | Module | 模块 |
| 10 | Property | 属性 |
| 11 | Unit | 单元 |
| 12 | Value | 值 |
| 13 | Enum | 枚举 |
| 14 | Keyword | 关键字 |
| 15 | Snippet | 代码片段 |
| 16 | Color | 颜色 |
| 17 | File | 文件 |
| 18 | Reference | 引用 |
| 19 | Folder | 文件夹 |
| 20 | EnumMember | 枚举成员 |
| 21 | Constant | 常量 |
| 22 | Struct | 结构体 |
| 23 | Event | 事件 |
| 24 | Operator | 操作符 |
| 25 | TypeParameter | 类型参数 |

### 5.4 悬停提示（Hover）

光标悬停在符号上时，Server 返回类型信息和文档注释。

```json
// 请求
{ "method": "textDocument/hover", "params": {
    "textDocument": {"uri": "file:///main.go"},
    "position": {"line": 5, "character": 10}
}}

// 响应
{
  "contents": {
    "kind": "markdown",
    "value": "```go\nfunc fmt.Println(a ...interface{}) (n int, err error)\n```\n\n---\n\nPrintln writes to standard output..."
  },
  "range": { }
}
```

### 5.5 跳转定义（Go to Definition）

```json
// 请求
{ "method": "textDocument/definition", "params": {
    "textDocument": {"uri": "file:///main.go"},
    "position": {"line": 5, "character": 10}
}}

// 响应：可以返回单个或多个 Location
{
  "uri": "file:///path/to/fmt/print.go",
  "range": {
    "start": {"line": 254, "character": 5},
    "end":   {"line": 261, "character": 1}
  }
}
```

类似的跳转能力：

- `textDocument/declaration` — 跳转到声明
- `textDocument/typeDefinition` — 跳转到类型定义
- `textDocument/implementation` — 跳转到接口实现
- `textDocument/references` — 查找所有引用

### 5.6 代码重构

| 方法 | 说明 |
|------|------|
| `textDocument/rename` | 重命名符号（全局替换所有引用） |
| `textDocument/formatting` | 格式化整个文档 |
| `textDocument/rangeFormatting` | 格式化选中范围 |
| `textDocument/codeAction` | 代码操作（快速修复、自动导入等） |
| `workspace/executeCommand` | 执行自定义命令（如 `goimports`） |

**CodeAction 示例**：当出现「未使用的变量」诊断时，Server 可以返回一个「移除该变量」的快速修复。

### 5.7 其他重要能力

| 类别 | 方法 | 说明 |
|------|------|------|
| 文档链接 | `textDocument/documentLink` | 识别文档中的 URL，支持 Ctrl+Click 打开 |
| 代码高亮 | `textDocument/documentHighlight` | 高亮当前符号的所有出现位置 |
| 折叠区域 | `textDocument/foldingRange` | 提供可折叠的代码块范围 |
| 签名帮助 | `textDocument/signatureHelp` | 函数调用时显示参数签名提示 |
| 代码透镜 | `textDocument/codeLens` | 在代码行上方显示可操作提示（如引用计数、运行测试按钮） |
| 语义标记 | `textDocument/semanticTokens` | 提供更精细的语法高亮（比正则匹配更准确） |
| 链接编辑 | `textDocument/linkedEditingRange` | 同时编辑配对的标签（如 HTML 开闭标签） |
| 内联提示 | `textDocument/inlayHint` | 在代码中内嵌显示类型推断、参数名等提示 |

### 5.8 工作区能力

除了针对单个文档的操作，LSP 还支持工作区级别的功能：

| 方法 | 说明 |
|------|------|
| `workspace/symbol` | 工作区符号搜索（模糊匹配，类似 Ctrl+T） |
| `workspace/didChangeWatchedFiles` | 文件系统变更通知 |
| `workspace/didChangeConfiguration` | 配置变更通知 |

## 6. 关键数据结构

### 6.1 Position（位置）

```typescript
interface Position {
  line: number;      // 从 0 开始的行号
  character: number; // 从 0 开始的列号（UTF-16 编码偏移）
}
```

> **重要**：`character` 使用 UTF-16 编码偏移，而非 Unicode 码点或字节偏移。
> 这意味着一个 Emoji 字符（如 👨‍👩‍👧‍👦）可能占用多个 character 单位。

### 6.2 Range（范围）

```typescript
interface Range {
  start: Position;  // 起始位置（包含）
  end: Position;    // 结束位置（不包含）
}
```

### 6.3 Location（位置信息）

```typescript
interface Location {
  uri: string;    // 文档 URI，如 "file:///path/to/file.go"
  range: Range;   // 在文档中的范围
}
```

### 6.4 TextEdit（文本编辑）

```typescript
interface TextEdit {
  range: Range;      // 要替换的范围
  newText: string;   // 新文本内容
}
```

### 6.5 TextDocumentIdentifier（文档标识符）

```typescript
interface TextDocumentIdentifier {
  uri: string;   // 文档的 URI，必须是 file:// 或 untitled: 等 scheme
}
```

### 6.6 Diagnostic（诊断信息）

```typescript
interface Diagnostic {
  range: Range;
  severity?: DiagnosticSeverity;   // 1=Error, 2=Warning, 3=Info, 4=Hint
  code?: number | string;
  source?: string;                  // 来源标识，如 "gopls", "pyright"
  message: string;
  tags?: DiagnosticTag[];          // 1=Unnecessary, 2=Deprecated
  relatedInformation?: DiagnosticRelatedInformation[];
  data?: unknown;                  // 用于 codeAction 时的上下文传递
}
```

## 8. LSP 与 AI/Agent 的关系

作为一个主要关注 AI Agent 方向的学习者，这部分尤为重要。

### 8.1 LSP 为 AI 编码助手提供代码理解能力

现代的 AI 编码助手（GitHub Copilot、Cursor、Claude Code、Cody 等）在做代码生成和修改时，严重依赖 LSP 提供上下文信息：

- **获取当前文件的符号表**：知道有哪些函数、类型、变量，才能生成一致的代码
- **获取诊断信息**：发现当前代码的错误，帮助 AI 更准确地定位和修复问题
- **获取引用关系**：修改一个函数时，知道哪些地方调用了它，避免破坏性修改
- **获取类型信息**：生成代码时保持类型一致

### 8.2 Claude Code 中的 LSP

Claude Code 使用了 LSP 来增强代码理解能力。在 `settings.json` 中可以配置 LSP 集成：

```json
{
  "lsp": {
    "servers": {
      "gopls": {
        "command": "gopls",
        "args": ["-mode=stdio"]
      }
    }
  }
}
```

这使得 Claude Code 在修改代码时，能够像人类开发者一样感知到代码的语义信息，而不仅仅是文本。

### 8.3 作为协议思想的参考

LSP 的设计思想对 AI Agent 工程有重要借鉴意义：

| LSP 思想 | Agent 类比 |
|----------|------------|
| Client-Server 分离 | Agent 框架中 tool/runtime 和执行环境的分离 |
| JSON-RPC 通信 | MCP (Model Context Protocol) 也基于 JSON-RPC，受 LSP 直接影响 |
| 能力协商（Capability Negotiation） | Agent 与 Tool 之间的能力注册与匹配 |
| 异步推送诊断 | Agent 执行任务时的实时状态推送 |
| 无状态的协议 + 有状态的 Server | Agent 会话管理策略 |

> **MCP (Model Context Protocol)** 是 Anthropic 推出的 AI 协议，其设计直接借鉴了 LSP。MCP 将 LSP 的「编辑器 ↔ 语言服务器」模式迁移到「AI 应用 ↔ 上下文服务器」模式。理解 LSP 是理解 MCP 的绝佳前置知识。

## 9. LSP 扩展与变体

### 9.1 DAP (Debug Adapter Protocol)

LSP 的成功催生了相同理念的 **调试适配器协议（DAP）**，用于统一编辑器和调试器之间的通信：

```
LSP: 编辑器 ↔ 语言服务器  →  代码智能
DAP: 编辑器 ↔ 调试适配器  →  断点调试
```

### 9.2 LSP 3.17+ 新特性

- **Type Hierarchy**：显示类型的继承层次结构
- **Inline Values**：调试时在代码旁显示变量值
- **Inline Completion**：内联补全（逐词补全，而非整项补全）
- **Diagnostic Pull Model**：除了 Server 推送，Client 也可以主动拉取诊断
- **Notebook Support**：支持 Jupyter Notebook 等交互式文档

### 9.3 LSIF (Language Server Index Format)

LSIF 是一种将 LSP 的交互式查询结果「固化」为静态索引文件的格式，用于代码托管平台的代码导航。GitHub、GitLab 等用它来在 Web 界面上提供「跳转定义」功能，而不需要运行 Language Server。

## 10. 动手实践建议

理解 LSP 最好的方式是亲自跑一个 Language Server 并观察通信过程：

```bash
# 1. 安装一个 Language Server（以 gopls 为例）
go install golang.org/x/tools/gopls@latest

# 2. 手动启动并观察 JSON-RPC 通信
# 在终端中启动 gopls（stdin/stdout 模式）
echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{
  "processId":null,
  "rootUri":"file:///tmp/test",
  "capabilities":{}
}}' | gopls -mode=stdio

# 3. 你会看到 Server 返回的 InitializeResult
```

> 也可以用 `lsp-devtools` 或 VS Code 的 "LSP Inspector" 功能来可视化监控 LSP 消息。

| **传输方式** | Stdio（最常用）、TCP、Pipe |
| **核心能力** | 补全、诊断、跳转定义、悬停提示、重构、格式化等 |
| **与你学习方向的关系** | MCP 直接继承 LSP 思想；AI 编码工具深度依赖 LSP |
