## 0. 从一个具体场景出发

AI Agent 生成了一段 Python 代码，需要在你服务器上执行：

```python
import requests

# 正常的：下载一个公开数据集
data = requests.get("https://pypi.org/simple/requests/")

# 危险的：扫描内网
requests.get("http://192.168.1.1/admin")
requests.get("http://10.0.0.5/internal-api")
```

你不能信任这段代码。它应该能访问外网（下载依赖包），但绝对不能碰内网。怎么办？

---

## 1. 第一层：网络命名空间 — "造一个盒子"

### 1.1 它到底干什么

计算机启动后，所有进程共享同一套网络环境：

```
┌──────────────────────────────────────┐
│          全局网络栈                    │
│                                      │
│  网卡：eth0 (192.168.1.10)            │
│  路由：default via 192.168.1.1        │
│  连接：500 个 TCP 连接                │
│  ┌────────┐  ┌────────┐  ┌────────┐  │
│  │ 进程 A  │  │ 进程 B  │  │ 进程 C  │  │
│  └────────┘  └────────┘  └────────┘  │
│   ↑ 都能看到 eth0、所有连接、所有端口  │
└──────────────────────────────────────┘
```

**网络命名空间（netns）** 给进程单独造一个盒子，盒子里有自己的一套网络"世界"：

```
┌──────────────────┐  ┌──────────────────┐
│  全局 netns       │  │ 沙箱 netns        │
│                  │  │                  │
│  eth0 ✓          │  │  lo ✓            │
│  路由表 ✓        │  │  路由表：空       │
│  所有连接 ✓      │  │  连接：0 条       │
│  ┌────────┐      │  │  ┌────────┐      │
│  │ 进程 A  │      │  │  │沙箱进程 │      │
│  └────────┘      │  │  └────────┘      │
└──────────────────┘  └──────────────────┘
```

盒子里默认只有 `lo`（127.0.0.1），没有 eth0、没有路由、不知道怎么出外网。**进程被关在里面了。**

### 1.2 用实际操作理解

```bash
# 创建一个新的网络命名空间
ip netns add sandbox

# 在里面跑个命令看看
ip netns exec sandbox ip addr
# 输出：
# 1: lo: <LOOPBACK> mtu 65536 ...
#     inet 127.0.0.1/8 scope host lo
#     （只有 lo，没有 eth0！）

ip netns exec sandbox ping 8.8.8.8
# connect: Network is unreachable
# （没有网卡、没有路由，完全出不去）

ip netns exec sandbox curl https://www.baidu.com
# Could not resolve host: www.baidu.com
# （DNS 也走不通）
```

**这就是网络命名空间的核心作用：把进程装进一个网络真空的盒子里。默认情况下，它哪里都去不了。**

### 1.3 但是…我们的代码需要网络啊

回到场景：Agent 代码要 `pip install`，得连 pypi.org。完全没网不行。

第一层 netns 解决了"全断"的问题，但没解决"部分通"的问题。需要第二层。

## 2. 第二层：nftables 防火墙 — "在盒子上开个受控的洞"

### 2.1 先用 veth pair 把盒子接上网

veth pair 是一对虚拟网卡，像一根网线的两端，一端插盒子外（宿主机），一端插盒子里（sandbox netns）：

```bash
# 创建一根"虚拟网线"
ip link add veth_h type veth peer name veth_j

# 把 veth_j 端插进盒子
ip link set veth_j netns sandbox

# 给两端配 IP
ip addr add 10.200.0.1/30 dev veth_h       # 盒子外的端点
ip netns exec sandbox ip addr add 10.200.0.2/30 dev veth_j  # 盒子内的端点
ip link set veth_h up
ip netns exec sandbox ip link set veth_j up

# 盒子内加路由：所有流量走 veth_j → 盒子外
ip netns exec sandbox ip route add default via 10.200.0.1

# 盒子外开启转发 + NAT
sysctl -w net.ipv4.ip_forward=1
iptables -t nat -A POSTROUTING -s 10.200.0.0/30 -j MASQUERADE
```

现在的拓扑：

```
sandbox netns（盒子内）          宿主机 netns（盒子外）
┌─────────────────────┐         ┌──────────────────────┐
│                     │         │                      │
│  10.200.0.2         │         │  10.200.0.1           │
│  veth_j ─────────────veth pair──────── veth_h         │
│                     │         │         │             │
│  路由：              │         │  MASQUERADE          │
│  default via        │         │  (SNAT: 盒子IP        │
│  10.200.0.1         │         │   改写为宿主机IP)      │
│                     │         │         │             │
│                     │         │         ▼             │
│                     │         │       eth0 → 外网     │
└─────────────────────┘         └──────────────────────┘
```

**现在盒子里能上网了！** 但问题又回来了——什么都能访问，包括内网。

### 2.2 nftables：控制"谁、去哪里、走什么端口"

nftables 是 Linux 防火墙，在 veth 接口上设置规则，**在盒子内的流量出来之前就拦截**：

```bash
# 在 sandbox netns 内设置防火墙规则
ip netns exec sandbox nft add table inet filter
ip netns exec sandbox nft add chain inet filter output \
    '{ type filter hook output priority 0; policy drop; }'  # 默认：全部拒绝

# 规则 1：允许已建立连接的回包（TCP 握手需要）
ip netns exec sandbox nft add rule inet filter output \
    ct state established,related accept

# 规则 2：允许 DNS（解析域名需要）
ip netns exec sandbox nft add rule inet filter output \
    udp dport 53 accept
ip netns exec sandbox nft add rule inet filter output \
    tcp dport 53 accept

# 规则 3：只允许去代理端口的流量（8888）
ip netns exec sandbox nft add rule inet filter output \
    oif veth_j tcp dport 8888 accept

# 其他所有流量 → 默认 DROP
```

规则效果图：

```
沙箱内进程请求：curl https://192.168.1.1/admin
    │
    ▼
nftables 检查：
  ├── DNS? → UDP 53 → ACCEPT ✓
  ├── 代理端口? → TCP 8888 → ACCEPT ✓
  └── 直连 192.168.1.1:443? → 不在白名单 → DROP ✗

沙箱内进程请求：curl https://pypi.org → 通过代理
    │
    ▼
nftables 检查：
  └── 代理端口? → TCP 10.200.0.1:8888 → ACCEPT ✓ → 进入代理
```

**nftables 给了精确到 IP+端口级别的控制。** 但它认不出"这个 TCP 连接到 pypi.org 是 OK 的，但到 evil.com 不行"——因为 `:443` 端口都一样。这就引入第三层。

## 3. 第三层：HTTP 代理 — "检查你到底在访问什么"

### 3.1 nftables 的盲区

nftables 工作在 OSI 第 3/4 层（IP + 端口），同一个 `:443` 端口上跑着无数不同的域名，nftables 分不出来：

```
TCP 连接到 151.101.1.1:443  → nftables：✅ 在白名单
  ├── 可能是 pypi.org（要允许）    ← 同一个 IP:端口
  ├── 可能是 evil.com（要拦截）     ← 同一个 IP:端口
  └── 可能是内网反向代理（要害）    ← 同一个 IP:端口
```

**nftables 只看到了 IP+端口，看不到域名。**

### 3.2 HTTP 代理的工作原理

代理工作在应用层（第 7 层），能读懂 HTTP 协议——知道你在访问什么域名、什么 URL：

```
沙箱代码：requests.get("https://evil.com/malware")
    │
    ▼
nftables: TCP → 10.200.0.1:8888 → ACCEPT（放行到代理）
    │
    ▼
HTTP 代理（运行在宿主机 netns）：
    收到 HTTPS CONNECT evil.com:443
    │
    ├── evil.com 在黑名单？ → 不在黑名单
    ├── evil.com 在白名单？ → 不在白名单
    │   → 拒绝：返回 403 Forbidden ✗
```

```
沙箱代码：requests.get("https://pypi.org/simple/requests/")
    │
    ▼
nftables: TCP → 10.200.0.1:8888 → ACCEPT
    │
    ▼
HTTP 代理：
    收到 CONNECT pypi.org:443
    │
    ├── pypi.org 在白名单？ → 是
    │   → 建立隧道，双向转发 ✓
```

### 3.3 代理过滤流程

```
外部调用 nsjail-run 发送命令
        │
        ▼
连接到 /run/nsjail.sock
        │
        ▼
发送命令字符串
        │
        ▼
nsjail 主进程接收命令
        │
        ▼
在已初始化的隔离环境中 fork 子进程
        │
        ▼
子进程执行命令
        │
        ├── stdout → 通过 socket 返回
        ├── stderr → 通过 socket 返回
        └── 退出码 → 通过 socket 返回
        │
        ▼
nsjail-run 输出结果并退出
        │
        ▼
沙箱主进程继续等待下一条命令
```

## 4. 三层全景回顾

把三层叠在一起看一条完整请求路径：

```
沙箱内代码：pip install requests
    │
    ├─ ① 解析 pypi.org
    │     DNS 请求 (UDP 53) → netns 盒子内 → veth_j → veth_h → 宿主机 DNS → 解析成功
    │     ↑ 第一层 netns 提供了容器  ↑ 第二层 nftables 允许 DNS
    │
    ├─ ② 连接 pypi.org:443
    │     TCP 请求 → netns 盒子内 → nftables: 目标是什么？
    │     ├─ 是 10.200.0.1:8888（代理端口）? → ✅ 放行
    │     └─ 是 192.168.1.1:443（内网直连）? → ❌ DROP
    │     ↑ 第二层 nftables 做 IP:端口级过滤
    │
    └─ ③ 代理决定是否放行
          代理收到 CONNECT pypi.org:443
          ├─ pypi.org 在白名单？ → ✅ 建立隧道，双向转发
          └─ evil.com 在黑名单？ → ❌ 403 Forbidden
          ↑ 第三层代理做域名级过滤
```

**每一层解决上游解决不了的精确度问题：**

| 层 | 能精确到 | 盲区 |
|---|---------|------|
| netns | 完全隔离（进程关盒子） | 太粗暴，全有或全无 |
| nftables | IP + 端口 | 同一 IP:端口上的不同域名分不出 |
| HTTP 代理 | 域名 + URL 路径 | 只认 HTTP/HTTPS，其他协议直接 DROP |

## 5. 在你的项目中的实际对应

```
容器启动时（setup_netns.sh）：
  ├── ip netns add starmerx_jail          ← 创建盒子（第一层）
  ├── ip link add veth_j_h type veth ...   ← veth pair
  ├── nft add table/chain/rule ...         ← 防火墙规则（第二层）
  └── starmerx-fileio start-proxy &        ← 代理守护进程（第三层）

代码执行时（每次 run-code）：
  ip netns exec starmerx_jail \           ← 进入盒子
    nsjail --config ... \                  ← nsjail 只管文件/进程隔离
      -- starmerx-fileio run-code ...      ← 代码在盒子里跑
        HTTP_PROXY=http://10.200.0.1:8888  ← 流量自动走代理（第三层）
```
